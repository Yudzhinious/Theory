# День 10 — Базы данных: SQL, ACID, транзакции, индексы

> Цель: уверенно писать запросы с JOIN/GROUP BY и объяснить ACID, изоляцию и индексы.

---

## 0. Что такое база данных и зачем она нужна

База данных (БД) — организованное хранилище данных, которым управляет СУБД
(система управления базами данных). СУБД берёт на себя сохранность данных на
диске, конкурентный доступ, транзакции, восстановление после сбоев и язык
запросов (SQL).

Аналогия: таблица в Excel тоже хранит данные, но не умеет:
- гарантировать, что при сбое питания данные не потеряются;
- обслуживать тысячи одновременных пользователей без порчи;
- связывать таблицы и следить за целостностью связей.

Именно это и даёт СУБД.

## 1. Виды баз данных

**Реляционные (SQL):** таблицы, жёсткая схема, SQL, ACID. Примеры: PostgreSQL, MySQL, Oracle. Для целостности, сложных JOIN, отчётности.

**NoSQL:**

| Тип | Примеры | Когда |
|---|---|---|
| Документные | MongoDB | гибкая схема, JSON |
| Ключ-значение | Redis, Memcached | кэш, сессии, очереди |
| Колоночные | ClickHouse, Cassandra | аналитика (OLAP) |
| Графовые | Neo4j | связи, рекомендации |

**Сравнение SQL и NoSQL:**

| Критерий | SQL | NoSQL |
|---|---|---|
| Схема | жёсткая, заранее | гибкая |
| Связи | JOIN, FK | обычно денормализация |
| Транзакции | ACID | часто BASE, eventual |
| Масштабирование | вертикальное + реплики | горизонтальное (шарды) |
| Запросы | стандартный SQL | свои API |
| Хорошо для | целостность, отчёты | объём, гибкость, скорость |

> **BASE** (Basically Available, Soft state, Eventual consistency) — альтернатива
> ACID в распределённых NoSQL-системах.

## 2. Основы SQL

```sql
-- CRUD
INSERT INTO users (name, age) VALUES ('Аня', 20);
SELECT id, name FROM users WHERE age >= 18 ORDER BY name LIMIT 10;
UPDATE users SET age = 21 WHERE id = 1;
DELETE FROM users WHERE id = 1;
```

Разберём каждый оператор:
- **INSERT** — добавляет строку. Колонки можно перечислять не все, остальные
  получат `DEFAULT` или `NULL`.
- **SELECT** — читает. `WHERE` фильтрует, `ORDER BY` сортирует, `LIMIT` ограничивает.
- **UPDATE** — меняет. **Без `WHERE` обновит все строки!**
- **DELETE** — удаляет. Тоже **без `WHERE` удалит всё**.

**Типичная ошибка:**

```sql
-- ❌ Забудете WHERE — снесёте всю таблицу
DELETE FROM users;

-- ✅ Сначала проверьте условие через SELECT
SELECT * FROM users WHERE id = 1;
DELETE FROM users WHERE id = 1;
```

**Агрегация:**
```sql
SELECT city, COUNT(*) AS cnt, AVG(age) AS avg_age
FROM users
GROUP BY city
HAVING COUNT(*) > 5
ORDER BY cnt DESC;
```
- `WHERE` — фильтр до группировки, `HAVING` — после.

**Порядок выполнения запроса** (логически, не как пишется):

```text
FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT
```

Поэтому в `WHERE` нельзя использовать псевдонимы из `SELECT`, а в `ORDER BY` — можно.

Основные агрегаты:

| Функция | Что считает |
|---|---|
| `COUNT(*)` | число строк |
| `COUNT(col)` | число не-NULL значений |
| `SUM(col)` | сумму |
| `AVG(col)` | среднее (делит на не-NULL) |
| `MIN`/`MAX` | минимум/максимум |

## 3. JOIN

```sql
SELECT u.name, o.total
FROM users u
JOIN orders o ON o.user_id = u.id;        -- INNER: только совпадения
```

| JOIN | Результат |
|---|---|
| `INNER JOIN` | строки, где есть совпадение в обеих таблицах |
| `LEFT JOIN` | все строки левой + совпадения правой (иначе NULL) |
| `RIGHT JOIN` | зеркально LEFT |
| `FULL JOIN` | все строки обеих таблиц |
| `CROSS JOIN` | декартово произведение |

**Пошаговый разбор INNER JOIN:**

```sql
-- users:  id | name       orders: id | user_id | total
--         1  | Аня                10 |   1     | 100
--         2  | Борис              11 |   1     | 50
--         3  | Вера               12 |   2     | 200

SELECT u.name, o.total
FROM users u
JOIN orders o ON o.user_id = u.id;
```

Результат:
```text
Аня   | 100
Аня   | 50
Борис | 200
```
Вера остаётся без заказов и в INNER JOIN **не попадает**.

```sql
-- LEFT JOIN покажет и Веру (с NULL вместо заказа)
SELECT u.name, o.total
FROM users u
LEFT JOIN orders o ON o.user_id = u.id;
```
```text
Аня   | 100
Аня   | 50
Борис | 200
Вера  | NULL
```

**Как найти пользователей без заказов** (частый вопрос):

```sql
SELECT u.name
FROM users u
LEFT JOIN orders o ON o.user_id = u.id
WHERE o.id IS NULL;
```

**Подводный камень:** забыть условие `ON` — получите `CROSS JOIN` и взрывной
размер результата (N × M строк).

## 4. Ключи и связи

- **Primary Key** — уникально идентифицирует строку, не NULL, часто автоинкремент.
- **Foreign Key** — ссылка на PK другой таблицы, обеспечивает ссылочную целостность (`ON DELETE CASCADE` и т.д.).

| Связь | Реализация |
|---|---|
| 1:1 | FK с `UNIQUE` |
| 1:many | FK в таблице «многих» |
| many:many | промежуточная таблица с двумя FK |

```sql
CREATE TABLE orders (
    id       SERIAL PRIMARY KEY,
    user_id  INT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    total    NUMERIC(10,2) NOT NULL
);
```

Варианты поведения при удалении родителя:

| Опция | Что делает |
|---|---|
| `CASCADE` | удаляет связанные строки |
| `SET NULL` | обнуляет FK |
| `RESTRICT` | запрещает удаление |
| `NO ACTION` | как RESTRICT (отложенная проверка) |

**Many-to-many** через промежуточную таблицу:

```sql
CREATE TABLE student_course (
    student_id INT REFERENCES students(id),
    course_id  INT REFERENCES courses(id),
    PRIMARY KEY (student_id, course_id)     -- составной ключ не даёт дублей
);
```

## 5. ACID

- **Atomicity** — всё или ничего.
- **Consistency** — перевод из одного корректного состояния в другое.
- **Isolation** — параллельные транзакции не мешают друг другу.
- **Durability** — после `COMMIT` данные сохраняются даже при сбое.

**Аналогия — перевод денег:** списание со счёта A и зачисление на B должны
произойти вместе (Atomicity). Баланс не может стать отрицательным, если есть
правило (Consistency). Другой перевод не должен видеть промежуточное состояние
(Isolation). После подтверждения перевод не потеряется при отключении питания
(Durability).

## 6. Транзакции и уровни изоляции

```sql
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;   -- или ROLLBACK
```
`SAVEPOINT` — промежуточная точка для частичного отката.

```sql
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
SAVEPOINT after_debit;
UPDATE accounts SET balance = balance + 100 WHERE id = 999;  -- ошиблись
ROLLBACK TO after_debit;     -- откатили только второе
COMMIT;                       -- первое осталось
```

**Аномалии:**
- **Dirty read** — чтение незафиксированных данных.
- **Non-repeatable read** — повторное чтение даёт другое значение.
- **Phantom read** — появляются новые строки по условию.

**Уровни (от слабого к сильному):**

| Уровень | Dirty | Non-repeatable | Phantom |
|---|---|---|---|
| Read Uncommitted | ✅ | ✅ | ✅ |
| Read Committed | ❌ | ✅ | ✅ |
| Repeatable Read | ❌ | ❌ | ✅* |
| Serializable | ❌ | ❌ | ❌ |

> ✅ — аномалия возможна, ❌ — невозможна. `*` В PostgreSQL Repeatable Read
> фактически не допускает и phantom read (реализован через снимок MVCC).
> Более строгий уровень = меньше аномалий, но больше блокировок и ниже параллелизм.

## 7. Индексы

Индекс — структура для быстрого поиска (обычно **B-tree**). Ускоряет `SELECT`/`WHERE`/`JOIN`, но замедляет вставку/обновление и занимает место.

```sql
CREATE INDEX idx_users_email ON users(email);
CREATE UNIQUE INDEX idx_users_login ON users(login);
```

**Аналогия:** оглавление книги. Без него поиск темы — перелистывание всех
страниц (Seq Scan). С ним — сразу к нужной странице (Index Scan). Но при
добавлении главы оглавление приходится переписать (цена записи).

- **B-tree** — по умолчанию, для диапазонов и сортировки.
- **Hash** — только точное равенство.
- **GIN/GiST** — полнотекстовый поиск, массивы, гео (PostgreSQL).
- **Составной индекс** — порядок колонок важен.
- **Индекс не используется**, если функция применяется к колонке (`WHERE lower(email) = ...`).

| Индекс | Подходит для | Не подходит |
|---|---|---|
| B-tree | `=`, `<`, `>`, `BETWEEN`, `ORDER BY` | поиск по подстроке в середине |
| Hash | `=` | диапазоны, сортировка |
| GIN | массивы, JSONB, полнотекст | обычные скалярные сравнения |
| GiST | гео, диапазоны | точное равенство |

**Как неправильно / как правильно:**

```sql
-- ❌ Функция на колонке мешает использовать обычный индекс
SELECT * FROM users WHERE lower(email) = 'a@b.com';

-- ✅ Функциональный индекс
CREATE INDEX idx_lower_email ON users(lower(email));
SELECT * FROM users WHERE lower(email) = 'a@b.com';

-- ❌ LIKE с ведущим % не использует B-tree
SELECT * FROM users WHERE name LIKE '%аня%';

-- ✅ Префиксный поиск использует индекс
SELECT * FROM users WHERE name LIKE 'Аня%';
```

**Цена индексов:**

| Операция | Без индекса | С индексом |
|---|---|---|
| `SELECT` по колонке | медленно (полный скан) | быстро |
| `INSERT`/`UPDATE`/`DELETE` | быстрее | медленнее (обновить индекс) |
| Место на диске | меньше | больше |

## 8. Нормализация

- **1НФ** — атомарные значения (без списков в ячейке).
- **2НФ** — нет частичной зависимости от составного ключа.
- **3НФ** — нет транзитивных зависимостей (неключевой → неключевой).

**Денормализация** — намеренная избыточность ради скорости чтения (отчёты).

**Пример нарушения 1НФ:**

```text
❌  id | name | phones
    1  | Аня  | 111, 222, 333      -- список в одной ячейке

✅  id | name     ✅  user_id | phone
    1  | Аня          1       | 111
                     1       | 222
                     1       | 333
```

**Пример нарушения 3НФ:** в таблице `orders` хранят `user_id` и `user_city`.
Город зависит от `user_id`, а не от заказа → транзитивная зависимость. Город
нужно держать в `users`.

| Форма | Условие | Что устраняет |
|---|---|---|
| 1НФ | атомарность | списки в ячейках |
| 2НФ | 1НФ + нет частичной зависимости | зависимость от части ключа |
| 3НФ | 2НФ + нет транзитивной зависимости | неключевой → неключевой |
| BCNF | усиление 3НФ | аномалии с несколькими ключами |

**Плюсы/минусы нормализации:**

| | Нормализация | Денормализация |
|---|---|---|
| Дублирование | минимум | намеренно есть |
| Запись | проще и безопаснее | риск рассинхрона |
| Чтение | много JOIN | меньше JOIN, быстрее |
| Когда | OLTP (транзакции) | OLAP (отчёты) |

## 10. Мини-итог и связки

- Реляционная модель строится на таблицах, ключах и связях; целостность держит СУБД.
- ACID и уровни изоляции — про надёжность при конкурентном доступе.
- Индексы ускоряют чтение ценой записи и места.
- Нормализация — для OLTP, денормализация — для OLAP.

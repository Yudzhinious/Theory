## 1. Реляционная модель и ключи

- **Candidate key** — любой минимальный уникальный набор колонок.
- **Primary key** — выбранный candidate key; **surrogate** (авто-id) vs **natural** (email, ISBN).
- **Foreign key** — ссылка + ссылочная целостность (`ON DELETE/UPDATE CASCADE/SET NULL/RESTRICT`).
- Ограничения: `NOT NULL`, `UNIQUE`, `CHECK`, `DEFAULT`.

```sql
CREATE TABLE accounts (
    id      SERIAL PRIMARY KEY,                    -- surrogate key
    email   TEXT UNIQUE NOT NULL,                  -- natural candidate key
    balance NUMERIC(12,2) NOT NULL DEFAULT 0
            CHECK (balance >= 0),                  -- бизнес-правило
    created TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

| Тип ключа | Пример | Плюсы | Минусы |
|---|---|---|---|
| Surrogate | `id SERIAL` | стабильный, компактный | нет бизнес-смысла |
| Natural | `email` | смысл, без лишней колонки | может меняться |

**Терминология:**
- **Суперключ** — набор колонок, уникально определяющий строку (может быть избыточным).
- **Candidate key** — минимальный суперключ.
- **Primary key** — выбранный candidate key.

## 2. NULL — трёхзначная логика

- `NULL` — «неизвестно», не равно ничему: `NULL = NULL` → `NULL` (не True).
- Проверка: `IS NULL` / `IS NOT NULL`.
- Агрегаты игнорируют NULL: `AVG` делит на число не-NULL.
- `COALESCE(a, b)` — первый не-NULL; `NULLIF(a, b)` — NULL если равны.

```sql
SELECT COALESCE(phone, email, 'нет') FROM users;
```

**Как неправильно / как правильно:**

```sql
-- ❌ Ничего не вернёт: NULL = NULL не True
SELECT * FROM users WHERE phone = NULL;

-- ✅
SELECT * FROM users WHERE phone IS NULL;
```

Логика трёхзначная: результат `AND`/`OR` может быть NULL.

| A | B | A AND B | A OR B |
|---|---|---|---|
| TRUE | NULL | NULL | TRUE |
| FALSE | NULL | FALSE | NULL |
| NULL | NULL | NULL | NULL |

Агрегаты и NULL:

```sql
-- users.age: 20, NULL, 30
SELECT COUNT(*)   AS rows_all,     -- 3
       COUNT(age) AS rows_nonnull, -- 2
       AVG(age)   AS avg_age       -- 25 (делит на 2, не на 3!)
FROM users;
```

`NULLIF` полезен для защиты от деления на ноль:

```sql
SELECT total / NULLIF(cnt, 0) AS avg FROM stats;   -- вместо деления на 0 → NULL
```

## 3. Продвинутый SQL

```sql
-- Подзапрос / EXISTS
SELECT * FROM users u
WHERE EXISTS (SELECT 1 FROM orders o WHERE o.user_id = u.id);

-- CTE (WITH)
WITH active AS (SELECT * FROM users WHERE active)
SELECT count(*) FROM active;

-- Оконные функции
SELECT name, salary,
       RANK() OVER (PARTITION BY dept ORDER BY salary DESC) AS rnk
FROM employees;

-- UNION / UNION ALL
SELECT id FROM a UNION ALL SELECT id FROM b;
```

- `UNION` убирает дубликаты (дороже), `UNION ALL` — нет.
- Оконные функции (`ROW_NUMBER`, `RANK`, `LAG`, `LEAD`, `SUM() OVER`) — без сворачивания строк.

### 3.1 Подзапрос vs JOIN vs EXISTS

| Способ | Когда лучше |
|---|---|
| `IN (подзапрос)` | небольшой список значений |
| `EXISTS` | проверка существования, коррелированный |
| `JOIN` | нужны колонки из обеих таблиц |

```sql
-- Пользователи с заказами тремя способами
SELECT DISTINCT u.* FROM users u JOIN orders o ON o.user_id = u.id;
SELECT * FROM users u WHERE u.id IN (SELECT user_id FROM orders);
SELECT * FROM users u WHERE EXISTS (SELECT 1 FROM orders o WHERE o.user_id = u.id);
```

`EXISTS` умеет **короткое замыкание** — останавливается на первой найденной строке.

### 3.2 Оконные функции подробнее

Оконная функция считает по «окну» строк, **не сворачивая** их (в отличие от `GROUP BY`).

```sql
-- Зарплата и место в отделе
SELECT name, dept, salary,
       ROW_NUMBER() OVER (PARTITION BY dept ORDER BY salary DESC) AS row_num,
       RANK()       OVER (PARTITION BY dept ORDER BY salary DESC) AS rnk,
       DENSE_RANK() OVER (PARTITION BY dept ORDER BY salary DESC) AS dense,
       LAG(salary)  OVER (PARTITION BY dept ORDER BY salary)      AS prev_salary
FROM employees;
```

| Функция | При равных значениях |
|---|---|
| `ROW_NUMBER` | разные номера (1,2,3) |
| `RANK` | пропуск (1,1,3) |
| `DENSE_RANK` | без пропуска (1,1,2) |

Разница `GROUP BY` и окна:

| | `GROUP BY` | Оконная функция |
|---|---|---|
| Число строк | сворачивает | сохраняет |
| Пример | `AVG(salary)` на отдел | `salary - AVG(salary) OVER (...)` |

### 3.3 CTE и рекурсия

```sql
WITH RECURSIVE org AS (
    SELECT id, manager_id, name, 1 AS level
    FROM employees WHERE manager_id IS NULL
    UNION ALL
    SELECT e.id, e.manager_id, e.name, org.level + 1
    FROM employees e
    JOIN org ON e.manager_id = org.id
)
SELECT * FROM org ORDER BY level;
```

Рекурсивный CTE строит иерархию (дерево подчинённости) сверху вниз.

## 4. План запроса

```sql
EXPLAIN ANALYZE SELECT ...;
```

- Смотри `Seq Scan` vs `Index Scan`, стоимость, реальное время.
- Индекс не используется: функция на колонке, несовпадение типов, `LIKE '%...'`, низкая селективность.
- `ANALYZE` обновляет статистику планировщика.

Пример плана PostgreSQL:

```text
Index Scan using idx_users_email on users  (cost=0.29..8.30 rows=1 width=64)
  Index Cond: (email = 'a@b.com'::text)
  Planning Time: 0.1 ms
  Execution Time: 0.05 ms
```

| Узел | Что значит |
|---|---|
| `Seq Scan` | полный перебор таблицы |
| `Index Scan` | поиск по индексу |
| `Index Only Scan` | всё нужное есть в индексе (covering) |
| `Bitmap Heap Scan` | индекс + пакетное чтение |
| `Hash Join` / `Nested Loop` | способы соединения |

**Когда индекс не поможет:**

```sql
-- ❌ функция на колонке
WHERE lower(email) = 'a@b.com'
-- ❌ ведущий %
WHERE name LIKE '%аня'
-- ❌ приведение типа, ломающее индекс
WHERE phone = 123456        -- phone хранится как TEXT
-- ❌ низкая селективность: половина таблицы всё равно сканируется
WHERE is_active = true
```

## 5. Индексы изнутри

- **B-tree** — сбалансированное дерево; поддерживает `=`, диапазоны, сортировку. `O(log n)`.
- **Clustered** (физический порядок строк) vs **non-clustered** (отдельная структура со ссылками).
- **Составной индекс** — порядок колонок важен (leftmost prefix).
- **Covering index** — содержит все нужные колонки → запрос только по индексу.
- **Partial** (`WHERE ...`), **functional** (`lower(email)`), **GIN/GiST** (полнотекст, массивы, гео), **Hash** (только `=`).
- Цена: замедляют запись, занимают место.

```sql
CREATE INDEX idx ON users (last_name, first_name);
CREATE INDEX idx_lower ON users (lower(email));
```

### 5.1 Как работает B-tree (пошагово)

1. Листья дерева содержат отсортированные ключи и ссылки на строки (TID).
2. Внутренние узлы хранят диапазоны и ведут к листьям.
3. Поиск значения — спуск по дереву за `O(log n)` шагов.
4. Листья связаны — удобно для диапазонов (`BETWEEN`, `ORDER BY`).

Аналогия: библиотечный каталог. Чтобы найти книгу по автору, не обходим все
полки — идём по разделам каталога, а потом к нужной полке.

### 5.2 Составной индекс и leftmost prefix

```sql
CREATE INDEX idx_abc ON t (a, b, c);
```

| Запрос | Использует индекс? |
|---|---|
| `WHERE a = 1` | ✅ |
| `WHERE a = 1 AND b = 2` | ✅ |
| `WHERE a = 1 AND b = 2 AND c = 3` | ✅ |
| `WHERE b = 2` | ❌ (нет левого префикса) |
| `WHERE a = 1 AND c = 3` | частично (только по `a`) |

**Правило:** индекс `(a, b)` работает как «телефонная книга по фамилии, потом
имени». Искать по одному имени, не зная фамилии, неудобно.

### 5.3 Covering index

```sql
CREATE INDEX idx_cover ON orders (user_id) INCLUDE (total);
-- Запрос только по индексу, без обращения к таблице (Index Only Scan):
SELECT user_id, total FROM orders WHERE user_id = 42;
```

### 5.4 Partial и functional

```sql
-- Partial: индексируем только активные строки — индекс меньше
CREATE INDEX idx_active ON users (email) WHERE is_active;

-- Functional: индекс по выражению
CREATE INDEX idx_lower_email ON users (lower(email));
SELECT * FROM users WHERE lower(email) = 'a@b.com';
```

### 5.5 Цена и правила

| Действие | Эффект |
|---|---|
| Лишние индексы | тормозят запись, занимают место |
| Индекс на колонку с 2 значениями | почти бесполезен |
| Индекс на FK | часто нужен для JOIN и каскадов |
| Регулярная `REINDEX`/`VACUUM` | поддерживают индекс здоровым |

## 6. MVCC и WAL

- **MVCC (Multi-Version Concurrency Control)** — читатели не блокируют писателей: каждая транзакция видит свою версию строк (PostgreSQL, MySQL InnoDB).
- **WAL (Write-Ahead Log)** — сначала запись в журнал, потом в данные → Durability и восстановление.
- Уровни изоляции реализуются через снапшоты/блокировки.
- **Pessimistic** (`SELECT ... FOR UPDATE`) vs **optimistic** (версии/`UPDATE ... WHERE version = ?`) блокировки.

### 6.1 Как работает MVCC (пошагово)

1. При `UPDATE` СУБД **не перезаписывает** строку, а создаёт новую версию.
2. Каждая версия помечена `xmin` (создана) и `xmax` (удалена).
3. Транзакция получает **снимок** (snapshot) и видит только версии, зафиксированные до её начала.
4. Старые версии удаляет **VACUUM** (иначе таблица «распухает»).

**Аналогия:** вместо правки документа поверх создаётся новая копия, а старые
лежат рядом. Читатель работает со своей копией и никому не мешает.

### 6.2 WAL и Durability

```text
COMMIT → запись в WAL (fsync) → [позже] применение к таблицам
```

Если сервер упал, при старте WAL «переигрывается» (recovery) — зафиксированные
транзакции не теряются. Именно поэтому `COMMIT` дорогой: нужен `fsync` на диск.

### 6.3 Pessimistic vs Optimistic

| | Pessimistic | Optimistic |
|---|---|---|
| Идея | блокируем заранее | проверяем версию при записи |
| Механизм | `SELECT ... FOR UPDATE` | `UPDATE ... WHERE version = ?` |
| Конфликты | редки, но блокировки | часты → повторы |
| Хорошо при | высокой конкуренции за строку | редких конфликтах |

```sql
-- Pessimistic
BEGIN;
SELECT balance FROM accounts WHERE id = 1 FOR UPDATE;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
COMMIT;
```

```sql
-- Optimistic
UPDATE accounts
SET balance = balance - 100, version = version + 1
WHERE id = 1 AND version = 7;
-- если затронуто 0 строк → кто-то опередил, повторить
```

## 7. Нормализация до BCNF

- 1НФ → 2НФ → 3НФ → **BCNF** (каждый детерминант — суперключ).
- 4НФ/5НФ — многозначные/соединительные зависимости (редко).
- **Денормализация** — сознательная избыточность ради скорости чтения.

| Форма | Устраняет | Пример проблемы |
|---|---|---|
| 1НФ | неатомарные значения | `phones = '111,222'` |
| 2НФ | частичную зависимость от составного ключа | цена зависит только от `product_id` |
| 3НФ | транзитивную зависимость | `order → user_id → city` |
| BCNF | зависимость не-суперключа | аномалии при нескольких ключах |

**Как это выглядит на практике:**

```text
❌ orders(order_id, product_id, product_name, product_price)
   product_name зависит от product_id, а не от заказа → нарушение 3НФ

✅ orders(order_id, product_id, qty)
   products(product_id, name, price)
```

## 8. Транзакции на практике

```sql
BEGIN;
SELECT balance FROM accounts WHERE id = 1 FOR UPDATE;   -- блокировка строки
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;
```

- Без `FOR UPDATE` возможна **lost update**.
- Держи транзакции **короткими** — длинные блокировки вредят конкурентности.

**Lost update — как воспроизвести:**

```text
T1: SELECT balance → 100
T2: SELECT balance → 100
T1: UPDATE balance = 100 - 10 → 90
T2: UPDATE balance = 100 - 20 → 80     -- изменение T1 потеряно!
```

Решение — `FOR UPDATE` (pessimistic) или проверка версии (optimistic).

**Практические правила:**
- Не держите транзакцию открытой во время сетевых вызовов к другим сервисам.
- Блокируйте строки в одном и том же порядке во всех транзакциях.
- Ставьте `statement_timeout`/`lock_timeout`, чтобы не зависнуть.

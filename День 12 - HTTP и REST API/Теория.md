## 0. Что такое HTTP и зачем он нужен

HTTP (HyperText Transfer Protocol) — протокол прикладного уровня, по которому
браузер и сервер общаются. Модель простая: **клиент отправляет запрос — сервер
возвращает ответ**. HTTP **stateless**: сервер не помнит предыдущие запросы; вся
«память» либо в самом запросе (токен), либо в отдельном хранилище (сессия).

Аналогия: обмен письмами. Каждое письмо самодостаточно: в нём есть адрес, тема,
текст. Почтальон не помнит, что вы писали раньше, — и это упрощает масштабирование.

## 1. HTTP — основы

HTTP — протокол прикладного уровня, модель «запрос — ответ», **stateless** (сервер не помнит клиента между запросами).

**Структура запроса:** метод, URL, заголовки, тело.
**Ответ:** статус-код, заголовки, тело.

- HTTP — порт **80**, HTTPS — порт **443**.
- **HTTPS** = HTTP + TLS-шифрование: конфиденциальность, целостность, аутентификация сервера.

Пример «сырого» запроса:

```text
GET /users/123 HTTP/1.1
Host: api.example.com
Accept: application/json
Authorization: Bearer eyJhbGci...

(тело отсутствует у GET)
```

Пример ответа:

```text
HTTP/1.1 200 OK
Content-Type: application/json
Content-Length: 42

{"id": 123, "name": "Аня"}
```

**Что даёт HTTPS:**
- **конфиденциальность** — данные зашифрованы;
- **целостность** — их нельзя незаметно подменить;
- **аутентификация сервера** — сертификат подтверждает, что это тот самый сайт.

## 2. Методы HTTP

| Метод | Назначение | Идемпотентный | Безопасный |
|---|---|---|---|
| GET | получить | ✅ | ✅ |
| POST | создать | ❌ | ❌ |
| PUT | заменить целиком | ✅ | ❌ |
| PATCH | частично обновить | ⚠️ (обычно да) | ❌ |
| DELETE | удалить | ✅ | ❌ |
| HEAD/OPTIONS | метаданные/CORS | ✅ | ✅ |

- **Идемпотентность** — повторный запрос даёт тот же результат, что и один.
- **Безопасность** — метод не меняет состояние.

**Важно не путать:**
- **Безопасный** (safe) — не меняет состояние: GET, HEAD, OPTIONS.
- **Идемпотентный** — повтор не меняет итог: GET, PUT, DELETE (даже если меняет
  состояние). POST не идемпотентен: два POST создадут две записи.

```text
DELETE /users/1   → первый раз удалил, второй раз 404/204, но состояние то же ✅
POST   /users     → два раза создаст двух пользователей ❌
```

## 3. PUT vs PATCH

- **PUT** — полная замена ресурса (клиент присылает все поля). Если поле не передано — обнуляется.
- **PATCH** — частичное изменение (только переданные поля).

```http
PUT /users/1
{"name": "Аня", "age": 21, "city": "Москва"}     # заменили всё

PATCH /users/1
{"city": "Казань"}                                # изменили только город
```

**Типичная ошибка:** использовать PATCH-семантику с PUT — незаданные поля
обнулятся (или станут NULL). И наоборот: ждать от PATCH полной замены.

| | PUT | PATCH |
|---|---|---|
| Что шлём | весь ресурс | только изменения |
| Отсутствующие поля | обнуляются | остаются как были |
| Идемпотентность | гарантирована | обычно да |
| Тело | обычно полное | diff/merge |

## 4. Статус-коды

| Диапазон | Значение |
|---|---|
| 1xx | информационные |
| 2xx | успех (200 OK, 201 Created, 204 No Content) |
| 3xx | перенаправление (301, 302, 304 Not Modified) |
| 4xx | ошибка клиента (400, 401, 403, 404, 409, 422, 429) |
| 5xx | ошибка сервера (500, 502, 503) |

- **401 Unauthorized** — не аутентифицирован.
- **403 Forbidden** — аутентифицирован, но нет прав.
- **409 Conflict** — конфликт (например, дубликат).

**Расшифровка частых кодов:**

| Код | Когда использовать |
|---|---|
| 200 OK | успешный GET/PUT |
| 201 Created | создан ресурс (в ответе — `Location`) |
| 204 No Content | успех без тела (DELETE) |
| 301/302 | постоянный/временный редирект |
| 304 Not Modified | ресурс не изменился (кэш) |
| 400 Bad Request | некорректный запрос |
| 401 Unauthorized | нет/неверные креды |
| 403 Forbidden | нет прав |
| 404 Not Found | ресурс не найден |
| 409 Conflict | конфликт состояния |
| 422 Unprocessable Entity | валидация не пройдена |
| 429 Too Many Requests | превышен rate limit |
| 500 Internal Server Error | ошибка на сервере |
| 502 Bad Gateway | прокси получил плохой ответ |
| 503 Service Unavailable | сервис недоступен |

**401 vs 403 — как неправильно / как правильно:**

```text
❌ Нет токена → 403          (это про «не аутентифицирован» → 401)
❌ Токен есть, но нет прав → 401  (это «нет доступа» → 403)

✅ Нет/просрочен токен → 401 + WWW-Authenticate
✅ Токен валиден, роль не позволяет → 403
```

## 5. REST

**REST** — архитектурный стиль (Рой Филдинг, 2000). **RESTful** — API, следующее его принципам.

Шесть принципов:
1. клиент-сервер;
2. stateless (нет состояния на сервере);
3. кэширование;
4. единообразный интерфейс (URI + методы + HATEOAS);
5. слои (прокси, балансировщики);
6. код по требованию (опционально).

```text
GET    /users          # список
GET    /users/123      # один
POST   /users          # создать
PUT    /users/123      # заменить
PATCH  /users/123      # частично обновить
DELETE /users/123      # удалить
```

Не RESTful: один URI для всего (`/api.php?action=getUser`), только POST, хранение сессий на сервере.

**Правила именования ресурсов:**
- существительные во множественном числе: `/users`, не `/getUsers`;
- вложенность для связей: `/users/123/orders`;
- фильтры — в query: `/users?city=Москва&page=2`.

**Плохо → хорошо:**

| Не RESTful | RESTful |
|---|---|
| `POST /createUser` | `POST /users` |
| `GET /getUser?id=1` | `GET /users/1` |
| `POST /deleteUser?id=1` | `DELETE /users/1` |
| `POST /updateUser` | `PATCH /users/1` |

## 6. Идентификация, аутентификация, авторизация

1. **Идентификация** — «кто я?» (логин).
2. **Аутентификация** — «докажи» (пароль/токен).
3. **Авторизация** — «что разрешено» (права).

**Схемы аутентификации:**
- **Basic** — логин:пароль в Base64 (только с HTTPS!).
- **Bearer** — токен в `Authorization: Bearer <token>`.
- **API Key** — ключ в заголовке/параметре.

```http
Authorization: Basic YW5uYUBleGFtcGxlLmNvbToxMjM0
Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...
X-API-Key: 3f8a1c...
```

**Аналогия:** охрана на входе в офис. Идентификация — вы назвали имя. Аутентификация —
показали пропуск. Авторизация — пропуск открывает только ваш этаж, а не серверную.

| Схема | Где креды | Для чего |
|---|---|---|
| Basic | заголовок (base64) | просто, только с HTTPS |
| Bearer/JWT | заголовок | SPA, мобильные, API |
| API Key | заголовок/параметр | сервис-сервис |

## 7. Сессии vs токены, JWT

- **Серверные сессии:** сервер хранит session ID, клиент — cookie. Минус: сложно масштабировать (общее хранилище).
- **JWT (Stateless):** токен содержит данные и подпись; сервер только проверяет подпись. Минус: сложно отозвать — делают короткоживущим.

**JWT = Header.Payload.Signature** (три части через точку):
- Header — алгоритм (`HS256`/`RS256`);
- Payload — claims (id, роль, `exp`);
- Signature — подпись секретным ключом.

```text
eyJhbGciOiJIUzI1NiJ9 . eyJzdWIiOiIxIiwiZXhwIjoxNzAwfQ . dBjftJeZ4CVP...
   header                 payload (claims)                  signature
```

```python
import jwt

token = jwt.encode(
    {"sub": "1", "role": "admin", "exp": 1700000000},
    "secret",
    algorithm="HS256",
)
payload = jwt.decode(token, "secret", algorithms=["HS256"])
print(payload["role"])          # admin
```

| | Серверные сессии | JWT |
|---|---|---|
| Где состояние | на сервере | в токене |
| Масштабирование | нужно общее хранилище | stateless |
| Отзыв | мгновенный | сложный |
| Размер | маленькая cookie | крупный токен |

**OAuth 2.0** — протокол **авторизации** (делегирование доступа), access + refresh токены.
**OpenID Connect** — надстройка над OAuth для **аутентификации** (кнопка «Войти через Google»).

> OAuth отвечает на вопрос «что приложение может делать от моего имени», а OIDC
> добавляет «кто пользователь».

## 8. Хранение паролей и безопасность

- Пароли — только в виде **хеша** (односторонняя функция), никогда в открытом виде.
- **Соль (salt)** — случайная строка на каждый пароль, чтобы одинаковые пароли давали разные хеши.
- **bcrypt** — медленный адаптивный алгоритм (защита от перебора).
- **CORS** — механизм браузера, разрешающий/запрещающий кросс-доменные запросы.
- **CSRF** — подделка запроса от имени пользователя; защита — CSRF-токены.
- **XSS** — внедрение чужого JS; защита — экранирование данных.

**Как неправильно / как правильно:**

```python
# ❌ Открытый пароль или быстрый хеш без соли
db.save(password=password)
db.save(password=hashlib.md5(password.encode()).hexdigest())

# ✅ Медленный хеш с солью
import bcrypt
hashed = bcrypt.hashpw(password.encode(), bcrypt.gensalt())
bcrypt.checkpw(password.encode(), hashed)      # True/False
```

| Угроза | Суть | Защита |
|---|---|---|
| CSRF | чужой сайт шлёт запрос от вашего имени | CSRF-токен, `SameSite` cookie |
| XSS | внедрение JS на страницу | экранирование, CSP |
| SQL-инъекция | вставка SQL в запрос | параметризация |
| Брутфорс | перебор паролей | bcrypt, rate limiting |

## 9. WSGI vs ASGI

| | WSGI | ASGI |
|---|---|---|
| Модель | синхронная, блокирующая | асинхронная, неблокирующая |
| Протоколы | HTTP/1.1 | HTTP/1.1, HTTP/2, WebSocket |
| Интерфейс | `def app(environ, start_response)` | `async def app(scope, receive, send)` |
| Серверы | Gunicorn, uWSGI | Uvicorn, Hypercorn, Daphne |
| Фреймворки | Flask, Django (по умолч.) | FastAPI, Starlette |

**Почему ASGI появился:** WSGI обрабатывает запрос в одном потоке до конца;
для тысяч одновременных соединений (особенно WebSocket) нужен асинхронный
интерфейс. ASGI позволяет держать много соединений в одном процессе.

```python
# WSGI
def app(environ, start_response):
    start_response("200 OK", [("Content-Type", "text/plain")])
    return [b"Hello"]

# ASGI
async def app(scope, receive, send):
    await send({"type": "http.response.start", "status": 200})
    await send({"type": "http.response.body", "body": b"Hello"})
```

## 11. Мини-итог и связки

- HTTP stateless, а HTTPS добавляет шифрование и подлинность.
- Методы различаются идемпотентностью и безопасностью.
- Коды — язык ошибок и успеха; 401 и 403 не взаимозаменяемы.
- REST — про ресурсы и единообразие интерфейса.
- JWT удобен для stateless, но плохо отзывается.
- Пароли — только через bcrypt с солью.
- WSGI — синхронный, ASGI — асинхронный и для WebSocket.

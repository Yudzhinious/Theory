## 1. Версии HTTP

- **HTTP/1.0** — новое соединение на запрос.
- **HTTP/1.1** — keep-alive, пайплайнинг (проблема head-of-line).
- **HTTP/2** — бинарный, мультиплексирование потоков в одном соединении, сжатие заголовков (HPACK), server push.
- **HTTP/3** — поверх QUIC (UDP), меньше задержки на установке.

**Проблема head-of-line (HOL):** в HTTP/1.1 ответы в одном соединении идут
строго по порядку; медленный ответ блокирует следующие. HTTP/2 решает это
мультиплексированием: несколько потоков в одном TCP-соединении.

| Версия | Транспорт | Мультиплексирование | Сжатие заголовков |
|---|---|---|---|
| HTTP/1.1 | TCP | нет (пайплайнинг не решает HOL) | нет |
| HTTP/2 | TCP | да (потоки) | HPACK |
| HTTP/3 | QUIC/UDP | да | QPACK |

**Аналогия:** HTTP/1.1 — одна касса, где нельзя начать обслуживать следующего,
пока текущий не расплатится. HTTP/2 — несколько касс в одном зале.

## 2. Заголовки, которые важно знать

| Заголовок | Смысл |
|---|---|
| `Content-Type` | тип тела (`application/json`) |
| `Accept` | какие типы принимает клиент |
| `Authorization` | схема + креды (`Bearer <jwt>`) |
| `Cache-Control` | правила кэширования |
| `ETag` / `If-None-Match` | условные запросы (304) |
| `Location` | куда ведёт (201/3xx) |
| `Retry-After` | когда повторить (429/503) |

Дополнительно полезно знать:

| Заголовок | Смысл |
|---|---|
| `Host` | целевой хост (виртуальные хосты) |
| `User-Agent` | клиент |
| `Cookie` / `Set-Cookie` | состояние клиента |
| `Content-Length` | длина тела |
| `Vary` | по каким заголовкам кэшировать |
| `X-RateLimit-*` | остаток лимита |

**Content negotiation:** клиент говорит, что принимает (`Accept`), сервер
отвечает подходящим `Content-Type`. Отсюда `406 Not Acceptable`, если ничего
не подходит.

## 3. Кэширование HTTP

- `Cache-Control: max-age=3600`, `no-store`, `no-cache`, `private/public`.
- **ETag** (версия ресурса) → клиент шлёт `If-None-Match` → сервер отвечает `304 Not Modified` (тело не передаётся).
- **Last-Modified** + `If-Modified-Since`.
- Уровни: браузер, CDN, reverse proxy, приложение.

**Директивы `Cache-Control`:**

| Директива | Значение |
|---|---|
| `max-age=N` | свежесть N секунд |
| `no-cache` | кэшировать, но перепроверять перед использованием |
| `no-store` | не сохранять вовсе |
| `private` | только браузер, не общие прокси |
| `public` | можно всем |
| `must-revalidate` | после устаревания обязательна проверка |

**Условный запрос по шагам:**

```text
1. Сервер: 200 OK, ETag: "v5"
2. Клиент кэширует ответ.
3. Клиент: GET с If-None-Match: "v5"
4. Сервер видит, что версия та же → 304 Not Modified (тела нет)
5. Клиент берёт данные из кэша.
```

```http
GET /users/1
If-None-Match: "v5"

HTTP/1.1 304 Not Modified
ETag: "v5"
```

| Механизм | Что проверяет | Заголовки |
|---|---|---|
| ETag | точную версию (хеш) | `ETag` / `If-None-Match` |
| Last-Modified | дату изменения | `Last-Modified` / `If-Modified-Since` |

ETag надёжнее: дата имеет точность до секунды и может «совпасть» у разных версий.

## 4. Аутентификация глубоко

- **Basic** — `base64(login:password)`, только по HTTPS.
- **Bearer/JWT** — токен в `Authorization`.
- **API Key** — долгоживущий ключ для сервисов.
- **OAuth 2.0 flows:** Authorization Code (+ PKCE для SPA/mobile), Client Credentials (сервис-сервис), Device Code.
- **Refresh token** — получить новый access без повторного логина; **ротация** refresh.
- **OIDC** — надстройка для аутентификации (`id_token` в формате JWT).

**JWT:** `Header.Payload.Signature`. Алгоритмы `HS256` (общий секрет) / `RS256` (приватный ключ подписи, публичный — проверки). **Атаки:** `alg=none`, подмена HS/RS, отсутствие проверки `exp`/`aud`. Токен **нельзя отозвать** до истечения → короткий срок + blacklist.

### 4.1 Authorization Code Flow + PKCE

```text
1. Клиент → Auth Server: /authorize?...&code_challenge=...
2. Пользователь логинится и даёт согласие.
3. Auth Server → Клиент: redirect c ?code=...
4. Клиент → Auth Server: /token с code + code_verifier
5. Auth Server → Клиент: access_token + refresh_token
6. Клиент → API: Authorization: Bearer <access_token>
```

**PKCE** (`code_challenge`/`code_verifier`) защищает публичных клиентов (SPA,
мобильные), у которых нет безопасного места для секрета, от перехвата `code`.

### 4.2 Атаки на JWT и защита

| Атака | Суть | Защита |
|---|---|---|
| `alg=none` | подпись отключена | явно задавать допустимые алгоритмы |
| HS/RS confusion | подписать HS публичным ключом RS | не доверять `alg` из токена |
| Нет проверки `exp` | просроченный токен проходит | проверять `exp`, `nbf` |
| Подмена `aud`/`iss` | токен чужой аудитории | проверять `aud`, `iss` |
| Отзыв | JWT живёт до истечения | короткий срок + blacklist/версия |

```python
# ✅ Явно ограничиваем алгоритм и проверяем claims
jwt.decode(token, key, algorithms=["RS256"], audience="my-api", issuer="auth.example.com")
```

| | HS256 | RS256 |
|---|---|---|
| Ключ | один общий секрет | приватный подпись / публичный проверка |
| Кто может подписать | все, кто знает секрет | только владелец приватного ключа |
| Для чего | монолит, простой сервис | распределённые системы |

## 5. Сессии vs токены

| | Серверные сессии | JWT |
|---|---|---|
| Состояние | на сервере | в токене |
| Отзыв | легко | сложно |
| Масштаб | общее хранилище | stateless |
| Размер | маленькая cookie | крупный токен |

Практика: короткий access-JWT + refresh в `HttpOnly` cookie.

**Почему `HttpOnly`:** такой cookie недоступен из JavaScript, что защищает от
кражи токена через XSS. `Secure` — только по HTTPS. `SameSite` — защита от CSRF.

```http
Set-Cookie: refresh=...; HttpOnly; Secure; SameSite=Strict; Path=/auth/refresh
```

## 6. REST и зрелость

- **Модель Ричардсона:** L0 (один URI) → L1 (ресурсы) → L2 (HTTP-методы и коды) → L3 (HATEOAS).
- **HATEOAS** — ссылки на связанные действия в ответе.
- **Идемпотентность:** GET/PUT/DELETE/HEAD — да, POST — нет.
- **Content negotiation** через `Accept`.
- **Версионирование:** URL (`/v1`), заголовок (`Accept: ...version=1`), query (`?v=1`).

| Уровень | Что добавлено | Пример |
|---|---|---|
| L0 | один endpoint | `POST /api` |
| L1 | ресурсы | `POST /users` |
| L2 | методы и коды | `DELETE /users/1 → 204` |
| L3 | HATEOAS | ссылки в ответе |

HATEOAS на практике:

```json
{
  "id": 1,
  "name": "Аня",
  "_links": {
    "self":   { "href": "/users/1" },
    "orders": { "href": "/users/1/orders" }
  }
}
```

| Способ версионирования | Пример | Плюс | Минус |
|---|---|---|---|
| URL | `/v1/users` | просто, явно | меняет URI |
| Заголовок | `Accept: application/vnd.api+json;version=1` | чисто | неудобно отлаживать |
| Query | `/users?v=1` | просто | «загрязняет» параметры |

## 7. Rate limiting и надёжность

- Алгоритмы: **fixed window**, **sliding window**, **token bucket**, **leaky bucket**.
- Ответ `429 Too Many Requests` + `Retry-After`, заголовки `X-RateLimit-*`.
- **Идемпотентные ключи** (`Idempotency-Key`) для безопасных повторов POST.
- **Retry с backoff** (экспоненциальный + jitter) на 5xx/таймауты.

### 7.1 Алгоритмы ограничения

| Алгоритм | Идея | Плюс | Минус |
|---|---|---|---|
| Fixed window | счётчик на интервал | простой | всплеск на границе |
| Sliding window | скользящий интервал | ровнее | сложнее |
| Token bucket | токены пополняются, запрос тратит | допускает всплески | настройка |
| Leaky bucket | очередь с постоянным сливом | ровный поток | задержки |

### 7.2 Идемпотентные ключи

Клиент шлёт уникальный `Idempotency-Key`. Если запрос повторился (сеть моргнула),
сервер возвращает **тот же** результат, а не создаёт дубликат.

```http
POST /payments
Idempotency-Key: 9f2c1a7e-...
```

### 7.3 Retry с backoff

```python
import time, random

def request_with_retry(fn, attempts=5):
    for i in range(attempts):
        try:
            return fn()
        except ServerError:
            if i == attempts - 1:
                raise
            delay = (2 ** i) + random.uniform(0, 1)   # экспонента + jitter
            time.sleep(delay)
```

**Jitter** предотвращает «стадо» одновременных повторов от всех клиентов.

## 8. Дизайн API: практика

- Существительные во множественном числе: `/users`, `/orders/{id}/items`.
- Пагинация: offset, page, **cursor** (стабильна при изменениях).
- Ошибки — структурированные: `{"detail": "...", "code": "..."}`.
- **GraphQL** — клиент сам выбирает поля; **gRPC** — бинарный, для сервис-сервис.
- **Webhooks** — сервер шлёт события клиенту.
- Документация — **OpenAPI/Swagger** (FastAPI генерирует автоматически).

### 8.1 Пагинация

| Тип | Пример | Плюс | Минус |
|---|---|---|---|
| Offset | `?limit=20&offset=40` | просто, есть номер страницы | дубли/пропуски при вставках |
| Cursor | `?limit=20&after=eyJ...` | стабильна | нет произвольного перехода |

```json
// Cursor-пагинация
{ "items": [...], "next_cursor": "eyJpZCI6MTIzfQ==" }
```

### 8.2 Структурированные ошибки

```json
{
  "detail": "Email уже занят",
  "code": "email_taken",
  "field": "email"
}
```

### 8.3 REST vs GraphQL vs gRPC

| | REST | GraphQL | gRPC |
|---|---|---|---|
| Формат | JSON | JSON | Protobuf (бинарный) |
| Выборка полей | сервер | клиент | сервер |
| Транспорт | HTTP | HTTP | HTTP/2 |
| Хорошо для | публичные API | гибкие клиенты | сервис-сервис |

### 8.4 Практические правила

- Не отдавайте внутренние ошибки (стек) наружу.
- Ограничивайте размер страницы (`limit <= 100`).
- Используйте таймауты и `Retry-After` в ответах.
- Держите API предсказуемым: одинаковые коды и формат ошибок.

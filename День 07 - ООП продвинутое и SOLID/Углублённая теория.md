## 1. C3-линеаризация вручную

MRO строится так: берём класс + MRO родителей (слева направо), затем последовательно выбираем «голову» списка, которая **не встречается в хвостах** других списков.

```python
class O: pass
class A(O): pass
class B(O): pass
class C(O): pass
class D(A, B): pass
class E(B, C): pass
class K(D, E): pass

print([c.__name__ for c in K.__mro__])
# K, D, A, E, B, C, O, object
```

Если порядок невозможен — `TypeError: Cannot create a consistent MRO`.

### Пошаговый разбор C3

Линеаризация `L` класса вычисляется как:

```
L[K] = K + merge(L[D], L[E], [D, E])
L[D] = [D, A, O, object]
L[E] = [E, B, C, O, object]
```

Слияние `merge`:
1. Смотрим головы: `D`, `E`, `D`. Кандидат — `D` (не встречается в хвостах).
2. Берём `D`. Остаётся `merge([A, O, object], [E, B, C, O, object], [E])`.
3. Голова `A` — берём `A` (её нет в хвостах).
4. Теперь головы `O`, `E` — `O` встречается в хвосте второго списка → пропускаем, берём `E`.
5. Далее `B`, `C`, затем `O`, `object`.

Итог: `K, D, A, E, B, C, O, object`.

### Почему нельзя просто «обойти дерево»

Наивный обход мог бы посетить `O` слишком рано. C3 гарантирует:
- локальный порядок предков,
- монотонность (порядок не меняется при наследовании),
- каждый класс ровно один раз.

### Когда падает

```python
class X: pass
class Y: pass
class A(X, Y): pass
class B(Y, X): pass
# class C(A, B): pass   # TypeError: Cannot create a consistent MRO
```

`A` требует `X` раньше `Y`, `B` — наоборот. Противоречие.

## 2. `super()` — кооперативное наследование

```python
class Base:
    def __init__(self):
        print("Base")

class A(Base):
    def __init__(self):
        print("A"); super().__init__()

class B(Base):
    def __init__(self):
        print("B"); super().__init__()

class C(A, B):
    def __init__(self):
        print("C"); super().__init__()

C()   # C → A → B → Base
```

Каждый класс вызывает `super()` — получается цепочка по MRO, а не двойной вызов `Base`.

### Что было бы без `super()`

```python
class A(Base):
    def __init__(self):
        print("A"); Base.__init__(self)   # прямой вызов

class B(Base):
    def __init__(self):
        print("B"); Base.__init__(self)

class C(A, B):
    def __init__(self):
        print("C"); A.__init__(self); B.__init__(self)
```

`Base` напечатался бы дважды. Кооперативный `super()` решает это.

### Важное правило

Если класс участвует в кооперативной цепочке, он **обязан** вызывать `super()`, даже если «ничего не делает». Иначе цепочка обрывается.

```python
class Logger:
    def __init__(self, **kwargs):
        super().__init__(**kwargs)   # пропускаем дальше
        self.log = print

class Service(Logger):
    def __init__(self, name, **kwargs):
        super().__init__(**kwargs)
        self.name = name
```

## 3. Метаклассы глубоко

Класс — это экземпляр метакласса (`type` по умолчанию).

```python
class Meta(type):
    @classmethod
    def __prepare__(mcls, name, bases):     # пространство имён класса
        return {}
    def __new__(mcls, name, bases, ns):
        ns["created"] = True
        return super().__new__(mcls, name, bases, ns)

class Foo(metaclass=Meta): pass
Foo.created   # True
```

- `__prepare__` — задаёт namespace (можно `OrderedDict`).
- `__new__` метакласса — модификация класса при создании.
- `__init_subclass__` (PEP 487) и `__set_name__` (PEP 487) — проще метаклассов для многих задач.
- Метаклассы конфликтуют при наследовании от разных метаклассов.

**Где реально:** ORM (Django/SQLAlchemy), регистрация плагинов, ABC.

### Пошаговый жизненный цикл класса

1. Python собирает тело класса в namespace.
2. `Meta.__prepare__` может задать тип этого namespace.
3. Вызывается `Meta.__new__(mcls, name, bases, ns)` — здесь класс можно изменить.
4. Вызывается `Meta.__init__(cls, name, bases, ns)` — финальная настройка.
5. Срабатывают `__set_name__` у дескрипторов.
6. Вызывается `__init_subclass__` у родителей.

### Пример: проверка, что у класса есть `__repr__`

```python
class RequireRepr(type):
    def __new__(mcls, name, bases, ns):
        cls = super().__new__(mcls, name, bases, ns)
        if "__repr__" not in ns and bases != (object,):
            raise TypeError(f"{name} должен определить __repr__")
        return cls

class Good(metaclass=RequireRepr):
    def __repr__(self): return "Good()"
```

### Почему метаклассы опасны

| Проблема | Пояснение |
|---|---|
| Сложно читать | «магия» неочевидна |
| Конфликты | нельзя наследовать от классов с разными метаклассами |
| Трудно тестировать | неявные изменения |
| Альтернативы проще | `__init_subclass__`, декораторы классов |

## 4. ABC и `register`

```python
from abc import ABC, abstractmethod

class Shape(ABC):
    @abstractmethod
    def area(self): ...

Shape.register(SomeClass)   # виртуальный подкласс без наследования
isinstance(obj, Shape)      # True
```

`Protocol` + `@runtime_checkable` — структурная проверка в рантайме (только наличие методов, не сигнатуры).

```python
from typing import Protocol, runtime_checkable

@runtime_checkable
class Flyer(Protocol):
    def fly(self) -> None: ...

class Bird:
    def fly(self): print("лечу")

print(isinstance(Bird(), Flyer))   # True — есть метод fly
```

### ABC vs Protocol vs миксин

| | ABC | Protocol | Миксин |
|---|---|---|---|
| Механизм | наследование | структура | наследование |
| Проверка | при создании | `runtime_checkable` | нет |
| Можно инстанцировать | нет | да (обычный класс) | да |
| Назначение | контракт | неявный интерфейс | переиспользование кода |

## 5. SOLID на более глубоких примерах

- **SRP:** разделяй «вычисление» и «побочные эффекты» (IO, БД, логирование).
- **OCP:** расширяй через новые реализации интерфейса, а не `if/elif` по типам.
- **LSP:** контракт (пред-/постусловия, инварианты) сохраняется в наследниках.
- **ISP:** много маленьких интерфейсов лучше одного «толстого».
- **DIP:** домен не зависит от фреймворка; инфраструктура подключается через адаптеры (DI).

### SRP: разделение вычисления и сохранения

```python
# Плохо
class Order:
    def total(self): ...
    def save_to_db(self): ...
    def print_invoice(self): ...

# Хорошо
class Order:
    def total(self): ...

class OrderRepository:
    def save(self, order): ...

class InvoicePrinter:
    def print(self, order): ...
```

### LSP: инварианты

```python
class BankAccount:
    def withdraw(self, amount):
        if amount > self.balance:
            raise ValueError("недостаточно средств")
        self.balance -= amount

class SavingsAccount(BankAccount):
    def withdraw(self, amount):
        if amount > 1000:
            raise ValueError("лимит 1000")
        super().withdraw(amount)
```

`SavingsAccount` усиливает предусловие (доп. ограничение), но не нарушает базовый контракт «нельзя уйти в минус». Если бы наследник разрешал отрицательный баланс — это нарушение LSP.

### OCP: реестр вместо `if/elif`

```python
HANDLERS = {}

def register(kind):
    def deco(cls):
        HANDLERS[kind] = cls
        return cls
    return deco

@register("email")
class EmailHandler:
    def handle(self, msg): ...

@register("sms")
class SmsHandler:
    def handle(self, msg): ...

def handle(kind, msg):
    return HANDLERS[kind]().handle(msg)
```

Добавление нового типа не меняет `handle`.

## 6. Каталог паттернов (GoF, кратко)

**Порождающие:** Singleton, Factory Method, Abstract Factory, Builder, Prototype.
**Структурные:** Adapter, Decorator, Facade, Proxy, Composite, Bridge, Flyweight.
**Поведенческие:** Strategy, Observer, Command, Iterator, Template Method, State, Chain of Responsibility.

```python
# Factory
class Dog: ...
class Cat: ...
def make(kind): return {"dog": Dog, "cat": Cat}[kind]()

# Observer
class Subject:
    def __init__(self): self._subs = []
    def subscribe(self, cb): self._subs.append(cb)
    def notify(self, e): [cb(e) for cb in self._subs]

# Builder
class Query:
    def __init__(self): self.parts = []
    def select(self, *c): self.parts.append(f"SELECT {c}"); return self
    def build(self): return " ".join(self.parts)
```

**Антипаттерны:** God Object, Spaghetti Code, Singleton-везде, преждевременная оптимизация.

### Builder подробнее

Позволяет собирать сложный объект пошагово, с цепочкой вызовов.

```python
class QueryBuilder:
    def __init__(self):
        self._select = "*"
        self._where = []
    def select(self, cols):
        self._select = ", ".join(cols)
        return self
    def where(self, cond):
        self._where.append(cond)
        return self
    def build(self):
        q = f"SELECT {self._select}"
        if self._where:
            q += " WHERE " + " AND ".join(self._where)
        return q

print(QueryBuilder().select(["id", "name"]).where("age > 18").build())
# SELECT id, name WHERE age > 18
```

### Когда паттерн — зло

- Если задача решается в 3 строки — паттерн только запутает.
- «Factory ради factory» без нескольких реализаций — лишний слой.
- Singleton глобально = скрытые зависимости и проблемы с тестами.

## 7. Композиция, DI, контейнеры

- **Dependency Injection** — передавай зависимости извне (через конструктор).
- **DI-контейнеры** (например, `dependency-injector`) автоматизируют сборку.
- Предпочитай композицию наследованию: меньше связности.

```python
class Service:
    def __init__(self, repo):     # внедряем зависимость
        self.repo = repo
```

### Почему DI облегчает тесты

```python
class FakeRepo:
    def get(self, id): return {"id": id, "name": "тест"}

class UserService:
    def __init__(self, repo):
        self.repo = repo
    def name(self, id):
        return self.repo.get(id)["name"]

svc = UserService(FakeRepo())
print(svc.name(1))   # тест — без базы данных
```

### Три способа внедрить зависимость

| Способ | Пример | Плюс |
|---|---|---|
| Через конструктор | `Service(repo)` | явно, по умолчанию |
| Через сеттер | `service.repo = repo` | гибко |
| Через параметр метода | `service.run(repo)` | локально |

Конструктор — самый предсказуемый.

### DI-контейнер (идея)

```python
class Container:
    def __init__(self):
        self._factories = {}
    def register(self, key, factory):
        self._factories[key] = factory
    def resolve(self, key):
        return self._factories[key](self)

c = Container()
c.register("repo", lambda c: FakeRepo())
c.register("service", lambda c: UserService(c.resolve("repo")))
print(c.resolve("service").name(1))
```

## 8. Мини-итог

- C3-линеаризация — детерминированный порядок предков; при противоречии — `TypeError`.
- `super()` обеспечивает кооперативное наследование и однократный вызов базы.
- Метаклассы создают/модифицируют классы; `__prepare__`, `__new__`, `__init_subclass__`.
- ABC — контракт через наследование, Protocol — структурно, миксин — переиспользование.
- SOLID: SRP, OCP, LSP, ISP, DIP — снижают связанность и упрощают расширение.
- Паттерны — каталог решений; применяйте по необходимости, избегайте антипаттернов.
- DI и композиция делают код тестируемым и слабо связанным.

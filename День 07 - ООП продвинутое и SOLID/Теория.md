# День 7 — ООП продвинутое, SOLID, паттерны

> Цель: объяснить MRO и `super()`, назвать SOLID и 2–3 паттерна проектирования.

## 0. Коротко о главном

- **MRO** — порядок поиска методов в иерархии классов; вычисляется алгоритмом C3.
- **`super()`** — не «родитель», а «следующий класс в MRO».
- **ABC** и **Protocol** задают интерфейсы: первый — через наследование, второй — структурно.
- **Метаклассы** создают классы; нужны редко (ORM, плагины).
- **SOLID** — пять принципов, снижающих связанность кода.
- **Паттерны** — проверенные решения типовых задач (Singleton, Factory, Strategy…).

Аналогия для MRO: инструкция «куда обращаться за справкой» — сначала к своему классу, потом к первому родителю, потом ко второму, и так по порядку, но каждый класс посещается ровно один раз.

## 1. MRO и C3-линеаризация

**MRO (Method Resolution Order)** — порядок, в котором Python ищет методы и атрибуты в иерархии классов. С Python 2.3 используется **C3-линеаризация**.

```python
class A: pass
class B(A): pass
class C(A): pass
class D(B, C): pass

print(D.__mro__)
# D → B → C → A → object
```

Правила C3:
1. Класс идёт раньше своих родителей.
2. Сохраняется порядок родителей из объявления.
3. При противоречии — `TypeError` (несовместимая иерархия).

**Ромбовидное наследование:**
```python
class A:
    def m(self): print("A")
class B(A):
    def m(self): print("B")
class C(A):
    def m(self): print("C")
class D(B, C): pass

D().m()   # "B" — MRO: D, B, C, A
```

### Пошаговый разбор

1. `D` наследует `B` и `C`.
2. `B` и `C` оба наследуют `A` — образуется «ромб».
3. MRO строится как `D, B, C, A, object`.
4. `D().m()` ищет `m`: у `D` нет → у `B` есть → возвращает `"B"`.
5. `C.m` и `A.m` не вызываются, потому что поиск останавливается на первом найденном.

### Как посмотреть MRO

```python
print([c.__name__ for c in D.__mro__])
# ['D', 'B', 'C', 'A', 'object']
print(D.mro())        # тот же список
```

### Когда MRO невозможен

```python
class A: pass
class B: pass
class C(A, B): pass
# class D(B, A, C): pass   # TypeError: Cannot create a consistent MRO
```

Потому что `C` требует, чтобы `A` шёл раньше `B`, а `D` — наоборот.

## 2. `super()` — не просто родитель

`super()` возвращает прокси, который делегирует вызов **следующему классу в MRO**, а не обязательно прямому родителю.

```python
class A:
    def m(self): print("A")
class B(A):
    def m(self):
        print("B")
        super().m()
class C(A):
    def m(self):
        print("C")
        super().m()
class D(B, C):
    def m(self):
        print("D")
        super().m()

D().m()   # D → B → C → A  (кооперативное наследование)
```

### Почему это важно

При **кооперативном наследовании** каждый класс вызывает `super()`, и вызовы идут цепочкой по MRO. Базовый класс `A` вызывается **один раз**, а не дважды.

Если вместо `super()` писать `A.m(self)` напрямую — в ромбовидной схеме `A.m` выполнится дважды или нарушится порядок.

### `super()` с аргументами

```python
class D(B, C):
    def m(self):
        super(D, self).m()   # явная форма, эквивалент super()
```

Внутри класса обычно пишут просто `super()`.

## 3. Абстрактные классы и протоколы

```python
from abc import ABC, abstractmethod

class Shape(ABC):
    @abstractmethod
    def area(self): ...

class Circle(Shape):
    def __init__(self, r): self.r = r
    def area(self): return 3.14 * self.r ** 2

# Shape()  # TypeError — нельзя создать абстрактный класс
```

**Protocol** — структурная типизация (утиная типизация, проверяемая статически):
```python
from typing import Protocol

class Flyer(Protocol):
    def fly(self) -> None: ...

def take_off(obj: Flyer):
    obj.fly()
```

### Разница ABC vs Protocol

| | ABC | Protocol |
|---|---|---|
| Как работает | явное наследование | структурно (по методам) |
| Проверка | при создании класса | статическая / `@runtime_checkable` |
| Нужно менять класс | да (`class X(Shape)`) | нет |
| Когда | общий базовый контракт | сторонние классы, гибкость |

### Пошаговый пример с ABC

1. `Shape(ABC)` — нельзя создать напрямую.
2. `@abstractmethod` помечает обязательный метод.
3. `Circle` реализует `area` → становится конкретным.
4. Если забыть реализовать — `TypeError` при создании.

```python
class Broken(Shape):
    pass
# Broken()   # TypeError: Can't instantiate abstract class
```

### Виртуальные подклассы

```python
class Duck:
    def area(self): return 1

Shape.register(Duck)          # Duck теперь «подкласс» Shape
print(isinstance(Duck(), Shape))   # True
```

## 4. Метаклассы

Класс класса. По умолчанию метакласс — `type`.

```python
MyClass = type("MyClass", (), {"x": 10})   # эквивалент class MyClass: x = 10

class Meta(type):
    def __new__(mcls, name, bases, dct):
        dct["version"] = 1.0
        return super().__new__(mcls, name, bases, dct)

class Foo(metaclass=Meta): pass
Foo.version   # 1.0
```

**Где нужны:** ORM (SQLAlchemy/Django собирают поля моделей), регистрация классов/плагинов, валидация интерфейса. В обычном коде — редко.

### Пошагово

1. `class Foo(metaclass=Meta)` — Python вызывает `Meta`.
2. `Meta.__new__` получает имя, родителей и словарь атрибутов.
3. Метакласс добавляет `version = 1.0`.
4. Создаётся класс `Foo` уже с этим атрибутом.

### Аналогия

Метакласс — это завод по производству чертежей. Обычный класс — чертёж объекта, а метакласс — «чертёж чертежа».

### Что проще метакласса

- `__init_subclass__` — настроить подклассы.
- `__set_name__` — узнать имя дескриптора.
- Декораторы класса — обернуть класс.

Используйте метакласс только если предыдущие не подходят.

## 5. `__slots__`

Ограничивает набор атрибутов и экономит память (вместо `__dict__` — слоты).

```python
class Point:
    __slots__ = ("x", "y")
    def __init__(self, x, y):
        self.x, self.y = x, y

p = Point(1, 2)
# p.z = 3   # AttributeError — нельзя добавлять новые атрибуты
```

Минусы: нет `__dict__`, сложнее с наследованием/множественным наследованием.

### Когда выгодно

| Сценарий | `__slots__` |
|---|---|
| Миллионы мелких объектов | да |
| Обычные бизнес-классы | обычно нет |
| Нужны динамические атрибуты | нет |
| Нужен `cached_property` | нет (требует `__dict__`) |

## 6. SOLID

| Принцип | Суть |
|---|---|
| **S**RP — единственная ответственность | У класса одна причина для изменения |
| **O**CP — открыт/закрыт | Расширяй через наследование, не меняя существующий код |
| **L**SP — подстановка Лисков | Наследник заменяет родителя без поломок |
| **I**SP — разделение интерфейсов | Не заставляй зависеть от неиспользуемых методов |
| **D**IP — инверсия зависимостей | Зависи от абстракций, не от конкретных классов |

**Пример DIP (инъекция зависимости):**
```python
class Notifier(ABC):
    @abstractmethod
    def send(self, msg): ...

class EmailNotifier(Notifier):
    def send(self, msg): print(f"Email: {msg}")

class UserService:
    def __init__(self, notifier: Notifier):   # зависим от абстракции
        self.notifier = notifier
```

### Разбор каждого принципа

**SRP (Single Responsibility).** Класс должен меняться по одной причине.

```python
# Плохо: и данные, и запись в файл
class Report:
    def build(self): ...
    def save(self): ...

# Хорошо: разделили
class Report:
    def build(self): ...

class ReportSaver:
    def save(self, report): ...
```

**OCP (Open/Closed).** Добавляй новое поведение, не правя старый код.

```python
# Плохо: каждый новый тип — правка функции
def area(shape):
    if shape.kind == "circle": ...
    elif shape.kind == "square": ...

# Хорошо: полиморфизм
class Shape(ABC):
    @abstractmethod
    def area(self): ...
```

**LSP (Liskov).** Наследник не должен ломать ожидания родителя. Классический антипример — «квадрат наследует прямоугольник»: если у квадрата ширина и высота связаны, метод, меняющий только ширину, ломает инвариант.

```python
# Плохо: Square ломает контракт Rectangle
class Rectangle:
    def set_width(self, w): self.w = w
    def area(self): return self.w * self.h

class Square(Rectangle):   # set_width меняет и h — сюрприз
    ...
```

**ISP (Interface Segregation).** Лучше много маленьких интерфейсов.

```python
# Плохо: один «толстый» интерфейс
class Machine(ABC):
    @abstractmethod
    def print(self): ...
    @abstractmethod
    def scan(self): ...

# Хорошо: разделили
class Printer(ABC):
    @abstractmethod
    def print(self): ...
class Scanner(ABC):
    @abstractmethod
    def scan(self): ...
```

**DIP (Dependency Inversion).** Домен не зависит от деталей; детали зависят от абстракций.

```python
class UserService:
    def __init__(self, notifier: Notifier):
        self.notifier = notifier
```

## 7. Паттерны проектирования (минимум для собеса)

**Singleton** — один экземпляр на всё приложение.
```python
class Singleton:
    _instance = None
    def __new__(cls):
        if cls._instance is None:
            cls._instance = super().__new__(cls)
        return cls._instance
```

**Factory** — создание объектов без указания конкретного класса.
```python
class Dog: ...
class Cat: ...

def create_animal(kind):
    return {"dog": Dog, "cat": Cat}[kind]()
```

**Abstract Factory** — фабрика, создающая семейства связанных объектов.
```python
class GUIFactory(ABC):
    @abstractmethod
    def button(self): ...
    @abstractmethod
    def checkbox(self): ...

class WinFactory(GUIFactory):
    def button(self): return WinButton()
    def checkbox(self): return WinCheckbox()
```

**Observer**, **Strategy**, **Decorator** — тоже частые вопросы. Начни с Singleton + Factory + Strategy.

### Разбор Strategy

Позволяет менять алгоритм во время выполнения.

```python
class Sorter:
    def __init__(self, strategy):
        self.strategy = strategy
    def sort(self, data):
        return self.strategy(data)

bubble = lambda d: sorted(d)          # упрощённо
quick = lambda d: sorted(d, reverse=True)

print(Sorter(bubble).sort([3, 1, 2])) # [1, 2, 3]
print(Sorter(quick).sort([3, 1, 2]))  # [3, 2, 1]
```

### Разбор Observer

Объект уведомляет подписчиков об изменениях.

```python
class Subject:
    def __init__(self):
        self._subs = []
    def subscribe(self, cb):
        self._subs.append(cb)
    def notify(self, event):
        for cb in self._subs:
            cb(event)

s = Subject()
s.subscribe(lambda e: print(f"1 получил {e}"))
s.subscribe(lambda e: print(f"2 получил {e}"))
s.notify("новость")
```

### Сводная таблица паттернов

| Паттерн | Категория | Суть |
|---|---|---|
| Singleton | порождающий | один экземпляр |
| Factory | порождающий | создание без указания класса |
| Abstract Factory | порождающий | семейства объектов |
| Builder | порождающий | пошаговая сборка |
| Adapter | структурный | совмещение интерфейсов |
| Decorator | структурный | добавление поведения |
| Facade | структурный | простой фасад над системой |
| Strategy | поведенческий | сменные алгоритмы |
| Observer | поведенческий | подписки и уведомления |
| Command | поведенческий | действие как объект |
| Template Method | поведенческий | каркас с шагами |

**Антипаттерны:** God Object, Spaghetti Code, Singleton-везде, преждевременная оптимизация.

## 8. Мини-итог и связки

- MRO вычисляется C3; `D(B, C)` даёт порядок `D, B, C, A, object`.
- `super()` — следующий в MRO, основа кооперативного наследования.
- ABC — явный интерфейс, Protocol — структурный.
- Метаклассы мощны, но почти всегда заменяются `__init_subclass__`.
- SOLID снижает связанность; начните с SRP и DIP.
- Паттерны — словарь решений; не прикручивайте их без нужды.

Связки: MRO опирается на наследование (День 6); DI и композиция — на инкапсуляцию. Углублённые детали — в `Углублённая теория.md`.

## 1. Git: базовая модель

### Зачем нужен Git

**Git** — распределённая система контроля версий. Она хранит историю изменений,
позволяет работать параллельно в ветках, откатываться к любому состоянию и
объединять работу нескольких людей.

Аналогия: Git — это «машина времени» для файлов плюс «параллельные вселенные»
(ветки).

### Три области

```
Working directory  --git add-->  Staging area  --git commit-->  Repository
(рабочие файлы)                  (индекс)                        (история)
```

- **Working directory** — файлы, которые вы редактируете.
- **Staging area (index)** — то, что попадёт в следующий коммит.
- **Repository** — сохранённая история коммитов.
- **Ветка** — указатель на коммит.
- **Remote** — удалённый репозиторий (origin).

### Основные команды

```bash
git init                          # создать репозиторий
git add .                         # добавить всё в staging
git commit -m "init"              # зафиксировать снимок
git branch feature/login          # создать ветку
git switch -c feature/login       # создать и сразу переключиться (совр. синтаксис)
git switch main                   # переключиться на main
git merge feature/login           # влить ветку в текущую
git push -u origin feature/login  # отправить ветку на сервер
git pull --rebase                 # забрать изменения и переложить свои сверху
git log --oneline --graph         # компактная история
git status                        # что изменено / что в staging
```

### Отмена изменений

| Команда | Что делает | Опасность |
|---|---|---|
| `git restore <file>` | откатить файл в рабочей директории | потеря несохранённых правок |
| `git restore --staged <file>` | убрать из staging (файл не трогается) | безопасно |
| `git reset --soft HEAD~1` | отменить коммит, оставив изменения в staging | безопасно |
| `git reset --mixed HEAD~1` | отменить коммит, изменения в рабочей директории | безопасно |
| `git reset --hard HEAD~1` | отменить коммит и **удалить** изменения | потеря данных! |
| `git revert <hash>` | создать новый коммит, отменяющий старый | безопасно для публичных веток |
| `git stash` | спрятать незакоммиченные изменения | легко забыть про stash |

### merge vs rebase

```bash
# merge: сохраняет историю, создаёт merge-коммит
git switch main
git merge feature

# rebase: переносит ваши коммиты на верхушку main -> линейная история
git switch feature
git rebase main
```

- **merge** — «соединить две линии», история ветвистая, но правдивая.
- **rebase** — «переписать, будто я начал с последнего main», история линейная,
  но **хеши коммитов меняются**.

> Золотое правило: **не делайте rebase публичных веток**, которые уже у других.
> Переписанная история сломает их работу.

Аналогия: merge — сшить две ветки ткани узлом. Rebase — переклеить свою ветку
поверх чужой, как будто так и было.

## 2. Тестирование: pytest

### Зачем тесты

Тесты — это «страховка»: они ловят регрессии (сломанное старое поведение),
документируют ожидания и дают уверенность при рефакторинге.

### Базовый pytest

```python
# test_math.py
import pytest
from myapp import add, divide

def test_add():
    assert add(2, 3) == 5              # обычный assert

@pytest.mark.parametrize("a,b,expected", [(1, 1, 2), (2, 5, 7)])
def test_add_many(a, b, expected):      # один тест — много кейсов
    assert add(a, b) == expected

def test_divide_by_zero():
    with pytest.raises(ZeroDivisionError):   # проверяем исключение
        divide(1, 0)
```

```bash
pytest -q                 # тихий режим
pytest -v                 # подробно
pytest -k "add"           # только тесты с "add" в имени
pytest --cov=myapp        # покрытие
pytest -x                 # остановиться на первой ошибке
```

### Виды тестов

| Вид | Что проверяет | Скорость | Сколько |
|---|---|---|---|
| **unit** | одну функцию/класс изолированно | очень быстро | много |
| **integration** | взаимодействие с БД/сетью/файлами | медленнее | меньше |
| **e2e** | весь сценарий «как пользователь» | медленно | мало |

Это **пирамида тестов**: широкая база из unit, узкая вершина из e2e.

### Моки

**Мок** — подмена настоящей зависимости «заглушкой», чтобы тест был быстрым,
детерминированным и не зависел от сети/БД.

```python
from unittest.mock import patch

@patch("myapp.requests.get")           # подменяем requests.get в модуле myapp
def test_fetch(mock_get):
    mock_get.return_value.status_code = 200   # «ответ» заглушки
    assert fetch_data() == 200
```

### Типичные ошибки

```python
# Плохо: тест зависит от порядка и общего состояния
counter = 0
def test_inc():
    global counter
    counter += 1
    assert counter == 1     # упадёт при повторном запуске/в другом порядке

# Хорошо: каждый тест изолирован
def test_inc():
    counter = 0
    assert counter + 1 == 1
```

## 3. Отладка

### Инструменты по возрастанию мощности

| Инструмент | Плюсы | Минусы |
|---|---|---|
| `print` | просто | не для прода, много шума |
| `logging` | уровни, можно выключить | нужно настроить |
| `breakpoint()` / pdb | пошаговое выполнение | только локально |
| IDE-отладчик | наглядно: стек, переменные | тяжелее для прода |
| профилировщик | находит узкие места | отдельная тема |

```python
# Логирование вместо print
import logging
logging.basicConfig(level=logging.INFO)
logging.info("Старт обработки %s", user_id)      # ленивое форматирование
logging.error("Не удалось обработать заказ %s", order_id)
```

Почему `logging.info("...%s", x)`, а не f-строка? Строка форматируется **только
если уровень включён** — экономия ресурсов.

### pdb — встроенный отладчик

```python
def buggy(a, b):
    breakpoint()      # выполнение остановится здесь
    return a + b
```

Команды pdb:

- `n` (next) — следующая строка;
- `s` (step) — войти в функцию;
- `c` (continue) — продолжить;
- `p expr` / `pp expr` — напечатать выражение;
- `l` (list) — показать код вокруг;
- `w` (where) — стек вызовов;
- `q` (quit) — выйти.

Запуск: `python -m pdb script.py`.

> Типичная ошибка: оставить `breakpoint()` в коде и задеплоить. Проверяйте diff.

## 4. Чистая архитектура (кратко)

### Идея

**Чистая архитектура** (Clean Architecture) — бизнес-логика не зависит от
фреймворков, БД и UI. Зависимости направлены **внутрь**, к домену.

Аналогия: ядро — это «сердце» приложения (правила бизнеса). Внешние слои — это
«розетки» и «переходники». Можно заменить БД или фреймворк, не трогая сердце.

### Слои (снаружи внутрь)

1. **Frameworks/Drivers** — FastAPI, SQLAlchemy, БД.
2. **Interface Adapters** — контроллеры, репозитории, сериализаторы.
3. **Use Cases** — сценарии приложения (оформить заказ, отправить письмо).
4. **Entities/Domain** — бизнес-правила (чистые, без зависимостей).

### Правило зависимостей

Внутренние слои **не знают** о внешних. Связь — через интерфейсы (**порты**),
которые реализуют **адаптеры** (Dependency Inversion Principle из SOLID).

```python
# Порт (интерфейс) объявлен в домене
from typing import Protocol

class UserRepository(Protocol):
    def get(self, id: int) -> "User": ...

# Use case зависит от интерфейса, а не от БД
class GetUser:
    def __init__(self, repo: UserRepository):
        self.repo = repo
    def execute(self, id: int):
        return self.repo.get(id)
```

Плюсы: тестируемость (подставьте fake-репозиторий), заменяемость инфраструктуры.
Часто реализуется через **порты и адаптеры** (гексагональная архитектура).

## 5. Стили и парадигмы

- **Процедурное** — последовательность функций/шагов.
- **ООП** — объекты, инкапсуляция, наследование, полиморфизм.
- **Функциональное** — чистые функции, неизменяемость, функции высшего порядка.
- **Императивный** (как делать) vs **декларативный** (что получить).
- Python поддерживает **мультипарадигмальность**.

| Парадигма | Пример в Python |
|---|---|
| Процедурная | циклы, функции |
| ООП | `class`, наследование |
| Функциональная | `map`, `filter`, comprehensions |
| Декларативная | SQL, list comprehensions |

- **PEP 8** — стандарт оформления; **black** (формат), **ruff** (линт+формат),
  **isort** (импорты), **mypy** (типы).

## 7. Поведенческие вопросы (soft skills)

- Расскажи о себе (2 минуты, по делу).
- Почему выбрал Python / backend?
- Опиши свой pet-проект: что, зачем, какие технологии, что было сложно.
- Как ищешь ошибку в незнакомом коде?
- Работа в команде, конфликты, обратная связь.
- Что учишь сейчас, куда хочешь расти.

**Совет:** подготовь **один pet-проект** (например, FastAPI + PostgreSQL + Docker
+ тесты) и умей подробно его рассказать — это сильно повышает шансы на стажировке.

Структура рассказа о проекте:

1. **Проблема** — какую задачу решает.
2. **Стек** — почему именно эти технологии.
3. **Архитектура** — слои, БД, схема.
4. **Сложность** — что было трудно и как решил.
5. **Что улучшил бы** — показывает рост и рефлексию.

## 1. Git: базовая модель

- **Working directory** → **staging area** (`git add`) → **repository** (`git commit`).
- **Ветка** — указатель на коммит.
- **Remote** — удалённый репозиторий (origin).

```bash
git init
git add .
git commit -m "init"
git branch feature/login
git switch -c feature/login
git push -u origin feature/login
git pull --rebase
```

**Отмена изменений:**
- `git restore <file>` — откатить файл;
- `git restore --staged <file>` — убрать из staging;
- `git reset --soft/mixed/hard HEAD~1` — отменить коммит (разная степень);
- `git revert <hash>` — безопасная отмена (создаёт новый коммит);
- `git stash` — спрятать изменения.

**merge vs rebase:** merge сохраняет историю и создаёт merge-коммит; rebase переписывает историю, делая её линейной (нельзя для публичных веток).

> Подробнее: `[[git команды]]`.

## 2. Тестирование: pytest

```python
# test_math.py
import pytest
from myapp import add, divide

def test_add():
    assert add(2, 3) == 5

@pytest.mark.parametrize("a,b,expected", [(1, 1, 2), (2, 5, 7)])
def test_add_many(a, b, expected):
    assert add(a, b) == expected

def test_divide_by_zero():
    with pytest.raises(ZeroDivisionError):
        divide(1, 0)
```

```bash
pytest -q
pytest --cov=myapp
```

**Виды тестов:** unit (модульные), integration (интеграционные), e2e.
**Моки** (`unittest.mock` / `pytest-mock`) — подмена внешних зависимостей (БД, сеть).

```python
from unittest.mock import patch

@patch("myapp.requests.get")
def test_fetch(mock_get):
    mock_get.return_value.status_code = 200
    assert fetch_data() == 200
```

## 3. Отладка

- `print`/`logging` — простой способ, но не для продакшена.
- `breakpoint()` (Python 3.7+) — встроенный отладчик pdb.
- `python -m pdb script.py`, `pdb` команды: `n`, `s`, `c`, `p`, `q`.
- **Логирование** вместо print: уровни DEBUG/INFO/WARNING/ERROR/CRITICAL.
- IDE-отладчик: точки останова, watch, call stack.

```python
import logging
logging.basicConfig(level=logging.INFO)
logging.info("Старт обработки %s", user_id)
```

## 4. Чистая архитектура (кратко)

Идея: бизнес-логика не зависит от фреймворков, БД и UI. Зависимости направлены **внутрь**, к домену.

Слои (снаружи внутрь):
1. **Frameworks/Drivers** — FastAPI, SQLAlchemy, БД.
2. **Interface Adapters** — контроллеры, репозитории, сериализаторы.
3. **Use Cases** — сценарии приложения.
4. **Entities/Domain** — бизнес-правила.

Плюсы: тестируемость, заменяемость инфраструктуры. Часто реализуется через **порты и адаптеры** и **Dependency Inversion**.

> Подробнее: `[[Чистая архитектура]]`, `[[Архитектуры программного обеспечения]]`.

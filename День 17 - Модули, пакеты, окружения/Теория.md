# День 17 — Модули, пакеты, окружения, метаданные

> Цель: понимать импорты, `__name__ == "__main__"`, виртуальные окружения и интроспекцию.

---

## 0. Зачем вообще делить код на модули

Весь проект одной «тетрадью на 10 000 страниц» неудобен: трудно искать, страшно править.
**Модули** делят код на главы, **пакеты** — на разделы. Так код становится читаемым,
переиспользуемым, тестируемым и изолированным (имена не конфликтуют). Модуль — это
буквально файл `.py`; при импорте Python выполняет его код и складывает имена в
отдельное «пространство имён».

## 1. Модуль и пакет

- **Модуль** — файл `.py`.
- **Пакет** — каталог с `__init__.py`, объединяющий модули в иерархию.

```text
myapp/
├── __init__.py
├── models.py
└── services/
    ├── __init__.py
    └── user.py
```

`__init__.py` может быть пустым (помечает пакет) или содержать инициализацию/реэкспорт.

### 1.1 Разбираем структуру по шагам

1. `myapp/` — это **пакет верхнего уровня**. Файл `__init__.py` говорит Python:
   «этот каталог — пакет, а не просто папка с картинками».
2. `models.py` — **модуль** внутри пакета. Полное имя модуля — `myapp.models`.
3. `services/` — **подпакет** (пакет внутри пакета) со своим `__init__.py`.
4. `services/user.py` — модуль, полное имя — `myapp.services.user`.

> **Аналогия.** Пакет — это шкаф с ящиками, модуль — ящик, функции и классы — вещи в ящике.
> Чтобы достать вещь, нужно указать путь: шкаф → ящик → вещь.

### 1.2 Что писать в `__init__.py`

```python
# myapp/__init__.py

# 1. Пустой файл — просто помечает пакет.
# 2. Версия пакета — удобно читать из кода.
__version__ = "0.1.0"

# 3. Реэкспорт — делаем удобный «фасад» пакета.
from .models import User          # теперь доступно как myapp.User
from .services.user import get_user

__all__ = ["User", "get_user"]    # что попадёт в `from myapp import *`
```

Зачем реэкспорт? Чтобы пользователь писал коротко:

```python
# без реэкспорта — длинно и «протекает» внутренняя структура
from myapp.models import User
# с реэкспортом — коротко и стабильно (внутренности можно менять)
from myapp import User
```

### 1.3 Обычный пакет vs namespace-пакет

| Тип | Нужен `__init__.py` | Особенность |
|---|---|---|
| Обычный пакет | Да | Один каталог, явная инициализация |
| Namespace-пакет (PEP 420) | Нет | Может «склеиваться» из нескольких каталогов |
| Подпакет | Да (обычно) | Пакет внутри пакета |

## 2. Импорты

```python
import math                       # импорт модуля
from math import sqrt             # импорт имени
from math import sqrt as s        # с псевдонимом
from myapp.services.user import get_user
```

### 2.1 Четыре формы импорта и когда какую брать

```python
# Форма 1: импорт всего модуля. Понятно, откуда имя: math.sqrt.
import math
print(math.sqrt(16))              # 4.0

# Форма 2: импорт конкретных имён. Короче, но теряется контекст.
from math import sqrt, pi
print(sqrt(16), pi)               # 4.0 3.141592653589793

# Форма 3: псевдоним. Спасает от конфликтов и длинных имён.
import numpy as np
import pandas as pd

# Форма 4: импорт подпакета/модуля из пакета.
from myapp.services.user import get_user
```

> **Правило стиля (PEP 8):** избегай `from module import *` — непонятно, какие имена
> появились, и легко случайно перезаписать свои. Исключение — когда модуль явно задал
> `__all__`.

### 2.2 Абсолютный и относительный импорт

- **Абсолютный импорт** — от корня проекта (предпочтительно).
- **Относительный** — внутри пакета: `from . import user`, `from .. import models`.
  - `.` — текущий пакет, `..` — родительский.
  - Не работает при запуске файла напрямую; нужно `python -m myapp.services.user`.

```python
# myapp/services/user.py

# Относительные импорты — только внутри пакета:
from . import helpers          # myapp.services.helpers
from ..models import User      # myapp.models
from .. import __version__     # myapp/__init__.py

# Абсолютный эквивалент (предпочтительнее в больших проектах):
from myapp.services import helpers
from myapp.models import User
```

Почему относительные «ломаются» при прямом запуске? Потому что Python запускает
файл как `__main__`, не зная, частью какого пакета он является, — и не может вычислить
`.` и `..`.

```bash
python myapp/services/user.py          # ошибка: attempted relative import
python -m myapp.services.user          # правильно: пакет известен
```

### 2.3 Сравнение

| Критерий | Абсолютный | Относительный |
|---|---|---|
| Читаемость | Виден весь путь | Коротко внутри пакета |
| Переносимость пакета | Нужно менять при переименовании корня | Не зависит от имени корня |
| Работа при прямом запуске | Да | Нет |
| Рекомендация | По умолчанию | Для глубоко вложенных внутренних модулей |

## 3. Поиск модулей: `sys.path` и `sys.modules`

Порядок поиска:
1. Кэш уже импортированных модулей — `sys.modules`.
2. Встроенные модули (`sys`, `os`).
3. Каталоги из `sys.path`: каталог скрипта → `PYTHONPATH` → site-packages.

```python
import sys
print(sys.path)
sys.path.append("/my/path")       # временное добавление
```

Повторный `import` берёт модуль из `sys.modules`, не перезагружая. Принудительно — `importlib.reload(mod)`.

### 3.1 Пошаговый разбор поиска

Когда выполняется `import myapp`, Python делает примерно следующее:

1. **Проверяет кэш** `sys.modules`. Если `myapp` уже импортирован — берёт готовый объект
   и **не выполняет код повторно**.
2. **Идёт по `sys.meta_path`** — списку «искателей» (finders). Первый стандартный искатель
   знает про встроенные модули.
3. **Второй искатель** (`PathFinder`) перебирает каталоги из `sys.path` слева направо
   и ищет `myapp.py` или `myapp/__init__.py`.
4. **Создаёт spec** (описание модуля) и вызывает **loader**, который исполняет файл.
5. **Кладёт результат** в `sys.modules`.

```python
import sys
print(sys.modules["sys"] is sys)   # True — модуль уже в кэше
```

### 3.2 Как «подсунуть» свой путь

```python
import sys
sys.path.insert(0, "/opt/my_libs")   # поставить в начало поиска
import my_lib                        # теперь найдётся
```

Порядок `sys.path` важен: если в двух местах есть модуль с одним именем, победит тот,
что левее. Отсюда классическая ошибка — свой файл `json.py` в папке проекта «затеняет»
стандартный `json` и ломает импорты (`import json` подтянет ВАШ файл).

### 3.3 Циклический импорт

**Циклический импорт** (`A` импортирует `B`, `B` — `A`) вызывает ошибки. Решения: вынести общий код в третий модуль или делать ленивый импорт внутри функции.

```python
# a.py
from b import func_b       # b ещё не догрузил func_b -> ImportError
def func_a(): ...

# b.py
from a import func_a
def func_b(): ...
```

Типичные решения:

```python
# Решение 1: ленивый импорт внутри функции
# b.py
def func_b():
    from a import func_a    # импорт в момент вызова, а не при загрузке
    return func_a()
```

```python
# Решение 2: импорт только для аннотаций типов
from typing import TYPE_CHECKING
if TYPE_CHECKING:           # True только для линтеров/статических проверок
    from a import A
```

## 4. `if __name__ == "__main__"`

При прямом запуске файла `__name__ == "__main__"`; при импорте — имя модуля.

```python
def main():
    print("запуск")

if __name__ == "__main__":     # только при прямом запуске
    main()
```

Это позволяет использовать файл и как скрипт, и как библиотеку без побочных эффектов при импорте.

### 4.1 Разбор на примере

```python
# greet.py
print("модуль загружается")

def greet(name):
    return f"Привет, {name}!"

if __name__ == "__main__":
    print(greet("мир"))       # выполнится ТОЛЬКО при `python greet.py`
```

```text
$ python greet.py
модуль загружается
Привет, мир!

>>> import greet
модуль загружается       # код на уровне модуля выполнился
>>> greet.greet("Аня")   # а блок под if — нет
'Привет, Аня!'
```

> **Аналогия.** Это как выключатель: одна и та же «машина» может работать как
> самостоятельное устройство (прямой запуск) или как деталь в большом механизме
> (импорт). Блок `if` говорит: «выполни вот эту часть только если я — главный».

### 4.2 Типичная ошибка

```python
# ПЛОХО: тяжёлый/побочный код на верхнем уровне
# library.py
print("подключаюсь к БД...")     # сработает при КАЖДОМ импорте!
connect_to_db()

# ХОРОШО: побочные эффекты — под if или в функциях
# library.py
def main():
    connect_to_db()

if __name__ == "__main__":
    main()
```

## 5. Метаданные и интроспекция

**Интроспекция** — способность программы «заглянуть в себя»: узнать имена, типы,
сигнатуры, атрибуты объектов во время выполнения.

| Атрибут | Что хранит |
|---|---|
| `__name__` | имя модуля/класса/функции (`"__main__"` для точки входа) |
| `__file__` | путь к файлу модуля |
| `__doc__` | docstring |
| `__dict__` | пространство имён (атрибуты) |
| `__annotations__` | аннотации типов |
| `__module__` | имя модуля, где определён объект |
| `__qualname__` | полное имя (для вложенных) |
| `__bases__` / `__mro__` | родители / порядок разрешения методов |
| `__closure__` | захваченные переменные замыкания |
| `__code__` | байт-код функции |

```python
import inspect
inspect.signature(some_func)     # сигнатура функции
inspect.getmembers(obj)          # все атрибуты
dir(module)                      # список имён
```

**Зачем:** фреймворки (Pydantic читает `__annotations__`, декораторы используют `functools.wraps`), сериализация (`__dict__` → JSON), отладка.

### 5.1 Практический пример интроспекции

```python
def add(a: int, b: int = 0) -> int:
    """Складывает два числа."""
    return a + b

print(add.__name__)        # add
print(add.__doc__)         # Складывает два числа.
print(add.__annotations__) # {'a': <class 'int'>, 'b': <class 'int'>, 'return': <class 'int'>}

import inspect
print(inspect.signature(add))   # (a: int, b: int = 0) -> int
```

### 5.2 `vars`, `dir`, `getattr`

```python
class User:
    def __init__(self, name):
        self.name = name

u = User("Аня")

print(vars(u))                 # {'name': 'Аня'} — это __dict__
print("name" in dir(u))        # True — dir перечисляет имена

# getattr — безопасное получение атрибута с значением по умолчанию
print(getattr(u, "age", "нет такого"))   # 'нет такого'
```

## 6. Виртуальные окружения и зависимости

- **venv** — изолированное окружение с собственным интерпретатором и пакетами.

```bash
python -m venv .venv
# Windows:
.venv\Scripts\activate
# Linux/macOS:
source .venv/bin/activate

pip install fastapi
pip freeze > requirements.txt
pip install -r requirements.txt
```

- **pip** — менеджер пакетов (PyPI).
- **requirements.txt** — список зависимостей.
- **pyproject.toml** — современный стандарт метаданных проекта и зависимостей (PEP 517/518).

### 6.1 Зачем нужно виртуальное окружение

Представь два проекта: один требует `Django 3`, другой — `Django 5`. В глобальном
Python они конфликтуют. **venv** создаёт «отдельную песочницу» для каждого проекта:
свои версии пакетов, не мешающие другим.

> **Аналогия.** Глобальный Python — общий кухонный шкаф в общежитии. venv — личный
> ящик: что положил, то твоё, соседи не тронут.

### 6.2 Пошаговый рабочий процесс

```bash
python -m venv .venv              # 1. создать окружение
.venv\Scripts\activate            # 2. активировать (приглашение: (.venv) C:\...)
python -m pip install --upgrade pip
pip install fastapi uvicorn       # 3. поставить зависимости
pip freeze > requirements.txt     # 4. зафиксировать версии
pip install -r requirements.txt   # 5. воспроизвести у коллеги
deactivate                        # 6. выйти
```

### 6.3 requirements.txt vs pyproject.toml

| | `requirements.txt` | `pyproject.toml` |
|---|---|---|
| Назначение | Список пакетов | Метаданные + зависимости + сборка |
| Версии | Часто жёстко (`==`) | Диапазоны (`>=`, `~=`) |
| Стандарт | Де-факто | PEP 518/621 |
| Транзитивные зависимости | Фиксируются `pip freeze` | Обычно lock-файл |

```toml
# pyproject.toml
[project]
name = "myapp"
version = "0.1.0"
requires-python = ">=3.11"
dependencies = ["fastapi>=0.110", "sqlalchemy>=2.0"]
```

### 6.4 Типичные ошибки

```bash
# ПЛОХО: ставить пакеты глобально, без активации venv
pip install fastapi          # попадёт в системный Python

# ХОРОШО: сначала активировать
.venv\Scripts\activate
pip install fastapi
```

> **В git:** не коммить `.venv/` и `__pycache__/` — добавь их в `.gitignore`.

## 7. Мини-итог

- Модуль — файл `.py`, пакет — каталог с `__init__.py`.
- Импорт ищет модуль в `sys.modules` → встроенные → `sys.path`.
- Относительные импорты работают только внутри пакета (запуск через `python -m`).
- `if __name__ == "__main__"` отделяет скрипт от библиотеки.
- Интроспекция (`__annotations__`, `inspect`) — основа фреймворков.
- venv изолирует зависимости; `pyproject.toml` — современный стандарт.

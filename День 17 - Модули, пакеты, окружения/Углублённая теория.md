## 1. Как реально работает `import`

1. Проверка `sys.modules` (кэш).
2. Поиск через **finders** в `sys.meta_path`.
3. Создание **spec** (module spec) и загрузка **loader**.
4. Исполнение модуля в его namespace.
5. Сохранение в `sys.modules`.

```python
import importlib, sys
mod = importlib.import_module("math")
sys.modules["math"] is mod    # True
```

- `importlib.util.spec_from_file_location` — импорт из произвольного файла.
- **Import hooks** (`MetaPathFinder`) позволяют кастомные источники (zip, БД, сеть).

### 1.1 Разбор пяти шагов подробнее

1. **Кэш.** `import x` сначала смотрит в словарь `sys.modules`. Если модуль там есть,
   оператор просто связывает имя и не перезагружает файл. Именно поэтому изменение
   файла во время работы не подхватывается без `reload`.
2. **Finders.** Python идёт по `sys.meta_path` — цепочке искателей. Стандартно это
   `BuiltinImporter` (встроенные), `FrozenImporter` (замороженные) и `PathFinder`
   (поиск по `sys.path`).
3. **Spec.** Finder возвращает `ModuleSpec`: имя модуля, путь к файлу, loader.
4. **Execution.** Loader читает файл и выполняет его как код в новом словаре-модуле.
   Всё, что определено на верхнем уровне, становится атрибутами модуля.
5. **Registration.** Готовый модуль кладётся в `sys.modules`.

### 1.2 Ручной импорт из файла

```python
import importlib.util, sys

spec = importlib.util.spec_from_file_location("mymod", "/tmp/plugin.py")
mod = importlib.util.module_from_spec(spec)
sys.modules["mymod"] = mod          # регистрируем ДО exec (важно для dataclass и др.)
spec.loader.exec_module(mod)
print(mod.some_function())
```

### 1.3 Что такое import hooks

`MetaPathFinder` — объект с методом `find_spec(name, path, target)`. Добавив свой
finder в `sys.meta_path`, можно импортировать модули из нестандартных мест: из zip-архива,
из базы данных, из сети. Так работают плагины и «виртуальные» модули.

```python
import sys
from importlib.abc import MetaPathFinder

class MyFinder(MetaPathFinder):
    def find_spec(self, fullname, path, target=None):
        if fullname == "virtual_module":
            ...  # вернуть свой ModuleSpec
        return None   # пусть ищут другие

sys.meta_path.insert(0, MyFinder())
```

## 2. Пакеты и `__init__.py`

- Обычный пакет — каталог с `__init__.py`.
- **Namespace packages** (PEP 420) — без `__init__.py`, могут объединять части из разных мест.
- `__all__` в модуле/пакете управляет `from pkg import *`.
- Реэкспорт в `__init__.py` для удобного API:

```python
# mypkg/__init__.py
from .models import User
from .services import create_user
__all__ = ["User", "create_user"]
```

### 2.1 Зачем namespace-пакеты

Иногда один логический пакет физически разложен по нескольким каталогам (например,
плагины, установленные в разные места). Namespace-пакет позволяет `import mypkg` собрать
все части без единого `__init__.py`. Классический пример — `google.*`.

```text
site-packages/google/cloud/storage/       # часть 1
site-packages/google/cloud/bigquery/      # часть 2
# единый namespace "google.cloud"
```

### 2.2 `__all__`: что и зачем

```python
# utils.py
__all__ = ["public_func"]      # только это попадёт в `from utils import *`

def public_func(): ...
def _internal(): ...           # по соглашению «приватное»
def also_public(): ...         # не попадёт в *
```

| Приём | Эффект |
|---|---|
| `__all__ = [...]` | Ограничивает `from mod import *` |
| Нет `__all__` | `import *` берёт все имена без `_` |
| Реэкспорт в `__init__` | Короткий публичный API |

### 2.3 `__init__.py` может делать лишнее

```python
# ПЛОХО: тяжёлая инициализация при импорте
# mypkg/__init__.py
connect_to_database()          # замедлит любой `import mypkg`

# ХОРОШО: лёгкий __init__, тяжёлое — по требованию
# mypkg/__init__.py
from .models import User
# подключение к БД — внутри функций
```

## 3. Циклические импорты

- A импортирует B, B импортирует A → частично инициализированные модули.
- Решения: вынести общий код в третий модуль; **ленивый импорт** внутри функции; импорт по `TYPE_CHECKING` для типов.

```python
def handler():
    from .heavy import do_work   # ленивый импорт
    return do_work()
```

### 3.1 Почему возникает ошибка

```python
# a.py
import b
def a_func():
    return b.b_func()

# b.py
import a
def b_func():
    return a.a_func()      # при импорте b, модуль a ещё не догружен
```

Порядок: Python начинает грузить `a` → доходит до `import b` → грузит `b` → `b` доходит
до `import a`, но `a` уже в `sys.modules` (частично!), и в нём ещё нет `a_func` →
`AttributeError`/`ImportError`.

### 3.2 Три способа починить

```python
# Способ 1: вынести общее в третий модуль common.py
# a.py: from .common import shared
# b.py: from .common import shared
```

```python
# Способ 2: ленивый импорт (внутри функции)
# b.py
def b_func():
    from .a import a_func      # импорт в момент вызова
    return a_func()
```

```python
# Способ 3: импорт только для типов
from typing import TYPE_CHECKING
if TYPE_CHECKING:              # не выполняется в рантайме
    from .a import A

def handle(x: "A") -> None:    # аннотация в кавычках — строка
    ...
```

### 3.3 Сравнение решений

| Решение | Плюсы | Минусы |
|---|---|---|
| Общий модуль | Чистая архитектура | Требует рефакторинга |
| Ленивый импорт | Быстро внедрить | Скрывает связи, чуть медленнее вызов |
| `TYPE_CHECKING` | Решает проблему типов | Только для аннотаций |

## 4. Метаданные пакета

```python
from importlib.metadata import version, entry_points
version("fastapi")
entry_points(group="console_scripts")
```

- **Entry points** — точки входа CLI/плагинов (`[project.scripts]`).
- `importlib.resources` — доступ к файлам внутри пакета (шаблоны, данные).

### 4.1 Entry points на практике

Когда вы ставите пакет, в системе появляется команда (`fastapi`, `uvicorn`, `black`).
Это и есть console script entry point.

```toml
# pyproject.toml
[project.scripts]
myapp = "myapp.cli:main"
```

После установки команда `myapp` вызывает `myapp.cli.main`.

```python
# Программно посмотреть все команды:
from importlib.metadata import entry_points
for ep in entry_points(group="console_scripts"):
    print(ep.name, "->", ep.value)
```

### 4.2 Доступ к ресурсам пакета

```python
from importlib.resources import files
text = (files("myapp.templates") / "email.html").read_text(encoding="utf-8")
```

Это правильный способ читать встроенные файлы: работает и внутри zip/wheel, где
обычный `open(путь)` не сработает.

## 5. Упаковка: wheel, sdist, pyproject

- **sdist** (`.tar.gz`) — исходники; **wheel** (`.whl`) — собранный дистрибутив.
- `pyproject.toml` (PEP 518/621) — стандарт метаданных и сборки.

```toml
[build-system]
requires = ["setuptools>=68"]
build-backend = "setuptools.build_meta"

[project]
name = "myapp"
version = "0.1.0"
dependencies = ["fastapi", "sqlalchemy>=2"]
```

```bash
python -m build        # создаёт sdist + wheel
```

### 5.1 sdist vs wheel

| | sdist | wheel |
|---|---|---|
| Формат | `.tar.gz` (исходники) | `.whl` (zip-архив) |
| Сборка при установке | Нужна | Не нужна (готово) |
| Скорость установки | Медленнее | Быстрее |
| Нужны компиляторы | Иногда да | Нет |

```bash
# Собрать оба артефакта
python -m build
# dist/myapp-0.1.0.tar.gz
# dist/myapp-0.1.0-py3-none-any.whl

# Установить локально
pip install dist/myapp-0.1.0-py3-none-any.whl
```

### 5.2 Версии и спецификаторы

| Спецификатор | Значение |
|---|---|
| `==1.2.3` | Ровно эта версия |
| `>=1.2,<2.0` | Диапазон |
| `~=1.2.3` | `>=1.2.3, <1.3.0` (совместимые) |
| `!=1.5` | Кроме этой |
| `*` | Любая |

> **Семантическое версионирование (SemVer):** `MAJOR.MINOR.PATCH`. Ломающие изменения —
> в MAJOR, новые возможности — в MINOR, багфиксы — в PATCH.

## 6. Менеджеры зависимостей и lock-файлы

| Инструмент | Особенность |
|---|---|
| `pip` + `requirements.txt` | базовый |
| `poetry` | зависимости + сборка + lock |
| `pipenv` | Pipfile + lock |
| `uv` | очень быстрый (Rust), замена pip/venv |
| `conda` | научный стек, свои пакеты |

- **Lock-файл** фиксирует точные версии всех транзитивных зависимостей → воспроизводимость.
- **Разрешение зависимостей** — поиск совместимых версий; конфликты версий — частая боль.

### 6.1 Что такое транзитивные зависимости

Ваш проект зависит от `fastapi`, а `fastapi` — от `starlette`, `pydantic`. Это
**транзитивные** зависимости. Их версии тоже важны: обновили `pydantic` несовместимо —
сломали `fastapi`.

```text
myapp
└── fastapi 0.110
    ├── starlette >=0.36
    └── pydantic >=1.7.4
        └── typing-extensions
```

### 6.2 Зачем lock-файл

`requirements.txt` может содержать диапазоны, тогда у разных людей — разные версии.
Lock-файл фиксирует **точное дерево**: «у всех ровно это».

```text
# requirements.txt (намерения)
fastapi>=0.110

# poetry.lock / uv.lock (факт, все транзитивные)
fastapi 0.110.1 ...
starlette 0.36.3 ...
pydantic 2.6.4 ...
```

### 6.3 Конфликты версий

```text
Пакет A требует urllib3<2
Пакет B требует urllib3>=2
→ pip не может найти совместимую версию
```

Решения: обновить пакеты, использовать виртуальные окружения для разных задач или
изолировать сервисы.

## 7. Виртуальные окружения

- `venv` создаёт изолированный `site-packages` и копию/ссылку на интерпретатор.
- `sys.prefix` отличается в venv; активация меняет `PATH`.
- `site`-модуль добавляет `site-packages`; `.pth`-файлы расширяют пути.

```bash
python -m venv .venv
.venv\Scripts\activate      # Windows
python -m pip install -U pip
```

### 7.1 Что происходит внутри

```python
import sys
print(sys.prefix)      # в venv: ...\.venv  (вне: системный Python)
print(sys.base_prefix) # всегда системный Python
print(sys.path)        # в venv первым идёт .venv/Lib/site-packages
```

Активация venv всего лишь меняет `PATH` (чтобы первой была `.venv\Scripts`) и
переменную `VIRTUAL_ENV`. Сам `python` в venv знает свой `sys.prefix` через файл
`pyvenv.cfg`.

```text
.venv/
├── pyvenv.cfg           # home = путь к базовому Python
├── Scripts/             # Windows: python.exe, pip.exe
│   ├── python.exe
│   └── activate
└── Lib/site-packages/   # пакеты этого окружения
```

### 7.2 `.pth`-файлы

Файл с расширением `.pth` в `site-packages` — по строке на путь; `site` добавляет их
в `sys.path`. Так некоторые пакеты «прописывают» свои каталоги.

## 8. Интроспекция

```python
import inspect
inspect.signature(func)
inspect.getmembers(obj)
inspect.getsource(func)
vars(obj)          # __dict__
dir(obj)           # все имена
getattr(obj, "x", default)
```

`inspect` используется декораторами, фреймворками, автодокументацией.

### 8.1 Пример: декоратор, сохраняющий метаданные

```python
import functools

def logged(func):
    @functools.wraps(func)          # копирует __name__, __doc__, __annotations__
    def wrapper(*args, **kwargs):
        print(f"вызов {func.__name__}")
        return func(*args, **kwargs)
    return wrapper

@logged
def add(a, b):
    """Складывает числа."""
    return a + b

print(add.__name__)   # add (без wraps было бы 'wrapper')
print(add.__doc__)    # Складывает числа.
```

### 8.2 Пример: сигнатура и валидация (как делает FastAPI)

```python
import inspect

def build_validator(func):
    sig = inspect.signature(func)
    for name, param in sig.parameters.items():
        print(name, "->", param.annotation, "по умолчанию:", param.default)

def create_user(name: str, age: int = 18):
    ...

build_validator(create_user)
# name -> <class 'str'> по умолчанию: <class 'inspect._empty'>
# age  -> <class 'int'> по умолчанию: 18
```

### 8.3 Типичная ошибка

```python
# ПЛОХО: декоратор без wraps «теряет» имя функции
def deco(f):
    def wrapper(*a, **k): return f(*a, **k)
    return wrapper

# ХОРОШО: сохраняем метаданные
import functools
def deco(f):
    @functools.wraps(f)
    def wrapper(*a, **k): return f(*a, **k)
    return wrapper
```

## 9. Сложность и производительность

| Операция | Стоимость | Комментарий |
|---|---|---|
| Повторный `import` | O(1) | Берётся из `sys.modules` |
| Первый `import` | Чтение файла + exec | Кэшируется в `.pyc` |
| `sys.path` поиск | O(числа путей) | Лучше не раздувать |
| Импорт внутри функции | Небольшой оверхед | Зато решает циклы/ленивость |

**Байт-код кэшируется:** после первого импорта рядом появляется `__pycache__/mod.cpython-311.pyc`.
Повторный запуск не перекомпилирует файл, если он не изменился.

```text
myapp/
└── __pycache__/
    └── models.cpython-311.pyc     # кэш байт-кода
```

> В `.gitignore` обычно добавляют `__pycache__/` и `*.pyc`.

## 11. Мини-итог

- Импорт — это проход по `sys.meta_path`, создание spec и exec модуля.
- Пакеты бывают обычные и namespace; `__all__` управляет `import *`.
- Циклические импорты лечатся общим модулем, ленью или `TYPE_CHECKING`.
- Метаданные пакета и entry points — основа CLI и плагинов.
- sdist/wheel — форматы дистрибутивов, `pyproject.toml` — стандарт сборки.
- Lock-файлы и venv дают воспроизводимость.
- Интроспекция питает декораторы и фреймворки.

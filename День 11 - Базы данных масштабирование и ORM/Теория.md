## 0. Зачем масштабировать БД

Когда данных и запросов становится много, один сервер перестаёт справляться:
не хватает диска, памяти, ядер или пропускной способности сети. Есть два
направления:

- **Вертикальное масштабирование** (scale up) — более мощный сервер. Просто, но
  упирается в физический предел и дорого.
- **Горизонтальное масштабирование** (scale out) — много серверов. Сложнее, но
  почти без предела.

Три кита горизонтального масштабирования БД:

| Техника | Что делит | Границы |
|---|---|---|
| Партиционирование | одну таблицу | внутри одного сервера |
| Шардирование | данные | по нескольким серверам |
| Репликация | копии данных | мастер + реплики |

Аналогия: библиотека. Партиционирование — разложить книги по залам в одном
здании. Шардирование — открыть филиалы в разных районах. Репликация — держать
копии каталога в каждом филиале, чтобы читать локально.

## 1. Партиционирование

Разделение **одной таблицы** на физические части **внутри одного сервера**.

- **Горизонтальное** — строки по партициям (по дате, по хешу ключа).
- **Вертикальное** — колонки по партициям (редко).

**Типы:** Range, List, Hash.

**Плюсы:** pruning (отбрасывание ненужных партиций), быстрое удаление старых данных (`DROP PARTITION` вместо `DELETE`).
**Минусы:** сложности с глобальными уникальными индексами.

```sql
-- PostgreSQL: партиционирование по диапазону дат
CREATE TABLE logs (
    id         BIGSERIAL,
    created_at DATE NOT NULL,
    msg        TEXT
) PARTITION BY RANGE (created_at);

CREATE TABLE logs_2026_01 PARTITION OF logs
    FOR VALUES FROM ('2026-01-01') TO ('2026-02-01');
CREATE TABLE logs_2026_02 PARTITION OF logs
    FOR VALUES FROM ('2026-02-01') TO ('2026-03-01');
```

Теперь запрос за январь читает **только** `logs_2026_01` (partition pruning):

```sql
EXPLAIN SELECT * FROM logs WHERE created_at BETWEEN '2026-01-01' AND '2026-01-31';
-- Scan on logs_2026_01  ← другие партиции не тронуты
```

**Удаление старых данных:**

```sql
-- ❌ Медленно: перебирает и удаляет строки, раздувает WAL
DELETE FROM logs WHERE created_at < '2025-01-01';

-- ✅ Мгновенно: отцепляет и удаляет файл партиции
DROP TABLE logs_2025_01;
```

| Тип | Критерий | Пример |
|---|---|---|
| Range | диапазон | по месяцам |
| List | перечень | по странам/регионам |
| Hash | хеш ключа | равномерно по `user_id` |

## 2. Шардирование

Распределение данных **по нескольким независимым серверам (шардам)**.

- Отличие от партиционирования: там — внутри одной БД, здесь — по разным узлам.
- Методы: по диапазону, по хешу (consistent hashing), по географии.

**Проблемы:** распределённые транзакции (2PC), JOIN между шардами, перебалансировка, глобальные уникальные ключи (Snowflake ID).

```text
Пользователи по шардам (hash по user_id):
  shard1: user_id % 3 == 0
  shard2: user_id % 3 == 1
  shard3: user_id % 3 == 2
```

| Аспект | Партиционирование | Шардирование |
|---|---|---|
| Узлы | один сервер | несколько серверов |
| JOIN | обычный | между шардами дорогой |
| Транзакции | обычные | распределённые (2PC) |
| Масштаб | до предела сервера | почти без предела |
| Сложность | средняя | высокая |

**Snowflake ID** — 64-битный уникальный ID: `timestamp | machine_id | sequence`.
Позволяет генерировать ID на разных шардах без координации.

**2PC (two-phase commit)** — протокол распределённой транзакции: фаза
«подготовиться» и фаза «зафиксировать». Медленный и уязвим к сбоям координатора.

## 3. Репликация

Копирование данных с мастера на реплики.

**Цели:** отказоустойчивость, масштабирование чтения, бэкапы.

- **Master-Slave:** один мастер на запись, много реплик на чтение. Асинхронная / полусинхронная / синхронная.
- **Master-Master:** несколько мастеров на запись (сложнее конфликты).
- **Физическая** (WAL/binlog) vs **логическая** (изменения строк/команд).

```text
        ┌──────────┐
запись →│  Master  │
        └────┬─────┘
     ┌───────┼───────┐
     ▼       ▼       ▼
  Replica Replica Replica   ← чтение
```

| Тип репликации | Гарантия | Скорость | Риск потери |
|---|---|---|---|
| Синхронная | данные на реплике до COMMIT | медленно | нет |
| Асинхронная | COMMIT не ждёт реплику | быстро | есть |
| Полусинхронная | ждёт хотя бы одну реплику | компромисс | малый |

**Replication lag** — отставание реплики. Если сразу после записи прочитать с
реплики, можно не увидеть своих данных. Это называют **read-your-writes**
проблемой.

**Типичная ошибка:** писать на мастер, а читать из реплики в рамках одной
операции. Пользователь «не видит» свой только что сохранённый профиль.

## 4. CAP-теорема

В распределённой системе из трёх свойств можно гарантировать только два:
- **Consistency** — согласованность,
- **Availability** — доступность,
- **Partition tolerance** — устойчивость к разделению сети.

На практике сеть может рваться, поэтому выбирают между C и A. NoSQL часто выбирают eventual consistency.

**Разбор:**
- **CP** (жертвуем доступностью) — при разрыве сети отказываем в ответе, но не
  отдаём несогласованные данные. Пример: HBase, ZooKeeper.
- **AP** (жертвуем согласованностью) — отвечаем всегда, но данные могут быть
  устаревшими. Пример: Cassandra, DynamoDB.
- **CA** — только когда сеть идеальна (на практике не бывает для распределённых).

Аналогия: два кассира в магазине. CP — пока связь между кассами не
восстановится, второй кассир не обслуживает (боится продать уже проданное).
AP — обслуживает всех, рискуя продать один товар дважды.

## 5. ORM: зачем

**ORM (Object-Relational Mapping)** сопоставляет таблицы классам, строки — объектам. Позволяет работать с БД через Python-объекты вместо SQL.

- Плюсы: меньше SQL-кода, защита от инъекций, переносимость.
- Минусы: может генерировать неэффективные запросы, «магия».

**SQLAlchemy:** Core (низкоуровневый) и ORM (декларативные модели).

```python
from sqlalchemy.orm import DeclarativeBase, Mapped, mapped_column, relationship
from sqlalchemy import ForeignKey

class Base(DeclarativeBase): pass

class User(Base):
    __tablename__ = "users"
    id: Mapped[int] = mapped_column(primary_key=True)
    username: Mapped[str] = mapped_column(unique=True)
    posts: Mapped[list["Post"]] = relationship(back_populates="author")

class Post(Base):
    __tablename__ = "posts"
    id: Mapped[int] = mapped_column(primary_key=True)
    user_id: Mapped[int] = mapped_column(ForeignKey("users.id"))
    author: Mapped["User"] = relationship(back_populates="posts")
```

**Сессия:**
```python
with Session(engine) as session:
    session.add(User(username="anya"))
    session.commit()

    stmt = select(User).where(User.username == "anya")
    user = session.scalar(stmt)
```

**SQLAlchemy Core** — тот же движок, но без маппинга объектов:

```python
from sqlalchemy import text

with engine.connect() as conn:
    rows = conn.execute(
        text("SELECT id, username FROM users WHERE id = :id"), {"id": 1}
    )
    for row in rows:
        print(row.username)
```

| | Core | ORM |
|---|---|---|
| Работа | таблицы и SQL | объекты и модели |
| Контроль | полный | скрыт |
| Удобство | ниже | выше |
| Когда | массовые операции, сложный SQL | доменные модели |

**Защита от инъекций** — параметризация, а не склейка строк:

```python
# ❌ SQL-инъекция
conn.execute(text(f"SELECT * FROM users WHERE name = '{name}'"))

# ✅ Параметры
conn.execute(text("SELECT * FROM users WHERE name = :name"), {"name": name})
```

## 6. Проблема N+1

Классический баг ORM: при обращении к связанным объектам в цикле выполняется 1 + N запросов.

```python
users = session.scalars(select(User)).all()
for u in users:
    print(u.posts)      # +1 запрос на каждого пользователя → N+1
```

Итого `1` запрос за пользователей + `N` запросов за их посты = **N+1**.
На 1000 пользователей — 1001 запрос вместо 2.

**Решение — eager loading:**
```python
from sqlalchemy.orm import selectinload, joinedload
stmt = select(User).options(selectinload(User.posts))
```

- `joinedload` — JOIN одним запросом;
- `selectinload` — отдельный запрос с `IN`.

```python
# 2 запроса: пользователи + один SELECT ... WHERE user_id IN (...)
stmt = select(User).options(selectinload(User.posts))
users = session.scalars(stmt).all()
for u in users:
    print(u.posts)      # уже загружено, без новых запросов
```

| Стратегия | Запросов | Плюсы | Минусы |
|---|---|---|---|
| Lazy (по умолчанию) | N+1 | просто | медленно |
| `joinedload` | 1 | один запрос | дубли строк, раздувает результат |
| `selectinload` | 2 | без дублей | отдельный запрос |
| `subqueryload` | 2 | для сложных случаев | сложнее |

## 7. Миграции: Alembic

Alembic сравнивает модели с текущей схемой БД и генерирует скрипты миграций.

```bash
alembic revision --autogenerate -m "add users"
alembic upgrade head      # применить
alembic downgrade -1      # откатить
```

Миграция — версионируемое изменение схемы. Это как Git для структуры БД:
каждое изменение имеет номер и может быть применено/откачено.

| Команда | Что делает |
|---|---|
| `alembic revision --autogenerate` | создаёт файл миграции по разнице моделей |
| `alembic upgrade head` | применяет все миграции |
| `alembic downgrade -1` | откатывает одну |
| `alembic current` | текущая ревизия |
| `alembic history` | список ревизий |

## 8. Лучшие практики

- Всегда закрывай сессии (`with Session(...)`).
- Настраивай `sessionmaker` один раз.
- Используй eager loading, чтобы избежать N+1.
- Для массовых `UPDATE` — Core `update()`, а не загрузка объектов.
- Смешивай ORM и Core там, где удобно.

```python
from sqlalchemy import update

# ❌ Загрузить 10 000 объектов и обновить по одному
for u in session.scalars(select(User)).all():
    u.active = True

# ✅ Один UPDATE на стороне БД
session.execute(update(User).values(active=True))
session.commit()
```

## 10. Мини-итог и связки

- Партиционирование — внутри сервера, шардирование — между серверами.
- Репликация ускоряет чтение и даёт отказоустойчивость, но появляется lag.
- CAP заставляет выбирать между согласованностью и доступностью.
- ORM ускоряет разработку, но требует контроля (N+1, массовые операции).
- Alembic версионирует схему.

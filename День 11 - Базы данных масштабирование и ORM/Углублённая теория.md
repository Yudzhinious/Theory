## 1. Партиционирование и pruning

- Партиции по **range/list/hash**; запрос обращается только к нужным (`partition pruning`).
- Партиции могут быть **вложенными**; возможен `partition-wise join`.
- `DROP PARTITION` почти мгновенен в отличие от массового `DELETE`.

```sql
CREATE TABLE logs (created_at date, msg text)
PARTITION BY RANGE (created_at);
```

```sql
-- Декларативные партиции (PostgreSQL 10+)
CREATE TABLE logs_2026_01 PARTITION OF logs
    FOR VALUES FROM ('2026-01-01') TO ('2026-02-01');

-- Подпартиции: logs → по дате → по региону
CREATE TABLE logs (
    created_at date,
    region text,
    msg text
) PARTITION BY RANGE (created_at);

CREATE TABLE logs_2026_01 PARTITION OF logs
    FOR VALUES FROM ('2026-01-01') TO ('2026-02-01')
    PARTITION BY LIST (region);
```

| Термин | Смысл |
|---|---|
| Partition pruning | планировщик читает только нужные партиции |
| Partition-wise join | JOIN партиция-к-партиции без перетасовки |
| Attach/Detach | подключение/отключение партиции |

**Как неправильно / как правильно:**

```sql
-- ❌ Функция на ключе партиционирования ломает pruning
WHERE date_trunc('month', created_at) = '2026-01-01'

-- ✅ Сравнение с константой диапазона → pruning работает
WHERE created_at >= '2026-01-01' AND created_at < '2026-02-01'
```

## 2. Шардирование и consistent hashing

- **Range sharding** — простые диапазоны, но «горячие» шарды.
- **Hash sharding** — равномернее; при добавлении узла переезжает много ключей.
- **Consistent hashing** — при добавлении узла перераспределяется лишь часть ключей (виртуальные узлы).
- **Проблемы:** кросс-шардовые JOIN/транзакции, перебалансировка, глобальные ID (**Snowflake**: timestamp + machine + sequence).

### 2.1 Почему обычный хеш плохо масштабируется

```text
shard = hash(key) % N        # N — число шардов
```

Добавили шард (`N` изменилось) → `hash % N` меняется почти для **всех** ключей →
приходится перевозить почти все данные. Это «перебалансировка-катастрофа».

### 2.2 Consistent hashing

Ключи и узлы отображаются на **кольцо**. Ключ идёт к ближайшему узлу по часовой
стрелке. При добавлении узла переезжает только часть ключей между соседями.

```text
Кольцо:  ... — nodeA — nodeB — nodeC — ...
Ключ k → ближайший узел справа.
Добавили nodeD между A и B → переезжает лишь диапазон (A, D].
```

**Виртуальные узлы:** каждый физический узел представлен несколькими точками
на кольце — распределение ровнее.

| Метод | Перебалансировка | Горячие точки | Сложность |
|---|---|---|---|
| Range | средняя | да (монотонные ключи) | низкая |
| Hash (`% N`) | почти всё | нет | низкая |
| Consistent hashing | часть | нет | средняя |

### 2.3 Глобальные ID (Snowflake)

```text
64 бита = [ 41 бит timestamp | 10 бит machine | 12 бит sequence ]
```

ID уникален, монотонно растёт и генерируется локально на каждом узле без
обращения к центральному сервису.

## 3. Репликация и отказоустойчивость

- **Синхронная** — надёжнее, медленнее; **асинхронная** — быстрее, возможна потеря; **полусинхронная** — компромисс.
- **Физическая** (WAL/binlog) vs **логическая** (изменения строк/команд, гибче).
- **Failover:** promotion реплики в мастер; риск **split-brain**.
- **Replication lag** — реплика отстаёт; чтение после записи может не увидеть данные (read-your-writes).

### 3.1 Физическая vs логическая

| | Физическая | Логическая |
|---|---|---|
| Что передаётся | байты WAL/страниц | логические изменения |
| Совместимость версий | нужна одинаковая | между версиями |
| Выборочность | вся БД | таблицы/схемы |
| Применение | standby, HA | репликация, CDC, миграции |

### 3.2 Failover и split-brain

**Failover** — при отказе мастера одна реплика «повышается» (promotion) и
становится новым мастером. Если сеть разделилась и обе стороны считают себя
мастером — это **split-brain**: два мастера принимают конфликтующие записи.
Защита — кворум/арбитр и fencing.

### 3.3 Read-your-writes

```text
Пользователь: PUT /profile (на мастер)
Затем:        GET /profile (с реплики, которая ещё отстаёт) → старые данные
```

Решения:
- читать с мастера сразу после своей записи;
- «sticky» маршрутизация сессии на мастера на короткое время;
- отслеживать LSN и ждать, пока реплика догонит.

## 4. CAP, PACELC и модели согласованности

- **CAP:** при разрыве сети выбираешь Consistency или Availability.
- **PACELC:** дополняет — даже без разрыва есть выбор между Latency и Consistency.
- Модели: **strong**, **eventual**, **causal**, **read-your-writes**, **monotonic reads**.
- **Quorum:** `R + W > N` — пересечение множеств чтения/записи.

**PACELC** расшифровывается: **P**artition — choose **A** or **C**; **E**lse —
choose **L** or **C**. То есть даже в нормальной работе распределённая система
выбирает между низкой задержкой (L) и согласованностью (C).

```text
N = 3 реплики
W = 2 (пишем в 2), R = 2 (читаем из 2)
R + W = 4 > N = 3  → множества пересекаются → видим последнюю запись
```

| Модель | Гарантия |
|---|---|
| Strong | все читатели видят последнюю запись |
| Eventual | со временем сойдётся |
| Causal | причина видна до следствия |
| Read-your-writes | вижу свою запись |
| Monotonic reads | не откатываюсь назад во времени |

## 5. Кэширование

- **Redis/Memcached** — in-memory key-value.
- Паттерны: **cache-aside** (приложение само), **write-through**, **write-behind**, **read-through**.
- **Инвалидация** — самая сложная часть (TTL, явная инвалидация, версии ключей).
- **Cache stampede** — много запросов одновременно при промахе; лечится блокировками/early recompute.
- **Redis** умеет структуры, TTL, pub/sub, транзакции (`MULTI/EXEC`), Lua.

### 5.1 Паттерны кэширования

| Паттерн | Как работает | Плюс | Минус |
|---|---|---|---|
| Cache-aside | приложение читает кэш, при промахе — БД и кладёт в кэш | просто | возможна устаревшесть |
| Read-through | кэш сам читает БД | прозрачно | нужна поддержка |
| Write-through | пишем в кэш и БД сразу | согласованно | медленная запись |
| Write-behind | пишем в кэш, БД позже | быстрая запись | риск потери |

Пример cache-aside:

```python
def get_user(user_id):
    cached = redis.get(f"user:{user_id}")
    if cached is not None:
        return json.loads(cached)          # попадание
    user = db.query(User, user_id)          # промах → БД
    redis.setex(f"user:{user_id}", 300, json.dumps(user))  # TTL 5 мин
    return user
```

### 5.2 Инвалидация

**«Есть только две сложные вещи в Computer Science: инвалидация кэша и
именование».** Подходы:
- **TTL** — данные живут N секунд, потом обновляются;
- **явная инвалидация** — при изменении удаляем ключ;
- **версионирование ключа** — `user:1:v5`, версия меняется при апдейте.

### 5.3 Cache stampede

Если популярный ключ истёк, сотни запросов одновременно идут в БД. Решения:
- **блокировка** — только один запрос пересчитывает, остальные ждут;
- **early recompute** — обновлять ключ заранее, до истечения;
- **jitter** — случайный разброс TTL, чтобы ключи не истекали синхронно.

### 5.4 Redis vs Memcached

| | Redis | Memcached |
|---|---|---|
| Структуры | строки, списки, хэши, множества, streams | только key-value |
| Персистентность | есть (RDB/AOF) | нет |
| Pub/Sub, Lua | есть | нет |
| Потоки | однопоточный event loop | многопоточный |

## 6. Пул соединений

- Открытие соединения дорого; **пул** переиспользует.
- В приложении — `pool_size`, `max_overflow` (SQLAlchemy).
- Отдельный пулер: **PgBouncer** (transaction/session pooling) для Postgres.
- Следи за утечками: соединения должны возвращаться в пул.

```python
from sqlalchemy import create_engine

engine = create_engine(
    "postgresql+psycopg://user:pass@host/db",
    pool_size=10,          # постоянных соединений
    max_overflow=20,       # дополнительных сверх pool_size
    pool_timeout=30,       # сколько ждать свободное соединение
    pool_recycle=1800,     # переоткрывать через 30 мин
)
```

**Аналогия:** такси-парк. Открывать новое соединение — как вызывать новую машину
из другого города. Пул — машины, уже стоящие у офиса.

**Типичные ошибки:**
- не закрывать сессию → утечка соединений → пул пуст → таймауты;
- слишком большой пул → БД перегружена контекстными переключениями;
- держать соединение открытым во время долгих вычислений.

## 7. ORM изнутри

- **Unit of Work** — сессия накапливает изменения и сбрасывает их (`flush`).
- **Identity Map** — один объект на строку в рамках сессии.
- **Lazy** vs **Eager** загрузка; **N+1** и решения (`selectinload`, `joinedload`).
- **Flush vs Commit:** flush отправляет SQL, commit фиксирует транзакцию.
- `expire_on_commit` — объекты обновляются после коммита.

```python
with Session(engine) as session:
    user = session.get(User, 1)       # identity map
    user.name = "new"                 # dirty
    session.flush()                   # UPDATE, но не commit
    session.commit()                  # фиксация
```

**Репозиторий** — абстракция над ORM, чтобы домен не зависел от SQLAlchemy.

### 7.1 Unit of Work и Identity Map (пошагово)

```python
with Session(engine) as s:
    a = s.get(User, 1)      # SELECT → объект A, записан в identity map
    b = s.get(User, 1)      # БЕЗ запроса: возвращается тот же объект A
    print(a is b)           # True

    a.name = "Аня"          # объект стал dirty
    s.flush()               # здесь уходит UPDATE в БД (внутри транзакции)
    s.rollback()            # можно откатить — до commit
```

| Понятие | Смысл |
|---|---|
| Unit of Work | сессия копит изменения и отправляет пачкой |
| Identity Map | одна строка = один Python-объект на сессию |
| Dirty | изменённый объект |
| Flush | отправить SQL, не завершая транзакцию |
| Commit | зафиксировать транзакцию |

### 7.2 Flush vs Commit

| | Flush | Commit |
|---|---|---|
| Что делает | отправляет SQL | фиксирует транзакцию |
| Видно другим | нет (транзакция открыта) | да |
| Откат | возможен | нет (нужна новая транзакция) |
| Авто | перед запросом/commit | вручную |

### 7.3 Ловушка lazy-loading после закрытия сессии

```python
with Session(engine) as s:
    user = s.get(User, 1)
print(user.posts)   # ❌ DetachedInstanceError: сессия закрыта, lazy-load невозможен
```

Решение — загрузить связи заранее (`selectinload`) или не закрывать сессию.

### 7.4 Репозиторий

```python
class UserRepository:
    def __init__(self, session):
        self.session = session

    def get(self, user_id: int) -> User | None:
        return self.session.get(User, user_id)

    def add(self, user: User) -> None:
        self.session.add(user)
```

Домен вызывает `repo.get(...)`, не зная про SQLAlchemy. Это упрощает тесты
(можно подставить in-memory реализацию).

## 8. Миграции (Alembic) — практика

```bash
alembic revision --autogenerate -m "add column"
alembic upgrade head
alembic downgrade -1
```

- Autogenerate не всегда точен (переименования, ограничения) — **проверяй сгенерированный файл**.
- Миграции должны быть идемпотентны и совместимы с работающей версией (expand/contract для zero-downtime).

### 8.1 Expand/Contract для zero-downtime

Меняем схему так, чтобы старая и новая версии приложения работали одновременно:

1. **Expand** — добавить новую колонку (nullable), старый код её игнорирует.
2. **Migrate** — бэкфилл данных, новый код пишет в оба места.
3. **Contract** — удалить старую колонку, когда старый код выведен.

```sql
-- Expand
ALTER TABLE users ADD COLUMN email_new TEXT;
-- Backfill
UPDATE users SET email_new = email WHERE email_new IS NULL;
-- Contract (позже)
ALTER TABLE users DROP COLUMN email;
```

**Типичная ошибка:** `ALTER TABLE ... SET NOT NULL` на большой таблице блокирует
запись на время проверки. Решение — сначала backfill, потом constraint отдельно.

## 0. О чём этот день

Когда браузер открывает сайт, происходит много «невидимого»: сервер узнаёт вас по
cookie, браузер проверяет безопасность соединения, а API отдаёт данные по строго
устроенным адресам. Здесь разберём эти механизмы простым языком.

> **Аналогия.** Cookie — как номерок в гардеробе: сервер выдал, браузер предъявляет
> при каждом визите. HTTPS — бронированная машина для перевозки номера. CORS — правила
> проходной, кому можно подходить к вашим данным из другого здания.

## 1. Cookies

**Cookie** — небольшой фрагмент данных, который сервер отправляет клиенту, а браузер прикладывает к последующим запросам к тому же домену.

**Установка:** заголовок `Set-Cookie` в ответе; далее браузер шлёт `Cookie: name=value`.

**Атрибуты cookie:**
| Атрибут | Смысл |
|---|---|
| `Domain` | на какой домен отправлять |
| `Path` | для каких путей |
| `Expires` / `Max-Age` | срок жизни (иначе — сессионная) |
| `HttpOnly` | недоступна из JS (защита от XSS) |
| `Secure` | отправлять только по HTTPS |
| `SameSite` | `Strict`/`Lax`/`None` — защита от CSRF |

```
Set-Cookie: session_id=abc123; HttpOnly; Secure; SameSite=Lax; Max-Age=3600
```

**Cookies vs Web Storage:**
- Cookies автоматически уходят на сервер (и ограничены ~4 КБ).
- `localStorage`/`sessionStorage` живут в браузере, доступны только JS, не отправляются автоматически (токены часто хранят здесь, но это уязвимо к XSS).

### 1.1 Как работает сессия на cookie — по шагам

1. Пользователь логинится: `POST /login` с логином и паролем.
2. Сервер проверяет данные и отвечает `Set-Cookie: session_id=abc123; HttpOnly`.
3. Браузер сохраняет cookie и **автоматически** прикладывает его к каждому запросу
   к тому же домену: `Cookie: session_id=abc123`.
4. Сервер по `session_id` находит сессию в хранилище и понимает, кто вы.

```text
Клиент                                 Сервер
  |-- POST /login (логин, пароль) ------>|
  |<-- 200 + Set-Cookie: session_id=... -|
  |-- GET /profile                       |
  |    Cookie: session_id=abc123 ------->|  находит сессию
  |<-- 200 (данные профиля) -------------|
```

### 1.2 `HttpOnly`, `Secure`, `SameSite` — зачем каждый

- **HttpOnly** — cookie нельзя прочитать из JavaScript. Даже если злоумышленник
  внедрит JS (XSS), украсть сессию не выйдет.
- **Secure** — cookie уходит только по HTTPS, не по открытому HTTP.
- **SameSite** — ограничивает отправку cookie при переходах с других сайтов:
  - `Strict` — не отправлять вообще при кросс-сайт запросе;
  - `Lax` — отправлять при обычной навигации (переход по ссылке), но не при
    POST с другого сайта (значение по умолчанию в современных браузерах);
  - `None` — отправлять всегда (обязателен `Secure`).

### 1.3 Cookies vs localStorage vs sessionStorage

| | Cookie | localStorage | sessionStorage |
|---|---|---|---|
| Отправляется на сервер | Автоматически | Нет | Нет |
| Размер | ~4 КБ | ~5–10 МБ | ~5–10 МБ |
| Срок жизни | По `Expires`/`Max-Age` | До удаления | До закрытия вкладки |
| Доступ из JS | Если нет `HttpOnly` | Да | Да |
| Уязвимость | CSRF | XSS | XSS |

> **Правило:** идентификатор сессии — в `HttpOnly` cookie; токены в `localStorage`
> хранить рискованно (XSS их читает).

### 1.4 Типичная ошибка

```
# ПЛОХО: cookie без защиты
Set-Cookie: session_id=abc123

# ХОРОШО: HttpOnly + Secure + SameSite
Set-Cookie: session_id=abc123; HttpOnly; Secure; SameSite=Lax
```

## 2. HTTPS и TLS

- **HTTP** — открытый текст, порт **80**. **HTTPS** — HTTP поверх TLS, порт **443**.
- TLS обеспечивает: **шифрование** (конфиденциальность), **целостность**, **аутентификацию сервера** (сертификат от CA).
- Handshake: клиент и сервер договариваются о шифрах, проверяют сертификат, обмениваются ключами.
- Cookies с флагом `Secure` передаются только по HTTPS.

### 2.1 Три гарантии TLS

| Свойство | Что означает | Против чего защищает |
|---|---|---|
| Конфиденциальность | Данные зашифрованы | Подслушивание |
| Целостность | Данные не изменены | Подмена в пути |
| Аутентификация | Сервер тот, за кого себя выдаёт | Поддельный сайт |

### 2.2 Handshake простыми словами

1. Клиент говорит «привет», предлагает версии и шифры.
2. Сервер выбирает шифр и присылает **сертификат** (подписан удостоверяющим центром, CA).
3. Клиент проверяет сертификат: домен совпадает, подпись валидна, не истёк.
4. Стороны обмениваются ключами (современный вариант ECDHE) и выводят общий секрет.
5. Дальше весь трафик шифруется симметричным ключом.

```text
Клиент                          Сервер
  |-- ClientHello ------------->|
  |<-- ServerHello + сертификат -|
  |-- проверка CA, обмен ключами|
  |== зашифрованный канал ======|
```

### 2.3 Типичная ошибка

```
# ПЛОХО: доверять самоподписанному сертификату в продакшене
requests.get(url, verify=False)      # уязвимо к MITM-атаке

# ХОРОШО: проверять сертификат (по умолчанию verify=True)
requests.get(url)
```

## 3. CORS (Cross-Origin Resource Sharing)

Механизм **браузера** (не атака!), управляющий кросс-доменными запросами.

- **Origin** = схема + хост + порт. Другой origin → кросс-доменный запрос.
- Для «сложных» запросов браузер шлёт предварительный **preflight** (`OPTIONS`) с `Access-Control-Request-Method`.
- Сервер отвечает заголовками `Access-Control-Allow-Origin`, `-Methods`, `-Headers`, `-Credentials`.

```python
# FastAPI
from fastapi.middleware.cors import CORSMiddleware
app.add_middleware(
    CORSMiddleware,
    allow_origins=["https://example.com"],
    allow_methods=["*"],
    allow_headers=["*"],
    allow_credentials=True,
)
```

> CORS защищает **пользователя в браузере**, а не сервер от прямых запросов (curl их не блокирует).

### 3.1 Что считается другим origin

| Страница | Запрос к | Один origin? |
|---|---|---|
| `https://a.com` | `https://a.com/api` | Да |
| `https://a.com` | `https://a.com:8443` | Нет (порт) |
| `https://a.com` | `http://a.com` | Нет (схема) |
| `https://a.com` | `https://b.com` | Нет (хост) |

### 3.2 Simple vs preflight

- **Simple request** (GET/POST/HEAD с простыми заголовками, `Content-Type` из ограниченного
  набора) — отправляется сразу, ответ читается, только если сервер разрешил origin.
- **Сложный запрос** (PUT/DELETE, кастомные заголовки, JSON `Content-Type: application/json`)
  — сначала `OPTIONS`-preflight, и только после разрешения — сам запрос.

```text
Браузер                           Сервер
  |-- OPTIONS /api (Origin: b.com) -->|
  |<-- 204 Allow-Origin: b.com -------|
  |-- POST /api (Origin: b.com) ----->|
  |<-- 200 ---------------------------|
```

### 3.3 Типичная ошибка

```python
# ПЛОХО: '*' + credentials несовместимы
allow_origins=["*"]
allow_credentials=True          # браузер отклонит

# ХОРОШО: явный список origin
allow_origins=["https://app.example.com"]
allow_credentials=True
```

## 4. CSRF и XSS

**CSRF (Cross-Site Request Forgery):** злоумышленник заставляет браузер аутентифицированного пользователя отправить нежелательный запрос.
Защита: CSRF-токены, `SameSite` cookies, проверка `Origin`/`Referer`.

**XSS (Cross-Site Scripting):** внедрение чужого JS на страницу.
Защита: экранирование пользовательских данных, CSP (Content-Security-Policy), `HttpOnly` cookies.

**SQL-инъекции:** не склеивать SQL со строками; использовать параметризованные запросы (или ORM).

### 4.1 CSRF на примере

Вы залогинены в банке, cookie сессии живёт в браузере. Открываете вредный сайт, а там:

```html
<!-- картинка, которая на самом деле отправляет запрос в банк -->
<img src="https://bank.com/transfer?to=hacker&sum=1000">
```

Браузер автоматически приложит cookie банка → перевод уйдёт. Защита — CSRF-токен:
форма содержит секретный токен, известный только вашему сайту.

```html
<form method="post" action="/transfer">
  <input type="hidden" name="csrf_token" value="случайная-строка">
</form>
```

### 4.2 XSS на примере

```python
# ПЛОХО: выводим пользовательский ввод без экранирования
return f"<h1>Привет, {username}</h1>"
# если username = "<script>украстьCookies()</script>" — скрипт выполнится
```

```python
# ХОРОШО: шаблонизатор экранирует по умолчанию (Jinja2 autoescape)
# или вручную: markupsafe.escape(username)
```

### 4.3 Сравнение CSRF и XSS

| | CSRF | XSS |
|---|---|---|
| Что делает | Шлёт запрос от вашего имени | Выполняет чужой JS на странице |
| Где проблема | Доверие к cookie | Доверие к вводу |
| Защита | CSRF-токен, `SameSite` | Экранирование, CSP, `HttpOnly` |
| Крадёт cookie | Нет (не читает) | Да (если нет `HttpOnly`) |

### 4.4 SQL-инъекция

```python
# ПЛОХО: склейка строк — можно подставить SQL
query = f"SELECT * FROM users WHERE name = '{name}'"
# name = "' OR '1'='1" -> вернёт всех пользователей

# ХОРОШО: параметризованный запрос
cursor.execute("SELECT * FROM users WHERE name = %s", (name,))
```

## 5. Анатомия URL / API-адреса

```
https://api.example.com:443/v1/users/42?active=true&limit=10#section
└┬─┘   └──────┬───────┘└┬┘└┬┘└───┬───┘└─────────┬────────┘└──┬──┘
scheme       host      port path           query          fragment
```

- **scheme** — `http`/`https`.
- **host** — домен (с поддоменом, часто `api.`).
- **port** — 80/443 по умолчанию (можно опускать).
- **path** — ресурс, `/users/42`.
- **query** — параметры `?key=value&...`.
- **fragment** — якорь, на сервер не отправляется.

**Path-параметры** (`/users/{id}`) — идентификация ресурса.
**Query-параметры** (`?limit=10&sort=desc`) — фильтрация, сортировка, пагинация.

### 5.1 Разбор в Python

```python
from urllib.parse import urlparse, parse_qs

url = "https://api.example.com:443/v1/users/42?active=true&limit=10#section"
u = urlparse(url)
print(u.scheme)    # https
print(u.netloc)    # api.example.com:443
print(u.path)      # /v1/users/42
print(u.query)     # active=true&limit=10
print(u.fragment)  # section
print(parse_qs(u.query))   # {'active': ['true'], 'limit': ['10']}
```

### 5.2 Path vs query

| | Path-параметр | Query-параметр |
|---|---|---|
| Вид | `/users/42` | `?limit=10` |
| Смысл | Какой ресурс | Как его отобрать |
| Обязателен | Обычно да | Обычно нет |
| Пример | id, slug | фильтр, сортировка, пагинация |

### 5.3 URL-кодирование

Пробелы и спецсимволы кодируются: пробел → `%20` (или `+` в query), кириллица — в
проценты. Это нужно, чтобы адрес оставался ASCII.

```python
from urllib.parse import quote, urlencode
print(quote("привет мир"))            # %D0%BF%D1%80%D0%B8%D0%B2%D0%B5%D1%82%20%D0%BC%D0%B8%D1%80
print(urlencode({"q": "a b", "page": 1}))   # q=a+b&page=1
```

## 6. Проектирование API

- **Версионирование:** `/v1/users` или заголовок `Accept: application/vnd.api+json;version=1`.
- **Пагинация:** `?limit=20&offset=40` (offset) или `?page=3&size=20`, либо cursor-based (`?after=...`).
- **Фильтрация/сортировка:** `?status=active&sort=-created_at`.
- **Множественные параметры:** `?ids=1,2,3` или `?id=1&id=2`.
- **Rate limiting:** заголовки `X-RateLimit-Limit/Remaining/Reset`, ответ `429 Too Many Requests`.
- **HATEOAS:** ссылки на связанные ресурсы в ответе (высший уровень зрелости REST).

### 6.1 Виды пагинации

| Вид | Пример | Плюс | Минус |
|---|---|---|---|
| Offset | `?limit=20&offset=40` | Просто, прыжки на страницу | Сдвиг при вставках |
| Page | `?page=3&size=20` | Понятно людям | То же, что offset |
| Cursor | `?after=id123` | Стабильно, быстро | Нельзя прыгнуть на стр. N |

```text
Offset:  [стр.1][стр.2][стр.3]   — при добавлении записи всё «сдвигается»
Cursor:  после id123 → следующие — стабильно, даже если данные меняются
```

### 6.2 Rate limiting

```http
HTTP/1.1 429 Too Many Requests
X-RateLimit-Limit: 100
X-RateLimit-Remaining: 0
X-RateLimit-Reset: 1710000000
Retry-After: 60
```

### 6.3 Коды ответов HTTP (часто спрашивают)

| Код | Смысл |
|---|---|
| 200 OK | Успех |
| 201 Created | Создано |
| 204 No Content | Успех без тела |
| 301/302 | Редирект |
| 400 Bad Request | Ошибка клиента |
| 401 Unauthorized | Не аутентифицирован |
| 403 Forbidden | Аутентифицирован, но нет прав |
| 404 Not Found | Не найдено |
| 429 Too Many Requests | Слишком много запросов |
| 500 Internal Server Error | Ошибка сервера |

## 7. Мини-итог

- Cookie — маленькие данные, автоматически уходящие на сервер; важны `HttpOnly`,
  `Secure`, `SameSite`.
- HTTPS/TLS даёт шифрование, целостность и аутентификацию.
- CORS — механизм браузера; preflight для сложных запросов.
- CSRF — чужие запросы от вашего имени; XSS — чужой JS на странице.
- URL = scheme + host + port + path + query + fragment.
- API проектируют: версии, пагинация, фильтры, rate limit.

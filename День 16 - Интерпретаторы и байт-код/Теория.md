# День 16 — Интерпретаторы и байт-код

> Цель: объяснить, как Python исполняет код, что такое CPython/PyPy и зачем нужен `.pyc`.

---

## 1. Python — компилируемый или интерпретируемый?

### Короткий ответ

Формально: **и то, и другое**. Исходник сначала **компилируется** в **байт-код**,
который затем **исполняется** **виртуальной машиной** (интерпретация). То есть
сначала компиляция, потом интерпретация.

```
исходник .py → компилятор → байт-код .pyc → PVM (виртуальная машина) → результат
```

Аналогия: это как рецепт на иностранном языке. Переводчик (компилятор) переводит
его на «кухонный» язык инструкций (байт-код), а повар (PVM) выполняет шаг за
шагом.

### Почему так, а не чистая интерпретация

Чистая интерпретация «читает текст и сразу делает» была бы очень медленной
(парсинг на каждом шаге). Python парсит **один раз** и дальше гоняет компактные
инструкции.

### Сравнение с другими языками

- **C/C++** — компилируются в машинный код **заранее** (ahead-of-time, AOT).
  Быстро, но привязано к платформе.
- **Java** — компилируется в байт-код JVM, исполняется JIT/интерпретатором.
- **Python (CPython)** — компилируется в байт-код CPython, исполняется в PVM.

| | Компиляция | Байт-код | Исполнение |
|---|---|---|---|
| C/C++ | AOT в машинный код | нет | напрямую CPU |
| Java | AOT в байт-код JVM | да | JVM (JIT) |
| Python | в байт-код CPython | да | PVM |

## 2. Байт-код и модуль `dis`

### Что такое байт-код

**Байт-код** — низкоуровневые инструкции для виртуальной машины Python. Он не
привязан к железу (в отличие от машинного кода) — это «язык» PVM.

```python
import dis

def add(a, b):
    return a + b

dis.dis(add)
# LOAD_FAST a, LOAD_FAST b, BINARY_OP +, RETURN_VALUE
```

Подробный вывод (Python 3.11+):

```
  2           0 RESUME                   0
  3           2 LOAD_FAST                0 (a)
              4 LOAD_FAST                1 (b)
              6 BINARY_OP                0 (+)
             10 RETURN_VALUE
```

### Как читать байт-код

PVM — **стековая машина**: инструкции кладут значения в стек и снимают их.

- `LOAD_FAST a` — положить локальную переменную `a` на стек.
- `LOAD_FAST b` — положить `b`.
- `BINARY_OP +` — снять два значения, сложить, положить результат.
- `RETURN_VALUE` — вернуть верхушку стека.

### Как это увидеть вживую

```python
import dis
dis.dis("x = 1 + 2")      # компилирует строку и показывает байт-код
```

### Разбор примера с условием

```python
import dis

def classify(x):
    if x > 0:
        return "positive"
    return "non-positive"

dis.dis(classify)
```

Упрощённо вывод выглядит так:

```
LOAD_FAST   0 (x)          # кладём x на стек
LOAD_CONST  1 (0)          # кладём 0
COMPARE_OP  >              # сравниваем
POP_JUMP_IF_FALSE  ...     # если ложь — прыжок на return "non-positive"
LOAD_CONST  'positive'     # иначе кладём строку
RETURN_VALUE               # возвращаем
```

Так работают **ветвления**: условный переход меняет позицию исполнения. Циклы
устроены похоже — прыжок назад к началу тела цикла.

Байт-код — основа для инструментов: `dis`, профилировщики, JIT, декораторы.

## 3. `.pyc` и `__pycache__`

При импорте модуля CPython кэширует скомпилированный байт-код в
`__pycache__/module.cpython-312.pyc`. При следующем импорте, если исходник не
менялся, байт-код берётся из кэша — быстрее (не нужно парсить снова).

- `.pyc` создаётся **только для импортируемых** модулей (главный скрипт не
  кэшируется — он и так исполняется один раз).
- `__cached__` модуля указывает на `.pyc`.
- Имя содержит версию (`cpython-312`), чтобы кэш разных версий не смешивался.
- Байт-код **не является «защитой» кода** — его можно декомпилировать.

```python
import my_module
print(my_module.__cached__)   # '.../__pycache__/my_module.cpython-312.pyc'
```

### Как это работает по шагам

1. `import my_module` → интерпретатор ищет `my_module.py`.
2. Проверяет `__pycache__/my_module.cpython-312.pyc`.
3. Если `.pyc` есть и его «штамп» (mtime/hash) совпадает с `.py` → использует.
4. Иначе компилирует заново и сохраняет `.pyc`.

### Типичные ошибки

```bash
# Плохо: коммитить __pycache__ в git
git add __pycache__/

# Хорошо: добавить в .gitignore
echo "__pycache__/" >> .gitignore
echo "*.pyc" >> .gitignore
```

```python
# Плохо: ждать, что .pyc защитит исходник от чтения
# .pyc легко декомпилируется (uncompyle6, decompyle3)
```

## 4. Реализации Python

| Реализация | Особенности |
|---|---|
| **CPython** | эталонная, на C, с GIL. Используется по умолчанию |
| **PyPy** | JIT-компиляция, часто быстрее для CPU-кода, но хуже с C-расширениями |
| **Jython** | на JVM, интеграция с Java |
| **IronPython** | на .NET |
| **MicroPython** | для микроконтроллеров |
| **GraalPy** | на GraalVM |

> В Python 3.13+ появился экспериментальный CPython без GIL (free-threaded). До
> этого GIL — часть CPython, а не языка.

### Как выбрать реализацию

- Обычная разработка → **CPython** (совместимость).
- Тяжёлые CPU-вычисления без C-расширений → попробовать **PyPy**.
- Нужна интеграция с Java/.NET → Jython/IronPython (редко).
- Микроконтроллеры → **MicroPython**.

## 5. Интерпретация vs компиляция vs JIT

- **Интерпретация** — исполнение инструкций по одной во время работы.
- **Компиляция (AOT)** — перевод в машинный код заранее.
- **JIT (Just-In-Time)** — компиляция «горячих» участков **во время выполнения**
  (PyPy, JVM). Компромисс: быстрее интерпретации, дороже старт.

Аналогия: интерпретатор — переводчик-синхронист (переводит на лету).
Компилятор AOT — перевод книги целиком до печати. JIT — синхронист, который
запоминает часто повторяемые фразы и потом произносит их быстрее.

| Подход | Скорость | Старт | Пример |
|---|---|---|---|
| Интерпретация | ниже | мгновенный | CPython |
| AOT | высокая | нет (уже собран) | C/C++ |
| JIT | высокая для «горячего» | разогрев | PyPy, JVM |

## 6. Как CPython исполняет программу

1. **Лексер/парсер** → **AST** (абстрактное синтаксическое дерево).
2. **Компилятор** → байт-код.
3. **PVM** (Python Virtual Machine) выполняет байт-код, управляя стеком и
   объектами.

```python
import ast
tree = ast.parse("x = 1 + 2")
print(ast.dump(tree, indent=2))
```

Вывод (фрагмент):

```
Module(
  body=[
    Assign(
      targets=[Name(id='x', ctx=Store())],
      value=BinOp(left=Constant(value=1), op=Add(), right=Constant(value=2)))])
```

**AST** используют линтеры, форматтеры (black), инструменты рефакторинга.

### Аналогия со сборкой мебели

1. **Лексер/парсер** — прочитали инструкцию и поняли, из чего состоит предложение.
2. **AST** — разложили детали по схеме («ножка к сиденью»).
3. **Компилятор** — составили пошаговый план сборки (байт-код).
4. **PVM** — выполняете план шаг за шагом.

### Свойства AST

- Дерево, а не текст: удобно анализировать программно.
- Не зависит от конкретных имён и форматирования.
- Его можно **менять** и компилировать обратно — так работают метапрограммирование
  и макросы (например, в некоторых библиотеках).

## 7. GIL и интерпретатор

GIL — деталь **реализации CPython**, а не языка. Именно из-за него потоки не
дают CPU-параллелизма. В PyPy/Jython GIL ведёт себя иначе (Jython вообще без
GIL). Это частый уточняющий вопрос.

```
Вопрос на собесе: «GIL — часть языка Python?»
Правильный ответ: нет, это деталь CPython.
```

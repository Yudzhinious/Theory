## 1. Гонки, блокировки, дедлоки

- **Race condition** — результат зависит от порядка выполнения потоков.
- **Deadlock** — потоки ждут друг друга (взаимная блокировка). Условия Коффмана: mutual exclusion, hold-and-wait, no preemption, circular wait.
- **Livelock** — потоки активны, но прогресса нет.
- **Starvation** — поток не получает ресурс.
- Правило: **минимизируй общий изменяемый стейт**; используй очереди вместо общих переменных.

```python
import threading
lock = threading.Lock()
def inc():
    global counter
    for _ in range(100_000):
        with lock:
            counter += 1
```

**Аналогия.** Race condition — двое редакторов правят один документ: чья правка
последняя, тот и «победил», чужие изменения потеряны. Deadlock — два человека в
узком коридоре, каждый ждёт, пока другой уступит, и никто не двигается.

### 1.1 Как воспроизвести race condition

```python
import threading

counter = 0

def unsafe():
    global counter
    for _ in range(1_000_000):
        counter += 1

threads = [threading.Thread(target=unsafe) for _ in range(4)]
for t in threads: t.start()
for t in threads: t.join()
print(counter)          # почти всегда МЕНЬШЕ 4_000_000
```

Причина: `counter += 1` — это три операции (`LOAD`, `ADD`, `STORE`). Переключение
потока между ними теряет инкременты.

### 1.2 Четыре условия дедлока (Коффман)

Дедлок возможен только если выполнены **все четыре**:

1. **Mutual exclusion** — ресурс занят кем-то одним.
2. **Hold and wait** — поток держит один ресурс и ждёт второй.
3. **No preemption** — ресурс нельзя отобрать силой.
4. **Circular wait** — есть цикл ожидания A→B→A.

Уберите любое — дедлока не будет. Классический пример:

```python
# ❌ Потенциальный дедлок: разный порядок захвата
def thread1():
    with lock_a:
        with lock_b:
            ...

def thread2():
    with lock_b:
        with lock_a:      # обратный порядок → circular wait
            ...
```

```python
# ✅ Фиксированный глобальный порядок захвата
def thread1():
    with lock_a:
        with lock_b: ...

def thread2():
    with lock_a:          # тот же порядок
        with lock_b: ...
```

### 1.3 Сравнение аномалий

| Явление | Что происходит | Прогресс |
|---|---|---|
| Race condition | результат непредсказуем | есть, но неверный |
| Deadlock | все ждут навсегда | нет |
| Livelock | все «работают», но без толку | нет |
| Starvation | один поток никогда не получает ресурс | есть у других |

## 2. Примитивы синхронизации

| Примитив | Смысл |
|---|---|
| `Lock` | мьютекс (не реентерабельный) |
| `RLock` | реентерабельный (тот же поток может взять снова) |
| `Semaphore` | ограничение до N одновременно |
| `Event` | флаг-сигнал (`set`/`wait`) |
| `Condition` | ожидание условия + уведомление |
| `Barrier` | точка синхронизации N потоков |
| `Queue` | потокобезопасная очередь (лучший способ обмена) |

**Producer–consumer** через `queue.Queue`:
```python
import queue
q = queue.Queue(maxsize=10)
```

Полный пример:

```python
import threading, queue, time

q = queue.Queue(maxsize=5)

def producer():
    for i in range(10):
        q.put(i)                      # блокируется, если очередь полна
        print(f"положил {i}")

def consumer():
    while True:
        item = q.get()
        if item is None:              # сигнал завершения
            break
        print(f"взял {item}")
        q.task_done()

p = threading.Thread(target=producer)
c = threading.Thread(target=consumer)
p.start(); c.start()
p.join()
q.put(None)                           # «таблетка» — остановить потребителя
c.join()
```

> `Queue` сама синхронизирует доступ — вам не нужен отдельный `Lock`. Это и есть
> причина «используй очереди вместо общих переменных».

**Thread-local** — данные, свои для каждого потока:
```python
local = threading.local()
local.user = "x"
```

`threading.local()` удобен, когда каждому потоку нужен свой контекст (например,
своё соединение к БД), и вы не хотите передавать его аргументами.

### 2.1 Lock vs RLock vs Semaphore

```python
# RLock нужен, если метод с локом вызывает другой метод с тем же локом
lock = threading.RLock()

def a():
    with lock:
        b()               # тот же поток берёт лок снова — ок

def b():
    with lock:
        ...

# Semaphore(3) — не более 3 потоков одновременно (например, 3 соединения к БД)
sem = threading.Semaphore(3)
```

| Примитив | Повторный вход тем же потоком | Ограничение N |
|---|---|---|
| `Lock` | нет (дедлок) | 1 |
| `RLock` | да | 1 |
| `Semaphore` | зависит от счётчика | N |

## 3. `multiprocessing` детали

- **Старт процессов:** `fork` (Unix, копирует память), `spawn` (Windows/macOS по умолчанию, свежий интерпретатор), `forkserver`.
- Из-за `spawn` на Windows обязателен `if __name__ == "__main__"`.
- Обмен: `Queue`, `Pipe`, `Manager` (прокси-объекты), `shared_memory`.
- Данные сериализуются через **pickle** — передавай picklable объекты.
- `Pool`/`ProcessPoolExecutor` — пул воркеров.

```python
from multiprocessing import Pool
if __name__ == "__main__":
    with Pool(4) as p:
        print(p.map(abs, [-1, -2, 3]))
```

Вывод:
```text
[1, 2, 3]
```

### 3.1 fork vs spawn vs forkserver

| Метод | Как работает | Плюсы | Минусы |
|---|---|---|---|
| `fork` | копия текущего процесса | быстрый, память наследуется | проблемы с потоками/сокетами |
| `spawn` | новый интерпретатор | чисто, безопасно | медленнее, нужен `__main__` |
| `forkserver` | отдельный серверный процесс форкает | компромисс | сложнее |

### 3.2 Почему данные должны быть picklable

```python
from multiprocessing import Pool

def f(x):
    return x * 2

# ❌ lambda не сериализуется pickle → ошибка
# pool.map(lambda x: x * 2, [1, 2, 3])

# ✅ обычная функция верхнего уровня
if __name__ == "__main__":
    with Pool(2) as pool:
        print(pool.map(f, [1, 2, 3]))
```

**Подводный камень:** не передавайте в процессы открытые соединения (сокеты,
файлы) и замыкания — они не пиклятся.

### 3.3 Общая память vs передача сообщений

```python
from multiprocessing import Process, Queue

def worker(q):
    q.put("привет из процесса")

if __name__ == "__main__":
    q = Queue()
    p = Process(target=worker, args=(q,))
    p.start()
    print(q.get())        # сообщение через очередь
    p.join()
```

`Manager().dict()`/`.list()` дают прокси к общим объектам, но медленнее
`Queue`/`shared_memory`, потому что каждое обращение — межпроцессный вызов.

## 4. `asyncio` изнутри

- **Event loop** управляет задачами; `await` — точка добровольной отдачи управления.
- **Coroutine → Task → Future:** корутину оборачивают в `Task`, который планируется в цикле; `Future` — «обещание» результата.
- **Блокирующий код замораживает весь цикл** → используй `run_in_executor` или async-библиотеки.

```python
import asyncio

async def main():
    results = await asyncio.gather(*tasks)      # все сразу
    async for r in asyncio.as_completed(tasks): # по мере готовности
        ...

asyncio.run(main())
```

Инструменты: `gather`, `as_completed`, `wait`, `Queue`, `Lock`, `Semaphore`, `timeout` (3.11), `TaskGroup` (3.11).

```python
async with asyncio.TaskGroup() as tg:
    tg.create_task(worker(1))
    tg.create_task(worker(2))
```

### 4.1 Как устроен event loop (пошагово)

1. Цикл держит **готовые** задачи и ждёт событий от селектора (сокеты, таймеры).
2. Запускает готовую задачу до ближайшего `await`.
3. На `await` задача регистрирует, чего ждёт (например, таймер), и **возвращает
   управление** циклу.
4. Когда событие пришло, цикл снова делает задачу готовой.
5. Повторяет, пока есть задачи.

```python
import asyncio

async def main():
    task = asyncio.create_task(worker())   # планируем
    print("пока задача работает, мы тут")
    await task                              # ждём результат

asyncio.run(main())
```

### 4.2 Future vs Task vs Coroutine

| Объект | Что это | Кто запускает |
|---|---|---|
| coroutine | `async def`, ещё не выполняется | нужен `await`/Task |
| Future | контейнер результата | низкоуровневый |
| Task | Future + запланированная корутина | event loop |

**Как неправильно:** создать корутину и забыть её await'нуть — она не выполнится
(и Python выдаст предупреждение):

```python
async def main():
    worker()        # ❌ корутина создана, но не запущена
```

```python
async def main():
    await worker()                 # ✅ последовательно
    # или
    asyncio.create_task(worker())  # ✅ конкурентно
```

### 4.3 Таймауты и отмена

```python
import asyncio

async def main():
    try:
        async with asyncio.timeout(1):     # Python 3.11+
            await asyncio.sleep(5)
    except TimeoutError:
        print("не успели")

asyncio.run(main())
```

Отмена кооперативна: задача получит `CancelledError` в ближайшей точке `await`.

## 5. Structured concurrency и `uvloop`

- `TaskGroup` гарантирует: если одна задача падает, остальные отменяются; выход — после всех.
- **`uvloop`** — быстрая замена event loop (на C/libuv), ускоряет asyncio.

```python
# uvloop: pip install uvloop
import asyncio, uvloop

uvloop.install()          # до asyncio.run(...)
asyncio.run(main())
```

Почему `TaskGroup` лучше «голого» `gather` для критичного кода:

| Свойство | `gather` | `TaskGroup` |
|---|---|---|
| Отмена остальных при ошибке | по умолчанию нет | да |
| Ждёт завершения всех | да | да |
| Обработка исключений | нужно вручную | встроенная (ExceptionGroup) |
| Модель | «свободные» задачи | структурная |

## 6. Когда что (уточнённо)

| Сценарий | Инструмент |
|---|---|
| CPU-тяжёлое | `ProcessPoolExecutor`/`multiprocessing` |
| I/O, мало задач | `threading` |
| I/O, тысячи соединений | `asyncio` |
| CPU внутри asyncio | `run_in_executor(ProcessPool)` |

Не смешивай потоки и asyncio без необходимости.

```python
import asyncio
from concurrent.futures import ProcessPoolExecutor

def cpu_heavy(n):
    return sum(i * i for i in range(n))

async def main():
    loop = asyncio.get_running_loop()
    with ProcessPoolExecutor() as pool:
        result = await loop.run_in_executor(pool, cpu_heavy, 10_000_000)
    print(result)

asyncio.run(main())
```

## 8. Мини-итог

- Конкурентность ≠ параллельность; asyncio — конкурентность в одном потоке.
- Общий изменяемый стейт — корень зла; `Queue` решает большинство задач.
- Дедлок ловится фиксированным порядком блокировок и таймаутами.
- Процессы дают истинный параллелизм, но дороги и требуют pickle.
- Structured concurrency (`TaskGroup`) делает async-код предсказуемым.

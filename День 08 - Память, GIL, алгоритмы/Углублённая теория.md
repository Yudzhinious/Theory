## 1. Аллокатор памяти CPython

- **pymalloc** — пул для мелких объектов (≤512 байт): arenas → pools → blocks.
- Крупные объекты — через системный `malloc`.
- Отсюда: много мелких объектов дороже, чем массив.
- `sys.getsizeof(obj)` — размер объекта, но **не** вложенных.

```python
import sys, tracemalloc
tracemalloc.start()
...  # код
print(tracemalloc.get_traced_memory())
```

Инструменты: `tracemalloc`, `memory_profiler`, `objgraph`, `pympler`.

### Устройство pymalloc

| Уровень | Размер | Смысл |
|---|---|---|
| Arena | 256 КБ | большой блок у ОС |
| Pool | 4 КБ | разбит на блоки одного размера |
| Block | ≤512 байт | один объект |

Объекты одного размера переиспользуются из пулов, поэтому создание/удаление мелких объектов быстрое и не дёргает ОС.

### `sys.getsizeof` не считает вложенное

```python
import sys

lst = [1, 2, 3]
print(sys.getsizeof(lst))        # ~88 байт (только сам список)
print(sys.getsizeof(1))          # 28
# вложенные объекты не учтены!
```

Для рекурсивного подсчёта нужен сторонний инструмент (`pympler.asizeof`).

### Измерение памяти через `tracemalloc`

```python
import tracemalloc

tracemalloc.start()
data = [str(i) for i in range(10000)]
current, peak = tracemalloc.get_traced_memory()
print(f"сейчас: {current} байт, пик: {peak} байт")
tracemalloc.stop()
```

### `__slots__` как способ сэкономить

Объект без `__dict__` весит меньше, что важно на миллионах экземпляров (см. День 6/7).

## 2. Reference counting изнутри

- Каждое присваивание/передача → `Py_INCREF`; удаление → `Py_DECREF`.
- При `refcount == 0` вызывается деструктор и память освобождается.
- **Циклы** не освобождаются refcount-ом → их собирает циклический GC.
- `__del__` (финализатор) в циклах может отложить сборку (объекты в `gc.garbage`).

```python
import gc
gc.get_threshold()    # (700, 10, 10)
gc.get_stats()
gc.collect()
```

### `__del__` и его опасность

```python
class Resource:
    def __del__(self):
        print("освобождаю ресурс")

r = Resource()
del r        # печатает "освобождаю ресурс"
```

В цикле `__del__` может вообще не вызваться или отложиться. Поэтому **не полагайтесь на `__del__`** для освобождения ресурсов — используйте `with`/`try-finally`/`weakref.finalize`.

```python
import weakref

class Handle:
    pass

h = Handle()
finalizer = weakref.finalize(h, lambda: print("объект удалён"))
del h        # напечатает "объект удалён"
```

### Почему refcount, а не только GC

Refcount освобождает память **сразу** (детерминированно), что важно для файлов, сокетов и т.п. GC — дополнение для циклов.

### Сравнение подходов

| Механизм | Что освобождает | Когда |
|---|---|---|
| Refcount | объекты без ссылок | немедленно |
| Циклический GC | недостижимые циклы | периодически |
| `weakref` | не удерживает объект | — |

## 3. `weakref` и слабые словари

```python
import weakref
class Node:
    pass

r = weakref.ref(Node())
r()          # объект или None
d = weakref.WeakValueDictionary()
```

Слабые ссылки: кэши, обратные ссылки «ребёнок → родитель», подписки (observer), чтобы не мешать удалению.

### Кэш на `WeakValueDictionary`

```python
import weakref

class Image:
    def __init__(self, path):
        self.path = path

_cache = weakref.WeakValueDictionary()

def load(path):
    img = _cache.get(path)
    if img is None:
        img = Image(path)        # «дорогая» загрузка
        _cache[path] = img
    return img

a = load("cat.png")
b = load("cat.png")
print(a is b)      # True — взяли из кэша
del a, b
# объект исчезнет, и запись в кэше тоже
```

### `WeakSet` для подписчиков

```python
import weakref

class Subject:
    def __init__(self):
        self._subs = weakref.WeakSet()
    def subscribe(self, cb):
        self._subs.add(cb)
    def notify(self, e):
        for cb in self._subs:
            cb(e)
```

Если подписчик больше нигде не используется, он не будет держаться только из-за подписки.

### Ограничения

- Слабая ссылка работает не на все типы: `list`, `dict` не поддерживают `weakref` напрямую (нужны подклассы или `weakref.ref` на пользовательский объект).
- `weakref.ref(obj)` на `int`/`str` невозможен.

## 4. GIL подробнее

- Переключение потоков: раз в `sys.getswitchinterval()` (по умолчанию 5 мс) или при блокирующем I/O.
- CPU-потоки конкурируют за GIL → нет параллелизма, иногда даже медленнее (переключения).
- I/O отпускает GIL → потоки помогают.
- Обход: `multiprocessing`, C-расширения (NumPy/Pandas отпускают GIL), `numba`, `Cython`.
- **Python 3.13+**: экспериментальный free-threaded (no-GIL) CPython (PEP 703).

### Почему CPU-потоки могут быть медленнее

Переключение контекста и борьба за GIL стоят времени. Иногда 4 потока для CPU-задачи работают **медленнее** одного.

```python
import threading, time

def cpu():
    s = 0
    for i in range(10_000_000):
        s += i
    return s

start = time.perf_counter()
threads = [threading.Thread(target=cpu) for _ in range(4)]
for t in threads: t.start()
for t in threads: t.join()
print(time.perf_counter() - start)   # обычно не быстрее, а то и медленнее
```

### Как выбрать инструмент

| Тип задачи | Инструмент |
|---|---|
| Много ожидания I/O | `threading` или `asyncio` |
| Тяжёлые вычисления | `multiprocessing` |
| Числовые массивы | NumPy (отпускает GIL) |
| Много сетевых запросов | `asyncio` + `aiohttp` |

### `sys.setswitchinterval`

```python
import sys
print(sys.getswitchinterval())   # 0.005 (5 мс)
sys.setswitchinterval(0.001)     # чаще переключаться
```

## 5. Амортизированная сложность

- `list.append` — O(1) **амортизированно** (редкие дорогие resize, усреднённо дёшево).
- `dict`/`set` — O(1) **в среднем**, худший O(n).
- Всегда уточняй: худший / средний / амортизированный.

### Как работает динамический массив

Список хранит массив с запасом. Когда места не хватает, он выделяет **больше** (примерно ×1.125–2) и копирует элементы — это `O(n)`. Но такие копирования редки, поэтому в среднем одна `append` стоит `O(1)`.

```python
import sys

lst = []
prev = 0
for i in range(10):
    lst.append(i)
    size = sys.getsizeof(lst)
    if size != prev:
        print(f"len={len(lst)}, bytes={size}")
        prev = size
```

Видно, что ёмкость растёт «ступеньками».

### Три вида сложности

| Вид | Значение | Пример |
|---|---|---|
| Худшая | гарантированный максимум | поиск в хеш-таблице при коллизиях |
| Средняя | ожидаемая | `dict`/`set` O(1) |
| Амортизированная | среднее по длинной серии | `list.append` O(1) |

**Типичная ошибка:** сказать «`in` для списка — быстро». Нет: для `list` это `O(n)`, для `set`/`dict` — `O(1)`.

## 6. Timsort подробнее

- Находит уже отсортированные «runs» и сливает их (merge sort + insertion sort).
- На почти отсортированных данных — близко к O(n).
- **Стабильна**: равные элементы сохраняют порядок.
- `minrun`, galloping mode — оптимизации.

```python
data.sort(key=...)          # на месте, стабильно
sorted(data, reverse=True)  # новый список
```

Стабильность позволяет сортировать по нескольким ключам последовательно.

### `key` вместо `cmp`

В Python 3 нет параметра `cmp`. Вместо него — `key`: функция, возвращающая ключ сортировки.

```python
words = ["banana", "apple", "cherry"]
words.sort(key=len)                 # по длине
words.sort(key=str.lower)           # по алфавиту без учёта регистра
```

### Сложность по памяти

Timsort требует `O(n)` дополнительной памяти на слияние (в худшем случае). `list.sort` сортирует **на месте** и возвращает `None` — частая ошибка:

```python
data = [3, 1, 2]
result = data.sort()    # result = None! (сортировка на месте)
result = sorted(data)   # правильный способ получить новый список
```

### Сравнение с другими

| | Timsort | Quicksort | Merge | Heap |
|---|---|---|---|---|
| Среднее | O(n log n) | O(n log n) | O(n log n) | O(n log n) |
| Худшее | O(n log n) | O(n²) | O(n log n) | O(n log n) |
| Память | O(n) | O(log n) | O(n) | O(1) |
| Стабильна | да | нет | да | нет |

## 7. Алгоритмические приёмы

- **Two pointers** — пары в отсортированном массиве, палиндромы.
- **Sliding window** — подмассив/подстрока фиксированной/переменной длины.
- **Prefix sums** — быстрые суммы диапазонов.
- **Binary search** — O(log n), `bisect`.
- **Хеш-таблица** — частоты, дедупликация, две суммы.
- **Рекурсия + мемоизация** — DP сверху вниз.
- **Табуляция** — DP снизу вверх.

```python
# Two Sum через хеш
def two_sum(nums, target):
    seen = {}
    for i, n in enumerate(nums):
        if target - n in seen:
            return [seen[target - n], i]
        seen[n] = i
```

### Prefix sums

Позволяют отвечать на запрос «сумма на отрезке» за O(1) после O(n) подготовки.

```python
nums = [2, 4, 6, 8]
prefix = [0]
for x in nums:
    prefix.append(prefix[-1] + x)   # [0, 2, 6, 12, 20]

# сумма nums[1:3] = nums[1] + nums[2] = 4 + 6 = 10
print(prefix[3] - prefix[1])        # 10
```

### Скользящее окно переменной длины

```python
def longest_unique(s):
    seen = {}
    left = best = 0
    for right, ch in enumerate(s):
        if ch in seen and seen[ch] >= left:
            left = seen[ch] + 1
        seen[ch] = right
        best = max(best, right - left + 1)
    return best

print(longest_unique("abcabcbb"))   # 3 ("abc")
```

### Частоты через `Counter`

```python
from collections import Counter

print(Counter("mississippi").most_common(2))
# [('i', 4), ('s', 4)]
```

## 8. DP: примеры

- **Fibonacci**: `O(2^n)` → `O(n)` с мемоизацией.
- **Рюкзак 0/1**: таблица по весам.
- **LCS / edit distance**: таблица по строкам.
- **LIS**: O(n log n) через `bisect`.

```python
from functools import lru_cache
@lru_cache(None)
def lcs(a, b):
    if not a or not b: return 0
    if a[0] == b[0]: return 1 + lcs(a[1:], b[1:])
    return max(lcs(a[1:], b), lcs(a, b[1:]))
```

### Memoization (сверху вниз) vs tabulation (снизу вверх)

| | Memoization | Tabulation |
|---|---|---|
| Направление | от задачи к базе | от базы к задаче |
| Реализация | рекурсия + кэш | цикл + таблица |
| Память на стек | есть | нет |
| Считает | только нужные состояния | все состояния |

```python
# Fibonacci: memoization
from functools import lru_cache

@lru_cache(maxsize=None)
def fib_memo(n):
    return n if n < 2 else fib_memo(n - 1) + fib_memo(n - 2)

# Fibonacci: tabulation
def fib_tab(n):
    if n < 2:
        return n
    a, b = 0, 1
    for _ in range(n - 1):
        a, b = b, a + b
    return b

print(fib_memo(30), fib_tab(30))   # 832040 832040
```

### Задача о рюкзаке 0/1

```python
def knapsack(weights, values, capacity):
    n = len(weights)
    dp = [[0] * (capacity + 1) for _ in range(n + 1)]
    for i in range(1, n + 1):
        for w in range(capacity + 1):
            dp[i][w] = dp[i - 1][w]                 # не берём
            if weights[i - 1] <= w:                 # берём
                dp[i][w] = max(dp[i][w],
                               dp[i - 1][w - weights[i - 1]] + values[i - 1])
    return dp[n][capacity]

print(knapsack([1, 2, 3], [10, 15, 40], 5))   # 55
```

### LIS за O(n log n)

```python
import bisect

def lis(nums):
    tails = []
    for x in nums:
        i = bisect.bisect_left(tails, x)
        if i == len(tails):
            tails.append(x)
        else:
            tails[i] = x
    return len(tails)

print(lis([10, 9, 2, 5, 3, 7, 101, 18]))   # 4
```

## 9. Графовые алгоритмы (обзор)

- **BFS** — кратчайший путь в невзвешенном графе.
- **DFS** — обход, циклы, топологическая сортировка.
- **Dijkstra** — кратчайшие пути (неотрицательные веса), куча.
- **Bellman-Ford** — с отрицательными весами.
- **Union-Find** — компоненты связности, Kruskal.
- **Topological sort** — порядок зависимостей.

### BFS

```python
from collections import deque

def bfs(graph, start):
    visited = {start}
    queue = deque([start])
    order = []
    while queue:
        node = queue.popleft()
        order.append(node)
        for nb in graph[node]:
            if nb not in visited:
                visited.add(nb)
                queue.append(nb)
    return order

print(bfs({"A": ["B", "C"], "B": ["A"], "C": ["A"]}, "A"))   # A, B, C
```

### Сравнение

| Алгоритм | Сложность | Для чего |
|---|---|---|
| BFS | O(V + E) | кратчайший путь без весов |
| DFS | O(V + E) | обход, циклы |
| Dijkstra | O((V+E) log V) | кратчайшие пути, веса ≥ 0 |
| Bellman-Ford | O(V·E) | отрицательные веса |
| Union-Find | ~O(α(n)) | связность |

## 10. Мини-итог

- pymalloc оптимизирует мелкие объекты; память измеряйте `tracemalloc`, помня, что `getsizeof` не рекурсивен.
- Refcount освобождает немедленно, но циклы собирает GC по поколениям.
- `weakref` не удерживает объект — идеален для кэшей и обратных ссылок; не полагайтесь на `__del__`.
- GIL ограничивает CPU-потоки; I/O-потоки полезны; для вычислений — процессы.
- Амортизированная сложность объясняет «дешёвый» `list.append`.
- Timsort стабилен и быстр, особенно на почти отсортированных данных.
- Two pointers, окно, prefix sums, хеш-таблицы и DP — базовые приёмы.
- Memoization и tabulation — две стороны DP; графовые алгоритмы — отдельный арсенал.

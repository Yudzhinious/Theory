## 1. FastAPI изнутри

### Из чего собран FastAPI

FastAPI — это «склейка» двух библиотек:

- **Starlette** — ASGI-фреймворк: роутинг, middleware, WebSocket, фоновые задачи.
- **Pydantic** — валидация и сериализация данных по type hints.

Плюс FastAPI добавляет: DI (`Depends`), генерацию OpenAPI, `response_model`.

**ASGI** (Asynchronous Server Gateway Interface) — асинхронный преемник WSGI.
WSGI обрабатывает один запрос на поток синхронно; ASGI умеет `async` и умеет
держать тысячи соединений (WebSocket, long polling).

### Как обрабатывается запрос

```
клиент → ASGI-сервер (uvicorn)
       → middleware (снаружи внутрь)
       → маршрутизация по path+method
       → разрешение зависимостей (Depends)
       → валидация входа (Pydantic)
       → вызов эндпоинта
       → сериализация выхода (response_model)
       → middleware (изнутри наружу)
       → клиент
```

### `def` vs `async def` — важнейший нюанс

- Эндпоинт `async def` исполняется **в event loop**. Если внутри вызвать
  блокирующий код (`requests.get`, тяжёлый цикл, синхронный драйвер БД), event
  loop встанет — все остальные запросы подождут.
- Эндпоинт `def` FastAPI автоматически уносит в **threadpool**, чтобы не
  блокировать loop.

```python
import time
from fastapi import FastAPI
app = FastAPI()

@app.get("/blocking")
async def blocking():
    time.sleep(3)         # ПЛОХО: блокирует весь event loop на 3 секунды
    return {"ok": True}

@app.get("/offloaded")
def offloaded():
    time.sleep(3)         # ок: FastAPI выполнит это в отдельном потоке
    return {"ok": True}

@app.get("/proper")
async def proper():
    import asyncio
    await asyncio.sleep(3)   # ЛУЧШЕ: не блокирует loop
    return {"ok": True}
```

**Правило:** либо `async def` и только неблокирующие вызовы, либо обычный `def`
с блокирующими вызовами (FastAPI сам вынесет в поток). Смешивать нельзя.

### Dependency Injection глубже

Граф зависимостей может быть вложенным: зависимость сама зависит от других.
FastAPI разрешает их и **кэширует** в пределах запроса (по умолчанию).

```python
def get_settings():
    return Settings()

def get_db(settings = Depends(get_settings)):
    ...

@app.get("/x")
def x(db = Depends(get_db), settings = Depends(get_settings)):
    # settings здесь тот же объект, что и внутри get_db (кэш запроса)
    ...
```

Полезные возможности:

- `Depends(use_cache=False)` — отключить кэширование.
- Классы как зависимости: `Depends(Service)`.
- `Security` — зависимости с проверкой прав/токенов.

### Lifespan — startup/shutdown

```python
from contextlib import asynccontextmanager
from fastapi import FastAPI

@asynccontextmanager
async def lifespan(app: FastAPI):
    # startup
    print("открываем пул соединений")
    yield
    # shutdown
    print("закрываем пул соединений")

app = FastAPI(lifespan=lifespan)
```

Раньше было `@app.on_event("startup")` / `("shutdown")`, но они устарели —
используйте `lifespan`.

### Остальные возможности

- **Middleware**, роутеры (`APIRouter`) для разбиения приложения на модули.
- **BackgroundTasks** — выполнить задачу после ответа (не путать с брокером:
  задачи живут только в памяти процесса и теряются при рестарте).
- **WebSocket** — двусторонний обмен.
- Автодокументация OpenAPI/Swagger на `/docs`, ReDoc на `/redoc`.

```python
from fastapi import APIRouter
router = APIRouter(prefix="/users", tags=["users"])

@router.get("/")
async def list_users(): ...

# в main.py: app.include_router(router)
```

## 2. Pydantic v2

### Что изменилось в v2

Ядро валидации переписано на **Rust** (`pydantic-core`) — обычно в 5–50 раз
быстрее v1. Изменились API и семантика.

| v1 | v2 |
|---|---|
| `.dict()` | `.model_dump()` |
| `.json()` | `.model_dump_json()` |
| `.parse_obj()` | `.model_validate()` |
| `.parse_raw()` | `.model_validate_json()` |
| `@validator` | `@field_validator` |
| `@root_validator` | `@model_validator` |
| `class Config` | `model_config = ConfigDict(...)` |
| `orm_mode` | `from_attributes` |

```python
from pydantic import BaseModel, Field, field_validator, ConfigDict

class User(BaseModel):
    model_config = ConfigDict(from_attributes=True)  # читать из ORM-объектов
    name: str = Field(min_length=1)
    age: int = Field(ge=0)

    @field_validator("name")
    @classmethod
    def strip(cls, v):
        return v.strip()

# Из ORM-объекта (у него есть атрибуты name/age)
user = User.model_validate(orm_user)
```

### Когда валидация происходит

- **При создании модели** — входные данные проверяются сразу.
- **При `model_validate`** — проверить произвольный объект/dict.
- **FastAPI** вызывает это автоматически для тела запроса, query-параметров,
  path-параметров и заголовков.

### `BaseSettings` — конфиги из окружения

```python
from pydantic_settings import BaseSettings

class Settings(BaseSettings):
    db_url: str
    debug: bool = False

    model_config = ConfigDict(env_file=".env")

settings = Settings()   # значения берутся из env / .env
```

Типичные ошибки:

```python
# Плохо: изменяемое значение по умолчанию в модели
class Bad(BaseModel):
    tags: list[str] = []      # общий список на все экземпляры!

# Хорошо: default_factory
from pydantic import Field
class Good(BaseModel):
    tags: list[str] = Field(default_factory=list)
```

## 3. Django глубоко

### ORM и ленивые QuerySet

`QuerySet` **ленив**: запрос к БД не выполняется, пока вы не начнёте итерировать,
не вызовете `list()`, `len()`, `count()`, `exists()`, `first()` и т.п.

```python
qs = User.objects.filter(is_active=True)   # SQL ещё НЕ выполнен
qs = qs.order_by("name")                    # наращиваем запрос
users = list(qs)                            # вот теперь пошёл SQL
```

### N+1 проблема

Классическая беда: делаем один запрос за списком, а потом по одному запросу на
каждый связанный объект.

```python
# ПЛОХО: 1 запрос на книги + N запросов на авторов каждой книги
for book in Book.objects.all():      # 1 запрос
    print(book.author.name)          # +1 запрос на каждую книгу (N)

# ХОРОШО: select_related делает JOIN (для FK/OneToOne)
for book in Book.objects.select_related("author"):
    print(book.author.name)          # всего 1 запрос

# ХОРОШО: prefetch_related — отдельный запрос и «склейка» в Python (для M2M/reverse FK)
for book in Book.objects.prefetch_related("tags"):
    print([t.name for t in book.tags.all()])
```

| Метод | Для чего | Как работает |
|---|---|---|
| `select_related` | FK, OneToOne | SQL `JOIN`, один запрос |
| `prefetch_related` | M2M, reverse FK | отдельные запросы + соединение в Python |

### Middleware, signals, DRF

- **Middleware** — цепочка обработки запроса/ответа (аутентификация, логирование,
  CORS). Порядок важен.
- **Signals** — `post_save`, `pre_delete` и т.д. Удобно, но создаёт неявные
  связи; злоупотребление ведёт к «магии», которую трудно отлаживать.
- **DRF:** сериализаторы (валидация+вывод), ViewSet, Router, permissions,
  throttling, пагинация.
- **Миграции** (`makemigrations`/`migrate`), `manage.py`, `settings.py`, admin.
- Синхронный ORM; async — через `sync_to_async`/`async_to_sync`.

### Частая ошибка Django

```python
# Плохо: бизнес-логика в сигнале post_save — её не видно при чтении view
@receiver(post_save, sender=Order)
def on_order(sender, instance, **kwargs):
    send_email(instance.user)   # где это вызывается? загадка

# Лучше: явный вызов сервиса из view/сервисного слоя
def create_order(...):
    order = Order.objects.create(...)
    notify_order_created(order)
    return order
```

## 4. Брокеры сообщений глубоко

### Delivery semantics (гарантии доставки)

| Семантика | Потери | Дубли | Когда |
|---|---|---|---|
| **at-most-once** | возможны | нет | метрики, логи (потеря не страшна) |
| **at-least-once** | нет | возможны | платежи (важнее не потерять) |
| **exactly-once** | нет | нет | сложно/дорого, обычно эмулируют |

На практике чаще всего **at-least-once + идемпотентный потребитель**: дубликаты
приходят, но обработка повторного сообщения не меняет результат.

```python
# Идемпотентность: повторная обработка того же события безопасна
def handle_payment(event):
    if Payment.objects.filter(event_id=event.id).exists():
        return                    # уже обработали — пропускаем
    Payment.objects.create(...)   # иначе создаём
```

### RabbitMQ

- **Exchanges:** `direct` (точное совпадение ключа), `topic` (шаблоны `a.*.b`),
  `fanout` (всем очередям), `headers` (по заголовкам).
- **Queues** и **bindings** — очереди и правила привязки к exchange.
- **ack/nack** — подтверждение обработки; без ack сообщение вернётся в очередь.
- **prefetch** — сколько сообщений воркер берёт за раз (ограничивает нагрузку).
- **Dead-letter queue (DLQ)** — куда попадают «безнадёжные» сообщения.
- **TTL** — срок жизни сообщения.

### Kafka

- **Топики → партиции**: топик разбит на партиции для параллелизма.
- **offset** — позиция потребителя в партиции.
- **consumer groups** — потребители одной группы делят партиции между собой
  (параллелизм); разные группы читают независимо.
- **retention** — события хранятся заданное время/размер, их можно перечитать.
- Порядок гарантирован **только внутри партиции**.
- **Ключ сообщения → партиция** (одна и та же сущность всегда в одной партиции,
  значит порядок по ней сохраняется).

```python
# Псевдокод консьюмера Kafka
for msg in consumer:            # consumer.poll() под капотом
    process(msg)
    consumer.commit()           # сдвигаем offset
```

### Паттерны

- **Outbox** — атомарно пишем и в БД, и событие в ту же БД (таблица outbox);
  отдельный процесс читает outbox и публикует в брокер. Решает проблему
  «БД закоммитилась, а событие не отправилось».
- **Saga** — распределённая транзакция через набор локальных транзакций и
  **компенсаций** (обратных действий) при сбое.
- **CQRS** — разделение модели чтения и записи.
- **Event sourcing** — состояние хранится как последовательность событий.

### Типичная ошибка

```python
# Плохо: публикуем событие ДО коммита — потребитель прочитает то, чего нет
db.commit_soon()
broker.publish(OrderCreated(id))   # а commit может упасть!

# Хорошо: Outbox — событие в той же транзакции
with transaction.atomic():
    order.save()
    Outbox.objects.create(topic="orders", payload=...)
# отдельный publisher читает Outbox и шлёт в брокер
```

## 5. Микросервисные паттерны

- **API Gateway** — единая точка входа, маршрутизация, аутентификация, rate limit.
- **Service Discovery** — находит инстансы сервиса (Consul, Kubernetes DNS).
- **Circuit Breaker** — разрывает поток к упавшему сервису, даёт ему «остыть»
  (состояния closed → open → half-open).
- **Bulkhead**, **Timeout**, **Retry** (с backoff и jitter), **Rate limit**.
- **Distributed tracing** (OpenTelemetry), централизованные логи, метрики.
- **Идемпотентность** и **eventual consistency** вместо распределённых транзакций.

| Проблема | Паттерн |
|---|---|
| Упал сервис → лавина ошибок | Circuit Breaker, Timeout |
| Дубликаты при retry | Идемпотентность |
| Нет единой транзакции | Saga, Outbox |
| Непонятно, где тормозит | Distributed tracing |
| Внезапный наплыв запросов | Rate limit, Bulkhead |

## 6. Docker глубоко

### Слои и кэш

Каждая инструкция Dockerfile создаёт **слой**. Слои кэшируются: если инструкция
и её входные данные не менялись — слой берётся из кэша.

```dockerfile
FROM python:3.12-slim AS base
WORKDIR /app

# requirements меняется редко -> кэшируем зависимости
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

# код меняется часто -> этот слой пересобирается, но pip уже в кэше
COPY . .

CMD ["uvicorn", "main:app", "--host", "0.0.0.0"]
```

### Multi-stage build

Собираем в «тяжёлом» образе, а в финальный копируем только артефакт.

```dockerfile
# --- этап сборки ---
FROM python:3.12 AS builder
WORKDIR /app
COPY requirements.txt .
RUN pip install --prefix=/install -r requirements.txt

# --- финальный лёгкий этап ---
FROM python:3.12-slim
WORKDIR /app
COPY --from=builder /install /usr/local
COPY . .
CMD ["uvicorn", "main:app", "--host", "0.0.0.0"]
```

### `.dockerignore`, volumes, networks

- **`.dockerignore`** — не копировать лишнее (`.git`, `__pycache__`, `.venv`).
- **Volume** — постоянные данные (БД); **bind mount** — код хоста в контейнер
  (удобно для разработки).
- **Networks** — контейнеры общаются по именам сервисов (в compose).

```yaml
# docker-compose.yml
services:
  web:
    build: .
    ports: ["8000:8000"]
    depends_on: [db]
  db:
    image: postgres:16
    environment:
      POSTGRES_PASSWORD: secret
    volumes:
      - pgdata:/var/lib/postgresql/data
volumes:
  pgdata:
```

Best practices: не root (`USER app`), pinned версии, маленький base
(`-slim`/`alpine`), healthcheck, один процесс на контейнер.

### Как уменьшить размер образа

| Приём | Эффект |
|---|---|
| `-slim`/`alpine` base | меньше базы |
| Multi-stage | нет компиляторов в финале |
| `.dockerignore` | не тащим мусор |
| `--no-cache-dir` в pip | нет кэша pip |
| Объединение `RUN` | меньше слоёв |

## 7. CI/CD (обзор)

- **CI** (Continuous Integration) — линт, тесты, сборка образа на каждый push
  (GitHub Actions, GitLab CI).
- **CD** (Continuous Delivery/Deployment) — деплой в staging/prod,
  blue-green (два окружения, переключение) / canary (постепенно на часть трафика).
- **12-factor:** конфиг в env, логи в stdout, stateless-процессы, паритет сред.

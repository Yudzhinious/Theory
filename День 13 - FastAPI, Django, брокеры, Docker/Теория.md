## 1. FastAPI vs Django

| Критерий | Django | FastAPI |
|---|---|---|
| Тип | full-stack («всё включено») | микрофреймворк для API |
| Асинхронность | ограниченная (ORM синхронный) | полная (`async def`) |
| ORM | встроенный | нет (SQLAlchemy) |
| Админка | есть | нет |
| Валидация | `django.forms` | Pydantic |
| Документация API | через DRF | автоматически (Swagger/ReDoc) |
| Лучше для | сайты, CMS, порталы | API, микросервисы, real-time |

## 2. FastAPI: базовый пример

```python
from fastapi import FastAPI, HTTPException, Depends
from pydantic import BaseModel

app = FastAPI()

class ItemIn(BaseModel):
    name: str
    price: float

class ItemOut(ItemIn):
    id: int

@app.get("/items/{item_id}", response_model=ItemOut)
async def get_item(item_id: int):
    if item_id != 1:
        raise HTTPException(status_code=404, detail="Not found")
    return ItemOut(id=1, name="Book", price=9.99)

@app.post("/items/", response_model=ItemOut, status_code=201)
async def create_item(item: ItemIn):
    return ItemOut(id=2, **item.model_dump())
```

- **Pydantic** валидирует и сериализует данные через type hints.
- Автодокументация: `/docs` (Swagger), `/redoc`.

## 3. Pydantic и зависимости

```python
from pydantic import BaseModel, Field, EmailStr, field_validator

class UserIn(BaseModel):
    name: str = Field(min_length=1, max_length=50)
    email: EmailStr
    age: int = Field(ge=0, le=120)

    @field_validator("name")
    @classmethod
    def strip_name(cls, v):
        return v.strip()
```

**Dependency Injection (Depends):** общие зависимости (сессия БД, текущий пользователь) подставляются автоматически.
```python
def get_db():
    db = SessionLocal()
    try:
        yield db
    finally:
        db.close()

@app.get("/users/")
def read_users(db=Depends(get_db)):
    ...
```

## 4. Микросервисы vs монолит

- **Монолит** — одно приложение, один деплой. Проще разрабатывать и отлаживать, но тяжело масштабировать целиком.
- **Микросервисы** — множество небольших сервисов, общаются по сети. Независимый деплой и масштабирование, но сложнее (сеть, согласованность, наблюдаемость).

**Когда микросервисы:** большая команда, независимые домены, разная нагрузка. Для стажировки/небольших проектов — монолит.

## 5. Брокеры сообщений

Брокер — посредник для асинхронного обмена сообщениями между сервисами.

**Задачи:** развязка сервисов (decoupling), асинхронность, балансировка нагрузки, гарантия доставки.

| | RabbitMQ | Kafka |
|---|---|---|
| Модель | очередь, FIFO, маршрутизация | распределённый лог событий |
| Сообщения | удаляются после прочтения | хранятся, можно перечитывать |
| Лучше для | задачи, RPC, корпоративные системы | стриминг, аналитика, логи, event-driven |

## 6. Docker: контейнеры vs ВМ

- **Виртуальная машина (VM)** — полноценная ОС с гипервизором, тяжёлая, медленно стартует.
- **Контейнер** — изолированный процесс, делит ядро хоста, лёгкий, быстрый старт.

**Ключевые понятия:**
- **Image** — неизменяемый шаблон (слои).
- **Container** — запущенный экземпляр образа.
- **Dockerfile** — инструкция сборки образа.
- **Volume** — постоянное хранилище данных.
- **Registry** — хранилище образов (Docker Hub).

```dockerfile
FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]
```

```bash
docker build -t myapp .
docker run -p 8000:8000 myapp
docker compose up
```

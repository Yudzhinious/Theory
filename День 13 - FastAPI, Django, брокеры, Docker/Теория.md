## 1. FastAPI vs Django

### Что такое фреймворк и зачем он нужен

**Фреймворк** — это «каркас» приложения: набор готовых решений для типовых задач
(разбор HTTP-запроса, роутинг, работа с БД, шаблоны, аутентификация). Вместо того
чтобы писать всё с нуля на голых сокетах, вы берёте фреймворк и заполняете
«пробелы» своей логикой.

Аналогия: фреймворк — это набор Lego. Вы не производите кирпичики, вы собираете
из них замок. Но у разных наборов разная комплектация: где-то есть колёса и
мотор (Django), а где-то только базовые кубики (FastAPI).

### Django — «всё включено»

**Django** — full-stack фреймворк с батарейками в комплекте:

- собственный **ORM** (объектно-реляционный маппинг);
- **админ-панель**, которая генерируется автоматически из моделей;
- система **миграций** (изменение схемы БД по коду);
- **шаблонизатор** для HTML;
- **аутентификация**, сессии, CSRF-защита;
- **Django REST Framework (DRF)** — надстройка для REST API.

Django выбирают, когда нужно быстро сделать «классический» сайт: интернет-магазин,
CMS, портал, админку для менеджеров.

### FastAPI — «микро, но современно»

**FastAPI** — современный микрофреймворк для API. Он сознательно не включает ORM,
админку и шаблоны, но даёт:

- **асинхронность** «из коробки» (`async def`);
- **валидацию** данных через Pydantic и обычные type hints;
- **автодокументацию** OpenAPI (Swagger UI на `/docs`, ReDoc на `/redoc`);
- **Dependency Injection** через `Depends`;
- очень высокую скорость за счёт Starlette (ASGI) и Pydantic (ядро на Rust).

FastAPI выбирают для микросервисов, публичных API, real-time-задач и ML-сервисов.

### Сравнительная таблица

| Критерий | Django | FastAPI |
|---|---|---|
| Тип | full-stack («всё включено») | микрофреймворк для API |
| Асинхронность | ограниченная (ORM синхронный) | полная (`async def`) |
| ORM | встроенный | нет (SQLAlchemy) |
| Админка | есть | нет |
| Валидация | `django.forms` | Pydantic |
| Документация API | через DRF | автоматически (Swagger/ReDoc) |
| Шаблоны HTML | есть | нет (отдаёте JSON) |
| Порог входа | выше (много концепций) | ниже для API |
| Лучше для | сайты, CMS, порталы | API, микросервисы, real-time |

> Важно: FastAPI и Django — не «кто лучше», а «кто уместнее». Для сайта с
> админкой Django сэкономит недели. Для чистого JSON-API FastAPI компактнее.

> Подробнее: `[[FastAPI vs Django]]`.

## 2. FastAPI: базовый пример

### Как это работает по шагам

1. Вы создаёте объект `app = FastAPI()`.
2. Декорируете функцию `@app.get(...)` / `@app.post(...)` — это **роут**.
3. FastAPI по type hints понимает, какие данные придут и что вернётся.
4. Pydantic автоматически валидирует вход и сериализует выход.
5. Swagger-документация собирается сама из этих же аннотаций.

```python
from fastapi import FastAPI, HTTPException, Depends
from pydantic import BaseModel

app = FastAPI()          # создаём приложение

# --- Схемы данных (Pydantic) ---
class ItemIn(BaseModel):          # то, что приходит от клиента
    name: str
    price: float

class ItemOut(ItemIn):            # то, что уходит клиенту
    id: int

# --- GET: чтение одного элемента ---
@app.get("/items/{item_id}", response_model=ItemOut)
async def get_item(item_id: int):        # item_id автоматически приводится к int
    if item_id != 1:
        raise HTTPException(status_code=404, detail="Not found")
    return ItemOut(id=1, name="Book", price=9.99)

# --- POST: создание ---
@app.post("/items/", response_model=ItemOut, status_code=201)
async def create_item(item: ItemIn):     # тело запроса валидируется как ItemIn
    return ItemOut(id=2, **item.model_dump())
```

Пример запроса и ответа:

```bash
curl -X POST http://127.0.0.1:8000/items/ \
     -H "Content-Type: application/json" \
     -d '{"name": "Pen", "price": 1.5}'
```

```json
{"id": 2, "name": "Pen", "price": 1.5}
```

Если прислать `{"name": "Pen", "price": "дорого"}`, FastAPI вернёт **422** с
описанием ошибки — код валидации писать не нужно.

- **Pydantic** валидирует и сериализует данные через type hints.
- Автодокументация: `/docs` (Swagger), `/redoc`.

### Как неправильно / как правильно

```python
# Плохо: ручная валидация, много кода и легко забыть проверку
@app.post("/items/")
async def create_item_bad(payload: dict):
    if "name" not in payload:
        raise HTTPException(400, "name required")
    if not isinstance(payload.get("price"), (int, float)):
        raise HTTPException(400, "price must be number")
    ...

# Хорошо: описали модель — валидация, документация и подсказки бесплатно
@app.post("/items/")
async def create_item_good(item: ItemIn):
    ...
```

> Типичная ошибка: путать `response_model` и возвращаемый тип. `response_model`
> отфильтрует «лишние» поля (например, пароль) перед отправкой клиенту.

## 3. Pydantic и зависимости

### Pydantic: валидация через типы

**Pydantic** берёт ваши аннотации типов и превращает их в правила проверки. Если
данные не подходят — понятная ошибка, а не `KeyError` где-то в глубине кода.

```python
from pydantic import BaseModel, Field, EmailStr, field_validator

class UserIn(BaseModel):
    name: str = Field(min_length=1, max_length=50)
    email: EmailStr                       # проверит формат email
    age: int = Field(ge=0, le=120)        # 0 <= age <= 120

    @field_validator("name")
    @classmethod
    def strip_name(cls, v):
        return v.strip()                  # убираем пробелы по краям

# Валидные данные
u = UserIn(name="  Alice ", email="a@b.com", age=30)
print(u.name)   # 'Alice'

# Невалидные — ValidationError с перечнем проблем
try:
    UserIn(name="", email="not-an-email", age=200)
except Exception as e:
    print(e)
```

### Dependency Injection (Depends)

**Внедрение зависимостей** — это способ отдать функции то, что ей нужно
(сессию БД, текущего пользователя), не создавая это внутри самой функции.

Аналогия: вы приходите в кафе и говорите «мне кофе». Вам не нужно самому
выращивать зерно — официант (DI-контейнер) приносит готовый ресурс.

```python
def get_db():
    db = SessionLocal()      # открываем сессию
    try:
        yield db             # отдаём её в эндпоинт
    finally:
        db.close()           # гарантированно закрываем после ответа

@app.get("/users/")
def read_users(db=Depends(get_db)):
    return db.query(User).all()
```

`yield` в зависимости даёт **setup/teardown**: код до `yield` выполняется перед
эндпоинтом, код после — после ответа (даже если была ошибка).

**Плюсы DI:**

| Без DI | С DI |
|---|---|
| Сессия создаётся в каждой функции | Один общий `get_db` |
| Трудно тестировать (реальная БД) | Легко подменить в тестах |
| Дублирование кода | Переиспользование |
| Явные зависимости разбросаны | Единый граф зависимостей |

### Частая ошибка с зависимостями

```python
# Плохо: соединение не закроется при исключении
def get_db_bad():
    db = SessionLocal()
    return db            # нет finally -> утечка соединений

# Хорошо: yield + finally
def get_db_good():
    db = SessionLocal()
    try:
        yield db
    finally:
        db.close()
```

## 4. Микросервисы vs монолит

### Монолит

**Монолит** — одно приложение, один деплой, одна кодовая база. Все модули
(пользователи, заказы, оплата) живут вместе и вызывают друг друга обычными
функциями.

- Плюсы: просто разрабатывать и отлаживать, одна транзакция на всю операцию,
  простой деплой, легко запустить локально.
- Минусы: масштабируется только целиком, любое изменение требует пересборки
  всего, со временем кодовая база «разрастается», команды мешают друг другу.

### Микросервисы

**Микросервисы** — множество небольших сервисов, каждый отвечает за свою
предметную область и общается с другими по сети (HTTP/gRPC/брокер).

- Плюсы: независимый деплой и масштабирование, каждая команда владеет сервисом,
  можно писать на разных языках.
- Минусы: сетевые сбои, распределённые транзакции (нет простого `ROLLBACK` на
  два сервиса), сложная наблюдаемость (логи, трейсинг), больше инфраструктуры.

Аналогия: монолит — один большой офис, где все кричат через комнату. Микросервисы
— сеть маленьких офисов, которые общаются по телефону (и иногда не дозваниваются).

### Сравнение

| Аспект | Монолит | Микросервисы |
|---|---|---|
| Деплой | один | по сервису |
| Масштабирование | всё сразу | точечно |
| Транзакции | ACID в одной БД | eventual consistency, Saga |
| Отладка | проще | сложнее (распределённая) |
| Порог | низкий | высокий |
| Команда | одна | много независимых |

**Когда микросервисы:** большая команда, независимые домены, разная нагрузка
(один сервис нагружен, другой почти нет). Для стажировки/небольших проектов —
монолит. Даже крупные компании часто начинают с **модульного монолита** —
монолита с чёткими границами модулей, который потом можно «распилить».

> Типичная ошибка: «давайте сразу микросервисы» на старте проекта. Это
> распределённый монолит — худшее из двух миров: сложно как микросервисы,
> связано как монолит.

## 5. Брокеры сообщений

**Брокер сообщений** — посредник для асинхронного обмена сообщениями между
сервисами. Отправитель кладёт сообщение в брокер и забывает о нём; получатель
забирает, когда готов.

Аналогия: почтовое отделение. Вы бросаете письмо в ящик и идёте по делам.
Почта хранит письмо, пока адресат не заберёт. Вам не нужно ждать, пока он
прочитает.

### Зачем нужен брокер

- **Развязка сервисов (decoupling):** сервис заказов не знает, кто и как
  обрабатывает письма — он просто публикует событие `OrderCreated`.
- **Асинхронность:** тяжёлая задача (отправка email, генерация отчёта) не
  тормозит ответ клиенту.
- **Балансировка нагрузки:** несколько воркеров разбирают одну очередь.
- **Устойчивость:** если потребитель упал, сообщения остаются в очереди.
- **Гарантия доставки:** подтверждения (ack) и повторная доставка.

### RabbitMQ vs Kafka

| | RabbitMQ | Kafka |
|---|---|---|
| Модель | очередь, FIFO, маршрутизация | распределённый лог событий |
| Сообщения | удаляются после прочтения | хранятся, можно перечитывать |
| Порядок | в очереди | внутри партиции |
| Потребители | конкурируют за сообщения | группы читают независимо |
| Хранение | нет (по умолчанию) | retention по времени/размеру |
| Лучше для | задачи, RPC, корпоративные системы | стриминг, аналитика, логи, event-driven |

Проще говоря: **RabbitMQ — это «сделай задачу»** (после выполнения сообщение
исчезает), **Kafka — это «журнал событий»** (события хранятся, разные читатели
читают их в своём темпе).

## 6. Docker: контейнеры vs ВМ

### Проблема, которую решает Docker

«У меня работает, а на сервере нет» — классическая беда из-за разных версий
Python, библиотек, переменных окружения. Docker упаковывает приложение **вместе
с его окружением** в образ, который одинаково запускается везде.

### Контейнер vs виртуальная машина

- **Виртуальная машина (VM)** — полноценная ОС с гипервизором, тяжёлая (гигабайты),
  медленно стартует (секунды–минуты), сильная изоляция.
- **Контейнер** — изолированный процесс, делит ядро хоста, лёгкий (мегабайты),
  быстрый старт (доли секунды), изоляция на уровне namespaces/cgroups.

| | ВМ | Контейнер |
|---|---|---|
| Ядро | своё | общее с хостом |
| Размер | ГБ | МБ |
| Старт | секунды–минуты | миллисекунды |
| Изоляция | сильная | достаточная |
| Плотность | мало на хост | много на хост |

Аналогия: ВМ — отдельная квартира со своим водопроводом и электричеством.
Контейнер — комната в общежитии с общей кухней (ядром).

### Ключевые понятия

- **Image** — неизменяемый шаблон (слои). Как «чертёж» или класс.
- **Container** — запущенный экземпляр образа. Как «объект» или запущенный процесс.
- **Dockerfile** — инструкция сборки образа.
- **Volume** — постоянное хранилище данных (данные живут после удаления контейнера).
- **Registry** — хранилище образов (Docker Hub, GitHub Container Registry).

```dockerfile
# Базовый образ: маленький python
FROM python:3.12-slim

# Рабочая директория внутри контейнера
WORKDIR /app

# Сначала только зависимости — это кэшируемый слой
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

# Потом код (меняется чаще — кэш не сбрасывается при правке кода)
COPY . .

# Команда запуска
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]
```

```bash
docker build -t myapp .                 # собрать образ с тегом myapp
docker run -p 8000:8000 myapp           # запустить, пробросив порт
docker ps                               # список запущенных контейнеров
docker compose up                       # поднять несколько сервисов из compose
```

Почему `COPY requirements.txt` идёт **до** `COPY . .`? Docker кэширует слои.
Если изменился только код, слой с `pip install` берётся из кэша — сборка быстрее.

> Типичная ошибка: ставить `COPY . .` в начало. Тогда любая правка кода
> сбрасывает кэш и зависимости переустанавливаются каждый раз.
